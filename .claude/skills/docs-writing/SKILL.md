# 書き方

大きな指針：認知負荷とメンテコストの低いドキュメントを書く。
- 認知負荷：読む人が、少ない労力で正しく仕様をつかめること。
- メンテコスト：仕様が変わったときに、直す箇所が少ないこと。

以下の規則の「なぜ」は、どちらかの柱を指す。

## 書く手順

1. そのリポの `README.md` と `AGENTS.md` を読む。食い違ったら、そちらに従う。
2. 正本をどこに置くか決める。
3. 依存の向きを決める。どのページが、どのページを参照するか。
4. 書く。
5. 最後の「チェックリスト」で確かめる。

## 正本は 1 か所に置き、ほかはリンクで指す

- 同じことを 2 か所に書かない。同じリポでも、別のリポでも。
  - 参照する側には、詳しい内容を書き写さない。該当ページの節へのリンクだけを書く。
  - 散らばっている仕様を見つけたら、1 か所にまとめる。
  - 例：予約の状態と遷移は 1 ページにまとめる。各 API のページは、状態ごとの振る舞いだけを書いてそのページを指す。
  - なぜ：メンテコスト。写しがあると、元が変わるたびに写しも直すことになる。
- 依存を一方向にする。使う側が共通の仕様を参照するのはよい。共通の仕様に使う側のことを書かない。
  - 共通の仕様に書かない：どこで使われるか、個別の API でどう振る舞うか。
  - 共通の仕様に書く：想定用途、想定シーンごとの正しい使い方。
  - 例：認証の仕様には「ログイン後の API 呼び出しで使う」と書く。「予約 API ではこう認証する」とは書かない。
  - 例：予約 API のページには「認証は [認証](../auth/README.md) の『ログイン後の API 呼び出し』に従う」とだけ書く。有効期限やトークンの形は書かない。
  - 仕様書を、スタブや E2E の実装に依存させない。外部の API は OpenAPI などの正本を指す。「E2E で何を保証すべきか」は書いてよい。
  - なぜ：メンテコスト。相互依存があると、使う側が増えるたびに共通の仕様も直すことになる。

## 構成

- 節は「何についてか」で切る。「前提」「仕様」「補足」のような情報の種類で切らない。
  - 悪い：`## 前提`、`## 仕様`、`## 補足`
  - 良い：`## 在庫の引き当て`、`## 予約の取り消し`、`## 通知`
  - なぜ：認知負荷。種類で切ると、1 つの話が複数の節に散る。

### ページの骨組み

- 冒頭の数行に想定用途を書く。どんな場面で、何のために使うか。
  - 用途が書けると、その API が要るかどうかや、値の根拠も決められる。
- 続けて、何についてかで切った節を並べる。
- 理由は、その決まりの隣に書く。「理由」の節を別に作らない。

## 書き方

- 1 行（1 文）に 1 つのことだけを書く。条件・項目・手順・例外が並ぶなら箇条書きにする。
  - 悪い：`重複の判定は会員・店舗・日付・時間帯（人数は比べず、取り消し済みも重複に含める）で行う。`
  - 良い：
    ```
    次の項目が同じなら、重複した予約とみなす。
    - 会員
    - 店舗
    - 日付
    - 時間帯

    人数は比べない。取り消し済みの予約も重複に含める。
    ```
  - 表のセルに長い文を入れない。文章になるなら表をやめる。
  - なぜ：認知負荷。詰めた文は読み飛ばされ、読み違えられる。
- 決まった技術用語を使う。造語、遠回しな言い換え、日本語として不自然な語を使わない。
  - 悪い：「何回か間違えたら止める」「予約を作る口」「仮のしるし」
  - 良い：「アカウントロック」「予約作成 API」「二要素認証」
  - 名前の無い機能には、名前を付けてから書く。
  - なぜ：認知負荷。読む人が言い換えを解読することになる。
- 主語と対象を省かない。「種別が `TEMPORARY` のとき」のように、何の種別かを推測させない。
- 頻度や程度の形容（「毎日」「すぐ」）は、根拠が無ければ書かない。
- 同じものは、どのファイルでも同じ名前で書く。揺れを見つけたら、正本の名前に全体を一度に直す。
  - なぜ：認知負荷。名前が違うと、別のものに見える。
- 連番の ID（`CO-04`・`GW-13` など）を作らない。ほかの決まりは、名前と節へのリンクで指す。
  - なぜ：メンテコスト。追加や削除のたびに付け直しと欠番が生まれる。

## 図

- 図の中には説明文を書かない。ノードとエッジのラベルは、名前（短い名詞）だけにする。
  - 説明・理由・条件は、図の下の本文に箇条書きで書く。
  - なぜ：認知負荷とメンテコストを下げるため。図の中の文は読みにくく、本文と二重になりやすいから。

## 仕様の中身

- 本文には、いつも最新の、決まったことだけを書く。変わったら本文を書き換える。
  - 書かない：追記のログ、以前の案からの経緯、改訂履歴、Front Matter の版や日付、commit ハッシュ。
  - 書かない：「未実装」「対応中」「暫定」「調整中」「今後対応」「（下書き）」のような状態。
  - 書かない：未確定のこと。決められないなら issue を切る。
  - なぜ：認知負荷。経緯や状態が混ざると、今の仕様がどれかわからなくなる。経緯はコミットと PR に残る。
- 対応しないことは書く。仕様の境界がわかる。
- 今の仕様の理由は書く。値（タイムアウトの秒数など）や、必須かどうかには根拠を添える。
- その仕様に関係しないことを書かない。読み手に関係しない要求も載せない。
- 実装やほかの仕様と照らして、確かめたことだけを書く。食い違ったら、どちらが正しいか決めて片方を直す。

## チェックリスト

書き終えたら、変えたファイルについて確かめる。

- [ ] ほかのページの内容を書き写していない。参照はリンクになっている。
- [ ] 共通の仕様のページに、使う側の API や画面の名前が出てこない。
- [ ] 経緯・状態の語が残っていない（`grep -nE '追記|未実装|対応中|暫定|調整中|今後対応|下書き'`）。
- [ ] 連番の ID が残っていない（`grep -nE '\b[A-Z]{1,4}-[0-9]{2}\b'`）。規格の名前（`ERC-20` など）は除く。
- [ ] 不自然な語が残っていない（`grep -nE '[をのる]口'` などで、API の意味の「口」が無い）。
- [ ] 1 行に 2 つ以上のことを詰めていない。
- [ ] 同じものを、どのファイルでも同じ名前で書いている。
- [ ] リンク切れが無い。

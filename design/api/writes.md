# 書き込みの決まり

書き込みの API を実装するときと、クライアントが書き込みの応答を扱うときに読む。
全体に共通する決まりは、[API](README.md) に書く。

## 書いた直後の読み

- 木は、[worker](../backend/worker.md) がスナップショットにしてから、読む側に出る。
- git に関わる書き込み（repository の作成、apply request の作成、`approve` による反映）の API は、書いたあとに worker を起こし、読む側に出るまで待ってから応答する。
  - 待つ時間の上限は、設定にする（[設定と秘密情報](../adapters/README.md)）。
  - 上限を過ぎたら、成功として応答し、`Logiforge-Pending-Revision` ヘッダーに、待っていたリビジョンを入れる。
  - クライアントは、少し待ってから、そのリビジョンを指定して読み直す。スナップショットがまだなければ、`snapshot_pending` が返る。
- 利用者がブランチに push した新しい版は、worker が次に巡回したときに、読む側に出る（[版](../backend/apply-request.md)）。
- GitForge だけに書く API（レビュー、close、人への依頼の起票と回答）は、待たない。GitForge から直接読むので、すぐに見える。
- worker が止まっていると、apply request の作成は `unavailable` を返す。少し待ってから送り直す。

## 同じ要求の繰り返し

- apply request の作成と、人への依頼の起票には、`Idempotency-Key` ヘッダーを付けられる。
  - なぜ：通信が切れて送り直しても、apply request や人への依頼が二重にできないようにするため。
- キーがあれば、バックエンドは、repository の名前・主体・キーから、識別子を決定的に作る。
  - 作り方：3 つを改行でつないだ文字列の SHA-256 の、先頭の 130 ビットを、Crockford の base32（大文字）の 26 文字にする。
  - キーがなければ、識別子は ULID にする。
- 同じ識別子のものがすでにあれば、新しく作らずに、それを返す。
  - 要求の中身は比べない。
  - なぜ：操作の中で作る仮説とストーリーの識別子は、要求ごとに乱数で決まり、最初の要求と比べられないから。
- クライアントは、中身の違う要求ごとに、新しいキーを作る。
- バックエンドが書く順は、[apply request の作成と更新](../backend/apply-request.md) に書く。
- キーと応答は、どこにも置かない。
  - なぜ：識別子だけで送り直しを見分けられ、再起動しても、別のプロセスに届いても効くから。
- repository の作成と、人への依頼への回答は、キーを使わない。
  - repository の作成：名前で一意である。送り直しは、[repository の用意](../backend/README.md) の判定で済む。
  - 回答：1 回だけである。送り直しは、回答がすでにあり、本文と回答した利用者が同じなら、成功とする（[人への依頼の回答](../files/artifacts.md)）。

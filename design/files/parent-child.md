# 親子関係の持ち方

親子関係を、パスで表すか、ファイル内の参照で表すかを決めた理由を確かめるときに読む。

## パスで表す

親子関係は、パスで表す。
子のディレクトリを、親のディレクトリの中に置く。

- なぜ：部分木が、そのままディレクトリになるから。
  - `git log <commit>.. -- <部分木のパス>` で、部分木の変化を調べられる。
  - 部分木の変化を git だけで調べられることは、引用元の変化と、反映の判定の両方で使える（[反映の手順](../backend/merge.md)）。
- なぜ：交互に並ぶことを、ディレクトリの形で確かめられるから。
- なぜ：親を指す参照が壊れること（親のないノード）が、起こらないから。

パスで表すことの短所は、次のように扱う。

- ノードを別の親へ移すと、パスが変わる。
  - ノードを移すことは、起こらない。
  - ストーリーの子仮説の集合は変えない（[ストーリー](../../docs/tree/README.md)）。
  - 作り直しは、新しい兄弟ストーリーで行う（[inactive 化](../../docs/tree/inactive.md)）。
- 木が深いと、パスが長くなる。
  - 識別子を短くすることと、深さの上限で抑える（[識別子](layout.md#識別子)、下の「深さの上限」）。

## ファイル内の参照で表さない

ファイル内の参照で表す案は、ノードを種類ごとに 1 つのディレクトリに並べ、各ファイルに親の識別子を書く。
この案は採らない。

- なぜ：木の形を見るには、すべてのファイルを読む必要があるから。
- なぜ：部分木の変化を調べるには、バックエンドがスナップショットツリーを組み立ててから比べる必要があるから。
- なぜ：親の識別子が壊れていないかを、別に確かめる必要があるから。
- この案の長所（パスが短く深さによらず一定、ノードを移してもパスが変わらない）は、上の扱いで要らない。

## 深さの上限

- 根から数えて、仮説は 24 段までにする。
  - なぜ：git のホスティングでよく使われる推奨の上限（例：ディレクトリの深さ 50）に収めるため。
  - 仮説 1 段で、仮説とストーリーの 2 つのディレクトリを使う。`tree/` を含めると、24 段で 49 になる。
- バックエンドは、25 段目の仮説を作る `story.create` を拒む（[差分の検査](../backend/checks.md)）。
- 24 段を超えて分解したいときは、その仮説を根とする別の repository を作る。
  - なぜ：配置を途中で平らに切り替える仕組みを持つより、単純だから。
- この上限なら、`tree/` から始まるパスの長さは、640 文字までに収まる。
  - 識別子は 12 文字（[識別子](layout.md#識別子)）で、区切りの `/` を含めて、ディレクトリ 1 つに 13 文字を使う。
  - 1 段の仮説とストーリーで、26 文字を使う。
  - いちばん長いのは、24 段目の仮説の検証結果のファイルである。`tree/`（5 文字）、仮説 24 個（312 文字）、ストーリー 23 個（299 文字）、`verdicts/v-<10 文字>.md`（24 文字）で、640 文字になる。
  - ディレクトリの repository では、これにディレクトリのパスが加わる（[ディレクトリ方式](../directory/README.md)）。
- Windows でクローンするときは、git の `core.longpaths` を有効にする必要がある。

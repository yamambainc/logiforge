# 親子関係の持ち方

親子関係を、パスで表すか、ファイル内の参照で表すかを決めた理由を確かめるときに読む。

## 比べた 2 つの案

パスで表す案：子のディレクトリを、親のディレクトリの中に置く。

- 長所
  - 部分木が、そのままディレクトリになる。
  - `git log <commit>.. -- <部分木のパス>` で、部分木の変化を調べられる。
  - 交互に並ぶことを、ディレクトリの形で確かめられる。
  - 親を指す参照が壊れること（親のないノード）が、起こらない。
- 短所
  - 木が深いと、パスが長くなる。
  - ノードを別の親へ移すと、パスが変わる。

ファイル内の参照で表す案：ノードを種類ごとに 1 つのディレクトリに並べ、各ファイルに親の識別子を書く。

- 長所
  - パスが短く、深さによらず一定である。
  - ノードを移しても、パスは変わらない。
- 短所
  - 木の形を見るには、すべてのファイルを読む必要がある。
  - 部分木の変化を調べるには、バックエンドが木を組み立ててから比べる必要がある。
  - 親の識別子が壊れていないかを、別に確かめる必要がある。

## 決めたこと

パスで表す案を採る。

- なぜ：パスで表す案の短所のうち、「ノードを移す」は起こらないから。
  - ストーリーの子仮説の集合は変えない（[ストーリー](../../docs/tree/README.md)）。
  - 作り直しは、新しい兄弟ストーリーで行う（[inactive 化](../../docs/tree/inactive.md)）。
- なぜ：もう 1 つの短所「パスが長くなる」は、識別子を短くすることと、深さの上限で抑えられるから（[識別子](layout.md)）。
- なぜ：部分木の変化を git だけで調べられることが、引用元の変化と、反映の判定の両方で使えるから（[反映の手順](../backend/merge.md)）。

## 深さの上限

- 根から数えて、仮説は 24 段までにする。
  - なぜ：git のホスティングでよく使われる推奨の上限（例：GitHub の、ディレクトリの深さ 50）に収めるため。
  - 仮説 1 段で、仮説とストーリーの 2 つのディレクトリを使う。`tree/` を含めると、24 段で 49 になる。
- バックエンドは、25 段目の仮説を作る `story.create` を拒む（[差分の検査](../backend/checks.md)）。
- 24 段を超えて分解したいときは、その仮説を根とする別の repository を作る。
  - なぜ：配置を途中で平らに切り替える仕組みを持つより、単純だから。
- この上限なら、パスの長さは 330 文字ほどに収まる。
- Windows でクローンするときは、git の `core.longpaths` を有効にする必要がある。
  - 1 段の仮説とストーリーで、26 文字（`h-` と `s-` の識別子と区切り）を使う。

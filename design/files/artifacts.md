# artifact の置き方

artifact の中身を、git リポジトリのどこに置き、どう受け取るかを確かめるときに読む。
artifact の種類と大きさの上限は、[artifact](../../docs/tree/verdict.md) が正本である。

## 種類と置き場所

| 種類 | 置き場所 |
|---|---|
| `file` | git リポジトリの `artifacts/sha256/<先頭 2 文字>/<残りの 62 文字>` |
| `link` | 中身を置かない。検証結果に URL だけを書く |

- 上限を超える `file` は、バックエンドが受け付けない（[差分の検査](../backend/checks.md)）。
- 上限は、どの repository でも同じにする。
  - なぜ：同じファイルが、repository によって受け付けられたり拒まれたりしないようにするため。

## 反映の前のファイル

- `file` の中身は、apply request の操作（`verdict.submit`）に含めて送る。
- バックエンドは、その中身を、版のリビジョンの `artifacts/sha256/` に入れる。
  - なぜ：アップロードの置き場所を別に持たず、版と同じ git のリビジョンで扱えるから。
- reviewer は、版のリビジョンを指定して、反映の前のファイルを読む。

## 人への依頼の回答

- 利用者が回答すると、バックエンドは、回答と添付を 1 つのリビジョンにまとめる。
  - 親は、そのときの `main` である。
  - 回答の本文は、回答のファイルとして `artifacts/sha256/` に入れる。
  - 添付の小さなファイルも、`artifacts/sha256/` に入れる。大きな添付は、`link` にする。
  - リビジョンは、[木の読み書き](../backend/ports/tree-read-write.md) の「リビジョンを作る」で作り、署名を付ける（[記録の形式](revisions.md)）。
- 回答のリビジョンの正本は、人への依頼の識別子から求める名前である（[名前を付けたリビジョン](../adapters/git.md)）。
- [やりとり](../backend/ports/interaction.md) には、回答の本文と、回答した利用者だけを記録する。
- なぜ：GitHub の API では issue のコメントにファイルを添付できず、独自プロバイダにファイルの置き場所を足すと仕組みが増えるため。版と同じ仕組みで済ませる。
- opener が `verdict.submit` で回答のファイルを引用すると、バックエンドは、回答のリビジョンから回答のファイルと添付を、版の差分に加える。
  - 加える前に、回答のリビジョンの署名を確かめる。

回答のファイルの front matter は、次のとおり。

| 項目 | 内容 |
|---|---|
| `human_request_id` | 人への依頼の識別子 |
| `answered_by` | 回答した利用者 |
| `answered_at` | 回答した日時 |
| `attachments` | 添付の一覧。各項目は、下の「検証結果からの参照」と同じ形 |

## 検証結果からの参照

検証結果の `artifacts` の各項目は、次のものを持つ。

| 項目 | 内容 |
|---|---|
| `kind` | `file` か `link` |
| `name` | 表示する名前（例：`run.py`） |
| `sha256` | 中身のハッシュ。`file` では必ず書く。`link` では任意 |
| `uri` | `link` のときの URL |
| `media_type` | 中身の形式 |

- `link` の `sha256` を照合するのは、リンクの先を取り出した利用者やエージェントである。
  - バックエンドは、リンクの先を取りに行かない。
  - なぜ：大きなデータを取り寄せることになり、サーバから外の URL へ要求を出すことにもなるため。

## 変えないこと

- `artifacts/sha256/` のファイルは、ファイル名が中身のハッシュなので、中身を変えると名前と合わなくなる。
- バックエンドは、ファイル名と中身のハッシュが一致するかを確かめる（[差分の検査](../backend/checks.md)）。

# artifact の置き方

artifact の中身を、git リポジトリのどこに置き、どう受け取るかを確かめるときに読む。
artifact の種類と大きさの上限は、[artifact](../../docs/tree/verdict.md) が正本である。

## 種類と置き場所

| 種類 | 置き場所 |
|---|---|
| `file` | git リポジトリの `artifacts/sha256/<先頭 2 文字>/<残りの 62 文字>` |
| `link` | 中身を置かない。検証結果に URL だけを書く |

- 上限を超える `file` は、バックエンドが受け付けない（[差分の検査](../backend/checks.md)）。
- 上限は、どの repository でも同じにする。
  - なぜ：同じファイルが、repository によって受け付けられたり拒まれたりしないようにするため。

## 反映の前のファイル

- `file` は、ただのファイルとして、利用者がブランチのコミットに入れる。
  - CLI のひな形が、ファイルを `artifacts/sha256/` の正しい名前に置く（[CLI](../cli/README.md)）。
  - なぜ：アップロードの API と置き場所を別に持たず、版と同じ git のコミットで扱えるから。
- 大きさの上限は、CLI の `check` と、バックエンドの [差分の検査](../backend/checks.md) の両方で確かめる。
- reviewer は、版のリビジョンを指定して、反映の前のファイルを読む。

## 人への依頼の回答

- 回答の本文と添付は、git に置かない。プロバイダのやりとりの側に置く（[やりとり](../backend/ports/interaction.md)）。
  - 独自フォージ：独自フォージのデータベースとファイルの置き場（[テーブル](../forge/tables.md)）
  - GitHub：issue のコメントに本文を書く。GitHub の API ではコメントにファイルを添付できないので、添付はリンクだけにする。利用者が、ファイルを外に置いてリンクを書く（[GitHub アダプタ](../adapters/github.md)）
    - なぜ：バックエンドがデータを保持せず、置き場に書くのを worker だけにするため。
  - なぜ：回答は、利用者が WebUI から行い、git を使わないから。サーバの側が git に書くのを、pull request の操作と repository の用意だけにするため。
- 独自フォージの構成の添付のファイルは、API の `getAnswerAttachment` で読む（[openapi.yaml](../api/openapi.yaml)）。
- opener が検証結果で回答を引用するときは、`link` の artifact にする。
  - URL は、その添付を読む API の URL である。`sha256` も書く。
  - 回答の本文を引用するときも、人への依頼を読む API の URL の `link` にする。

## 検証結果からの参照

検証結果の `artifacts` の各項目は、次のものを持つ。

| 項目 | 内容 |
|---|---|
| `kind` | `file` か `link` |
| `name` | 表示する名前（例：`run.py`） |
| `sha256` | 中身のハッシュ。`file` では必ず書く。`link` では任意 |
| `uri` | `link` のときの URL |
| `media_type` | 中身の形式 |

- `link` の `sha256` を照合するのは、リンクの先を取り出した利用者やエージェントである。
  - バックエンドは、リンクの先を取りに行かない。
  - なぜ：大きなデータを取り寄せることになり、サーバから外の URL へ要求を出すことにもなるため。

## 変えないこと

- `artifacts/sha256/` のファイルは、ファイル名が中身のハッシュなので、中身を変えると名前と合わなくなる。
- バックエンドは、ファイル名と中身のハッシュが一致するかを確かめる（[差分の検査](../backend/checks.md)）。

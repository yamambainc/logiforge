# キャッシュ

バックエンドと worker が、GitForge の一覧の API だけでは足りない情報を、どこに持ち、いつ書き換え、いつ捨てるかを確かめるときに読む。
一覧をどの API で読むかは [一覧の読み](list-reads.md) に書く。

## キャッシュに置くもの

| 何か | 何に使うか | それで省ける GitForge の呼び出し | どこに置くか | いつ書き換わるか（誰が書くか） | いつ捨ててよいか | 失ったときにどうなるか |
|---|---|---|---|---|---|---|
| 記録の控え（`log`）。形を変える | 記録とレビューを読む（バックエンドの一覧と 1 件の読み、worker の反映かの判定） | repository のコメントの一覧の全ページ、PR ごとのコメントの一覧 | 置き場の `keep/records/<識別子>/log` | 記録を読む間隔ごとと、新しい `main` のコミットがある見回り（worker） | 捨てない（下の「記録の控えを捨てない理由」） | GitForge から消された記録を数えられない。バックエンドはコメントを全部読み、遅くなる |
| `latest`。今のまま（使い道を足す） | 設定の repository の一覧の `prepared`。木の読み | repository ごとの `main` の ref と contents の読み | 置き場（[latest](snapshot/main.md#latest)） | `main` を取り込むたび（worker） | いつでも | worker が git から作り直すまで、repository が見えず、`prepared` が `false` に見える |
| 権限のキャッシュ。今のまま（使い道を足す） | 認可。repository の一覧で、読めるかを決める | repository ごとの `GET /repos/{owner}/{repo}` | バックエンドのメモリ（[権限のキャッシュ](../settings/users.md#権限のキャッシュ)） | 60 秒ごとに問い合わせ直す（バックエンド） | 60 秒たったら | 次の要求で問い合わせ直す |
| GitForge の repository の識別子。新しく足す | 記録を控えに足すときの、控えのキーと署名の確かめ | 記録を読むたびの `GET /repos/{owner}/{repo}` | worker のメモリ | 10 分ごとに問い合わせ直す（worker） | 10 分たったら | 次に記録を読むときに問い合わせ直す |

- 記録の控えは、今の番号ごとのキーを、repository ごとに 1 つのオブジェクトにまとめ、読む位置も入れる（[記録の控え](verify/records.md)）。
- バックエンドが新しく持つものはない。[状態を持たない](README.md#状態を持たない) は変えない。
  - バックエンドは、GitForge の repository の識別子を、pull request の一覧から取るか、要求の中でだけ覚える（[一覧の読み](list-reads.md#どの一覧の-api-で読むか)）。
  - なぜ持たないか：識別子は記録の署名に使う。プロセスに持つと、同じ名前で repository を作り直したあと、古い識別子で署名した記録が残り、あとから直せないから。
- 設定の DB には、キャッシュを置かない。
  - なぜ：設定の DB は、利用者が WebUI から変える設定の正本で、GitForge の写しを持つ場所ではないから（[設定の DB](../settings/database.md)）。

## 記録の控えを捨てない理由

- 記録の控えは、GitForge から消された記録を持つ。消された記録を数えるのは、控えだけである。
  - なぜ数えるか：repository に書く権限を持つ人が、レビューの記録を消して、反映の条件を変えられないようにするため（[記録の控え](verify/records.md)）。
- GitForge にはもうないので、控えは GitForge からも git からも作り直せない。そのため、置き場の `keep/` に置き、捨てない（[スナップショットの置き場](ports/snapshot-store.md)）。
- 表のほかの 3 つは、失っても、GitForge か git から作り直せる。

## 記録の控えの読み方

- 一覧の読みと 1 件の読みでは、記録とレビューを、記録の控えと、控えの読む位置より後のコメント（`issues/comments?since=`）を合わせて作る。
  - バックエンドも、worker と同じく、読む位置の 1 秒前から読む。同じ id のコメントは 1 つにし、控えにあるものは控えの中身を使う（`MergeComments`）。
  - 控えの読む位置より前の記録は、すべて控えにある。署名の合わないレビューの記録も、「無効」の印つきで控えにある。そのため、合わせたものは、repository のコメントの一覧を全部読んだときと同じ記録と、同じ鎖の切れを持つ。
  - 読む位置より後のコメントは、記録を読む間隔のあいだに書かれたものだけなので、ふつうは 1 ページである。
- 控えは、読む位置と記録を 1 つのオブジェクトに持ち、worker が 1 回の書き込みで置き換える。
  - なぜ：読む位置と記録を別に書くと、その間に読んだバックエンドが、記録を読み落とすから。
- 控えのオブジェクトがなければ、バックエンドは、`since` を付けずに、repository のコメントを全部読む。遅いだけで、正しい。
- worker が止まっているあいだは、読む位置より後のコメントが増え、ページ送りが増える。記録は読み落とさない。
- 控えが記録 1 万件（10 MB ほど）を超えたら、要求ごとに読む量を見直す。

## worker の識別子を使う範囲

- worker は、記録を控えに足すときだけ、識別子をメモリに持つ。
  - なぜ持つか：記録を読むたびに問い合わせると、REST の回数が倍になり、repository が 30 個で installation の上限に近づくから（[費用と規模の見積もり](../estimates/README.md#github-アダプタ)）。
  - worker は記録を読むだけで、署名しない。識別子が古くても、記録を書き込む側を壊さない。
- 反映かの判定と、用意のコミットの判定は、この識別子を使わない。要求の中でだけ識別子を覚える（[反映かの判定](verify/README.md)）。
  - なぜ：判定は、署名を確かめて「壊れた」を長く記録するので、古い識別子で誤って決めると、あとから直せないから。
- 同じ名前で repository を作り直したあとの 10 分は、新しい repository の記録の署名が合わず、控えに足されない。
  - 新しい repository のレビューのコメントは、古い識別子の控えに「無効」として入る。キーが違うので、新しい repository の判定には効かない。
  - 10 分たつと、新しい識別子の控えを、はじめから作る。

## 複数のプロセス

- バックエンドは、プロセスの間で共有するキャッシュを持たない。何台並べても、互いに影響しない。
- 置き場のもの（記録の控え、`latest`）は、どのプロセスも同じものを読む。控えのオブジェクトは 1 回の書き込みで置き換わるので、読む側は、古いものか新しいものの、どちらか一方を読む。

# worker の内部 API

バックエンドが worker を呼ぶ API を、実装するときに読む。
この API は、バックエンドの中の worker のクライアントが、直接呼ぶ。クライアントには公開しない。

- worker は、ポートにしない。
  - なぜ：worker は、どの構成でも同じもので、差し替える先がないから。前に、サーバの状態をポートにしなかったのと、同じ理由である。
  - テストのために、バックエンドの中で Go の interface にするのは構わない。

## 操作

| 操作 | 受け取るもの | 返すもの |
|---|---|---|
| 木を作る | repository の名前、`main` のコミットの SHA | なし |
| 起こす | repository の名前 | なし（すぐ返す） |
| ヘルスチェック（`GET /healthz`） | なし | `200`（[ヘルスチェック](../deploy.md#ヘルスチェック)） |

- 「木を作る」は、`main` のコミットの木がなければ作る（[木を作るコミット](snapshot.md#木を作るコミット)）。あれば、すぐ返す。
  - バックエンドが、API で過去のリビジョンを指定され、その木がないときに使う。
  - そのコミットの記録がなければ、見つからないとして返す。バックエンドは `snapshot_pending` にする。
  - 上限（既定 60 秒、設定）まで待つ。過ぎたら、作るのを裏で続けたまま、503 と `Logiforge-Snapshot-Pending: true` を返す。
- 「起こす」は、その repository の巡回を、すぐに始めさせる。バックエンドは、GitForge に書いたあと（apply request の作成を含む）に呼ぶ。
  - 届かなくても、worker は間隔ごとに巡回するので、追いつく。
- apply request の作成のためにブランチを読む操作は、ない。バックエンドが、作業用の git の複製から読む（[作成](apply-request.md#作成)）。
- worker は、git にも GitForge にも書かない。この API にも、書く操作はない。

## 認証

- バックエンドと worker は、同じ秘密の鍵を設定に持つ（[設定と秘密情報](../adapters/README.md)）。
- バックエンドは、要求に、その鍵を Bearer トークンとして付ける。worker は、鍵が合わない要求を拒む。
  - ヘルスチェックだけは、鍵を求めない。中身を返さず、`200` だけを返すからである。
- worker の内部 API は、バックエンドからだけ届くネットワークに置く。

## 失敗したとき

- 「木を作る」に応答がなければ、バックエンドは同じ要求を 1 度送り直す。それでもだめなら、`unavailable` を返す。
- 「木を作る」が上限までに終わらなければ、worker は 503 と `Logiforge-Snapshot-Pending: true` を返す。
  - バックエンドは、送り直さずに、`snapshot_pending` を返す。作るのは、worker が裏で続ける。
- 「起こす」の失敗は、無視する。

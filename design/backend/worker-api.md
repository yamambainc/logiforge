# worker の内部 API

バックエンドが worker を呼ぶ API を、実装するときに読む。
この API は、バックエンドの [スナップショットの置き場](ports/snapshot-store.md) のポートの、アダプタが使う。クライアントには公開しない。

## 操作

| 操作 | 受け取るもの | 返すもの |
|---|---|---|
| ブランチを読む | repository の名前、ブランチの名前 | ブランチの先頭のコミット、base、そのスナップショットのキー |
| 起こす | repository の名前 | なし（すぐ返す） |
| ヘルスチェック（`GET /healthz`） | なし | `200`（[ヘルスチェック](../deploy.md#ヘルスチェック)） |

- 「ブランチを読む」は、ブランチを fetch し、先頭のコミットと `main` の分かれた点を base として求め、base からの差分のスナップショットを作る。
  - 先に、`main` のスナップショットを進める。なぜ：base の `main` のスナップショットがないと、バックエンドが差分を検査できないから。
  - apply request を作るときに、バックエンドが、巡回を待たずに検査するために使う（[作成](apply-request.md)）。
  - 何度呼んでも、同じ結果になる。スナップショットは、コミットの SHA ごとに 1 つだからである。
- 「起こす」は、その repository の巡回を、すぐに始めさせる。バックエンドは、GitForge に書いたあとに呼ぶ。
  - 届かなくても、worker は間隔ごとに巡回するので、追いつく。
- worker は、git にも GitForge にも書かない。この API にも、書く操作はない。

## 認証

- バックエンドと worker は、同じ秘密の鍵を設定に持つ（[設定と秘密情報](../adapters/README.md)）。
- バックエンドは、要求に、その鍵を Bearer トークンとして付ける。worker は、鍵が合わない要求を拒む。
  - ヘルスチェックだけは、鍵を求めない。中身を返さず、`200` だけを返すからである。
- worker の内部 API は、バックエンドからだけ届くネットワークに置く。

## 失敗したとき

- 「ブランチを読む」に応答がなければ、バックエンドは同じ要求を 1 度送り直す。それでもだめなら、`unavailable` を返す。
- 「ブランチを読む」の中の `main` の取り込みが、上限までに終わらなければ、worker は 503 と `Logiforge-Snapshot-Pending: true` を返す（[初めての取り込みの時間](worker.md)）。
  - バックエンドは、送り直さずに、`snapshot_pending` を返す。取り込みは、worker が裏で続ける。
- 「起こす」の失敗は、無視する。

# 記録の控え

worker が、GitForge の記録のコメントをどう読み、置き場に追記して覚えるかを確かめるときに読む。
控えを判定にどう使うかは [反映かの判定](README.md) に書く。

## 控えに足す

- worker は、見回りのたびに、repository の記録のコメントを読み、署名の合うものを、置き場の `keep/records/<GitForge の repository の識別子>/log` に足す（[スナップショットの置き場](../ports/snapshot-store.md)）。
- `log` は、控えの記録と、次に読む位置を、1 つのオブジェクトに持つ。worker は、足した記録と進めた位置を、1 回の書き込みで置き換える。
  - なぜ：記録と位置を別に書くと、その間に読んだバックエンドが、記録を読み落とすから（[キャッシュ](../caches.md#記録の控えの読み方)）。
- `log` がないときは、`since` を付けずに、repository のコメントを全部読んで作る。
  - 以前の、番号ごとのキー（`keep/records/<識別子>/<番号>`）があれば、その記録も取り込む。番号ごとのキーは消さない。
  - なぜ消さないか：控えは GitForge から作り直せず、前の版の worker に戻したときにも読めるようにするため。
  - `log` を作り終えるまで、バックエンドは、番号ごとのキーを読まない。そのあいだは、GitForge から消された記録を数えない。これは受け入れる危険である。
  - 前の版の worker に戻すと、そのあいだの記録は番号ごとのキーにだけ入る。そのあと今の版に戻すと、`log` はもうあるので、番号ごとのキーは取り込まない。そのあいだに GitForge から消された記録は、控えから落ちる。これも受け入れる危険である。
  - なぜ受け入れるか：起きるのは、版を上げた直後か、版を戻して上げ直したときだけで、そのあいだに記録が消されたときだけだから。
- 識別子は、記録の署名に使うもの（Forgejo の id、GitHub の node_id）である。
  - なぜ：`owner/name` は、名前の変更や owner の移動で変わり、そのとき控えが古いキーに取り残されるから。
- なぜ repository ごとに 1 つのキーか：バックエンドが一覧を返すとき、apply request ごとに置き場を読まずに済むから（[キャッシュ](../caches.md#記録の控えの読み方)）。
  - 大きさは、記録 1 つで 1 KB ほどなので、記録 1,500 個で 1.5 MB ほどである。
- `Logiforge-Record: review` を含むのに署名の合わないコメントも、「無効」の印をつけて控えに足す。中身は、コメントの id、番号、本文である。
  - レビューを読むとき、無効の印のある記録は、数えないレビューの記録として扱う。そのため、鎖が切れたとみなす（[記録](../../adapters/records.md#レビューの書き方)）。
  - なぜ：控えに足す前に書き換えられたレビューを、控えと `since` だけで読んでも見落とさないため。一覧、1 件の読み、worker の判定が、同じ鎖の切れを見る。
- 控えは、記録の識別子ごとに、最初に見た中身を持つ。同じ識別子で中身が違うものを見たら、最初のものを残し、警告する。
- 控えからは、消さない。GitForge から記録が消えても、控えには残る。
- 控えは、記録といっしょに、GitForge のコメントの id を持つ。レビューの順番（「最後の決めるレビュー」）は、この id の順で決める。
  - なぜ：控えにだけある記録と、今の GitForge の記録を合わせたときに、順番を 1 つに決めるため。コメントの id は、GitForge の中で作った順に増える。
- 控えは、git から作り直せないので、`keep/` に置く（[スナップショットの置き場](../ports/snapshot-store.md)）。

## 読む位置

- 読むのは、repository のコメントの一覧のうち、前に読んだあとに作られたか変わったもの（`since`）だけである。
- `issues/comments?since=` は、編集されたコメントを、`updated_at` とともに返す。
- `updated_at` は秒の単位なので、worker は、前に読んだ位置の 1 秒前から読む。同じものを読み直しても、控えには足さない。
- 位置は、前の位置より戻さない。
- ページの送り方は、GitForge の並び順で違う（下の「ページ送り」）。どちらも、1 回の見回りで、位置より後のコメントを全部読む。
  - なぜ全部読むか：1 回に 1 ページ分しか位置を進めないと、控えを初めて作るときや、worker が長く止まったあとに、残りのページを見回りごとに読み直し、REST の回数がページの数の 2 乗で増えるから。
- 記録を読む間隔の既定は、GitHub では 30 秒、Forgejo では見回りの間隔と同じである。
  - なぜ GitHub は 30 秒か：REST の上限のため（[GitHub アダプタ](../../adapters/github.md) の「見回りの間隔」）。設定で変えなくても、上限に当たらないようにする。
  - 新しい `main` のコミットがある見回りでは、間隔を待たずに読む（[反映かの判定](README.md#gitforge-の-api)）。

## ページ送り

ページを送るあいだにコメントが編集されたり消されたりしても、コメントを読み落とさないための決まりである。
読み落としたコメントは、位置がそれより後に進むと二度と読まれず、控えから落ちるので、これを防ぐ。
バックエンドが `since` で読むときも、同じ送り方をする（[キャッシュ](../caches.md#記録の控えの読み方)）。

- GitHub：`issues/comments?since=&sort=updated&direction=asc` は、`updated_at` の順に返す。
  - 次のページは、`page` を進めずに、`since` を、読んだページの最後の `updated_at` にして読む。同じ id は 1 つにする。
  - ページの全部が同じ `updated_at` のときだけ、`since` を変えずに `page` を進める。なぜ：`since` は秒の単位なので、同じ秒のものが 1 ページを超えると、`since` だけでは先へ進めないから。
  - なぜ `page` で送らないか：送るあいだに編集されたコメントは後ろへ動き、消されたコメントの分は前へ詰まるので、境目のコメントを読まないことがあるから。`since` で送れば、編集されたものは後で読み、詰まっても飛ばさない。
  - 位置は、読んだコメントの最大の `updated_at` まで進める。
- Forgejo：`issues/comments?since=` は、`sort` を受け付けず、コメントを作った順（id の順）に返す。`since` と `before` は、`updated_at` で絞り、どちらも境目の秒を含む。
  - `since` で絞った集まりには、読むあいだに編集された古いコメントが、その id の位置に入ってくる。後ろのコメントがずれるので、ページの境目のものを読まないことがある。消されたコメントの分は、前へ詰まる。
  - そのため、上の端 `before` を決め、そのあとのすべての要求に、同じ `since` と `before` を付ける。`before` は、1 ページ目の応答の `Date` の 1 秒前である。
    - なぜ：上の端を止めると、集まりは減るだけになるから。読むあいだに編集されたものは、`updated_at` が `before` より後になって出ていく。消されたものも出ていく。新しく入るものはない。
    - なぜ 1 秒前か：`before` は境目の秒を含むので、`Date` と同じ秒に編集されたものが入ってこないようにするため。
  - 1 ページ目は `since` だけで読み、応答の `Date` と、`X-Total-Count` からページの数を知る。1 ページで終われば、位置は `before` まで進める。
  - 1 ページで終わらなければ、`since` と `before` を付けて、最後のページから 1 ページ目まで、逆の順に読み直す。
    - なぜ逆の順か：集まりが減るだけなら、コメントは、まだ読んでいない前のページへ動くだけなので、飛ばさないから。
    - なぜ 1 ページ目も読み直すか：最初の 1 ページ目には `before` が付いていないうえ、そのあとに減ると、2 ページ目の先頭が 1 ページ目へ動くから。
  - 位置は、`before` まで進める。出ていったコメントは、`updated_at` が `before` より後なので、次の見回りで読む。

## 判定に使う

- 判定は、控えの記録と、控えの読む位置より後に GitForge から読んだ記録の、署名の合うものを合わせて行う。
- 無効の印のある記録は、数えず、鎖の切れとして扱う（上の「控えに足す」）。

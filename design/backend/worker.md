# worker

git を読んで、スナップショットを作り続ける worker を、動かすときと作るときに読む。
スナップショットの中身は [スナップショット](snapshot.md)、バックエンドから呼ばれる API は [worker の内部 API](worker-api.md) に書く。

## 形

- worker は、バックエンドとは別のコンテナで動く、常駐のプロセスである。バックエンドのコンテナと、同じタスクに並べる（[動かし方](../deploy.md)）。
  - 中身は、バックエンドと同じ Go のコードである（例：`logiforge worker`）。
  - なぜ：ファイルの形とスナップショットの作り方を、バックエンドと 1 つのコードで持つため。
- worker は、git を読むだけである。git にも GitForge にも書かない。書く鍵も持たない。
- サーバの側で git のファイルを解析して木にするのは、worker だけである。
  - CLI の `check` も同じ解析のコードを使うが、それは利用者の手元である（[ひな形と check](../cli/local.md)）。
- worker は、永続するストレージを 1 つ持ち、その中に repository ごとの clone を持ち続ける。
  - clone は正本ではない。失っても、clone し直せば元に戻る。
- 置き場に書くのは、worker だけである。バックエンドは、置き場を読むだけである。
- worker は、ルールを判定しない。木を解析し、記録し、不変条件が破れていれば警告するだけである。
- 動かす場所は問わない。特定の CI やクラウドの製品に頼らない。

## 依存するもの

| もの | 使い方 |
|---|---|
| repository ごとの clone | 永続するストレージに置く。fetch して読む |
| ファイルの解析のコード | git のファイルからスナップショットを作る。CLI の `check` と同じコード |
| 置き場への書き込み | スナップショット、artifact、`latest`、ブランチの履歴、`repositories` を書く。バックエンドのポート（読むだけ）とは別のインターフェース |
| リモートの git リポジトリ | GitForge。読むだけの資格情報を使う |

## 起きるきっかけ

- バックエンドは、GitForge に書いたあとに、worker を起こす（[worker の内部 API](worker-api.md)）。
- 起こされなくても、設定した間隔ごとに巡回する。
  - 利用者の push を版として見つけるのは、この巡回である。間隔は、版が読む側に出るまでの遅れになる。1 分ほどにする。
  - `git ls-remote` は、GitForge の API の上限には数えないことが多い。ただし、git の操作にも、乱用を防ぐ制限がある。

## すること

repository ごとに、1 つずつ順に処理する。repository が違えば、並行してよい。

1. `git ls-remote` で、`main` とブランチの先頭を読み、変わっていれば `git fetch` する。
2. 消えたブランチの履歴に、消えたことを記録する。
   - 消えたブランチは、置き場のブランチの名前の一覧のうち、履歴の最後が「消えた」でなく、`ls-remote` の結果にないものである。
   - なぜ置き場と比べるか：手元の ref と比べると、fetch で ref が消えたあと、記録する前に止まったときに、記録が失われるから。
   - main より先に行う。なぜ：main の処理で誤りが出ても、巻き込まれないようにするため。
3. スナップショットのないコミットについて、スナップショットを作る。
   - 解析の前に、blob の大きさと種類を確かめる。上限を超える blob と、普通のファイルでないもの（シンボリックリンク、実行の属性、submodule）は、読まずに誤りとして記録する（[差分の検査](checks.md)）。
   - ブランチの先頭は、`main` と分かれた点からの差分のスナップショットにする。
4. 先頭が変わったブランチについて、[ブランチの履歴](snapshot.md) に足す。
   - 初めて見たブランチは、履歴より先に、ブランチの名前の一覧に足す。
5. [latest](snapshot.md) の規則で、`latest` を書く。
6. `main` の新しいコミットについて、次のことを確かめ、破れていれば警告として記録する。
   - 反映の記録（`Logiforge-Apply-Request:`）がある（[記録の形式](../files/revisions.md)）。
   - 木の不変条件が成り立つ（[差分の検査](checks.md) の「head の木で確かめること」）。
   - 反映した apply request の対象ノードが、その base のあとに、別の反映で変わっていない（[対象ノードの変化](merge.md)）。
     - base は、反映した版のコミット（反映のコミットの `Logiforge-Version:`）と、反映の直前の `main` の分かれた点である。worker は、自分の clone の `git merge-base` で求める。
     - 比べる範囲は、ノードの変更の一覧のうち、base の番号より大きく、その反映のコミットの番号より小さいものである。反映のコミット自身は除く。
     - 対象ノードは、反映のコミットで変わったファイルから求める。検証結果と背景情報はその仮説、新しいストーリーは親の仮説、inactive 化はそのストーリーである。
     - 版のコミットは、ブランチが消えても、`refs/pull/*/head` を fetch して読む。版のコミットか base が見つからなければ、確かめられなかったことを警告する（`overlap_unchecked`）。
   - 警告の種類は、`no_apply_request`、新しく破れた不変条件の規則、`overlap`、`overlap_unchecked`、`main_rewritten`（[latest](snapshot.md)）である。
   - なぜ：`main` の保護が外れたときと、検査と merge のすき間（[反映の手順](merge.md)）で起きたことに気づくため。
7. `repositories` を書き直す。

- 何度動かしても、結果は同じになる。

## worker を 1 つだけ動かす

- worker は、1 つだけ動かす。worker のコンテナを含むタスクのレプリカを 1 にする（[動かし方](../deploy.md)）。
  - なぜ：`latest` とブランチの履歴を書く規則が、書き手が 1 つであることを前提にするから。
- worker は、起動のときに、clone のディレクトリの排他のロック（ファイルのロック）を取る。取れなければ、起動しない。
- 誤って 2 つ動いても、木もブランチの履歴も壊れない。
  - `latest`、ブランチの履歴、ブランチの名前の一覧は、条件付きで書く（読んだときの値のときだけ書く）（[スナップショットの置き場](ports/snapshot-store.md)）。

## 初めての取り込みの時間

- 初めての取り込みは、`main` のコミットの数の 2 乗に近い時間がかかる。
  - なぜ：コミットごとに、木の全体を組み立て直し、値と不変条件を計算し、スナップショットの木の全体を書くから。木が大きくなるほど、1 コミットあたりの時間も伸びる。
  - 測った値は、[費用と規模の見積もり](../estimates.md) に書く。
- 「ブランチを読む」は、base のスナップショットのために、先に `main` を取り込む。その取り込みを待つ時間には、上限（既定 60 秒、設定）を設ける。
  - 上限を過ぎたら、取り込みを裏で続けたまま、`snapshot_pending` を返す（[worker の内部 API](worker-api.md)）。少し待って送り直せば、続きから終わる。
- 制約：大きな repository を移すときは、`ar create` の前に、巡回で取り込みを終えておく。
- 2 乗の時間を減らすこと（`history` を分けて置く、変わった部分木だけを計算する、など）は、後の課題とする。

## worker が止まっているとき

- 読むと、止まる前の木と版が返る。レビューと人への依頼は、GitForge から読むので、新しいものが返る。
- apply request の作成は、ブランチを読めないので、`unavailable` で止まる。
- 反映は、今の `main` のスナップショットがないと検査できないので、`snapshot_pending` で止まる（[反映の手順](merge.md)）。
- 木は壊れない。worker が戻れば、止まっていた間のコミットに追いつく。

## 鍵

| 鍵 | 使い方 |
|---|---|
| git を読む資格情報 | 読むだけの権限のもの（[設定と秘密情報](../adapters/README.md)） |
| 置き場に書く鍵 | スナップショットと `latest` を書く |
| 内部 API の鍵 | バックエンドからの要求を確かめる（[worker の内部 API](worker-api.md)） |

- git と GitForge に書く鍵は、持たない。

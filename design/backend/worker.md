# worker

git を読み書きし、スナップショットを作り続ける worker を、動かすときと作るときに読む。
スナップショットの中身は [スナップショット](snapshot.md)、バックエンドから呼ばれる API は [worker の内部 API](worker-api.md) に書く。

## 形

- worker は、1 つのコンテナで動く、常駐のプロセスである。
  - 中身は、バックエンドと同じ Go のコードである（例：`logiforge worker`）。
  - なぜ：ファイルの形とスナップショットの作り方を、バックエンドと 1 つのコードで持つため。
- git に触れるのは、worker だけである。読む、解析する、書く（commit と push）のどれも、worker が行う。
  - バックエンドは、git を読まず、clone も作らない。git に書くときは、worker の内部 API を呼ぶ。
  - なぜ：clone を持つものを 1 つにし、バックエンドがデータを保持しないようにするため。
- worker は、永続するストレージを 1 つ持ち、その中に repository ごとの clone を持ち続ける。
  - clone は正本ではない。失っても、clone し直せば元に戻る。
- 置き場に書くのは、worker だけである。バックエンドは、置き場を読むだけである。
- worker は、ルールを判定しない。バックエンドが検査を終えた変化を書き、木を解析し、記録するだけである。
- 動かす場所は問わない。特定の CI やクラウドの製品に頼らない。

## 依存するもの

| もの | 使い方 |
|---|---|
| repository ごとの clone | 永続するストレージに置く。fetch、commit、push に使う |
| ファイルの解析のコード | `tree/` のファイルからスナップショットを作る。バックエンドと同じコードの、解析の側 |
| 置き場への書き込み | スナップショット、artifact、`latest`、`repositories` を書く。worker の中のインターフェースで、バックエンドのポート（読むだけ）とは別にする |
| リモートの git リポジトリ | GitHub か独自フォージ。読む資格情報と書く資格情報を使う |

## 処理の順

- worker は、repository ごとに、要求を 1 つずつ順に処理する。repository が違えば、並行してよい。
  - なぜ：同じ repository の書き込みどうしが、clone の中でぶつからないようにするため。
- 処理は、次のどちらかで始まる。
  - バックエンドからの要求（[worker の内部 API](worker-api.md)）。ブランチを読む、版を書く、書く
    - ブランチを読むときは、利用者が push したブランチを fetch し、`main` と分かれた点からの差分のスナップショットを作る。解析は、ここでも worker だけが行う。
  - 巡回：設定した間隔ごとに、`git ls-remote` で `main` と `refs/logiforge/` の下の ref を読み、`latest` と違えば追いつく

## 書き込みの要求

1. `git ls-remote` で、リモートが `latest` と同じかを確かめる。違えば、先に下の「追いつく」を行う。
2. バックエンドから受け取った変化で、コミットを作る。署名と trailer を付ける（[記録の形式](../files/revisions.md)）。
3. 受け取った ref の期待する値で、1 回の atomic な push をする（[ref を書く](../adapters/git.md)）。
4. push が通れば、新しいコミットのスナップショットを作り、`latest` を書いてから応答する。
   - そのため、応答を受け取ったバックエンドとクライアントは、すぐに読んでも、書いたものが見える。

## 追いつく

1. `git fetch` で、`main` と `refs/logiforge/` の下の ref を取る。
2. スナップショットのないコミットについて、スナップショットを作る。署名のないコミットは、`history` でわかる。
3. [latest](snapshot.md) の規則で、`latest` を書く。force push なら、その記録を残す。
4. `repositories` を書き直す。

- 巡回は、owner や admin の直接の push（[main への書き込みを守る](../adapters/github-main.md)）に追いつくためにある。
  - バックエンドからの書き込みは、要求の中でスナップショットまで作るので、巡回を待たない。
- 巡回の間隔は、5 分ほどでよい。
  - `git ls-remote` は GitHub の API の上限には数えないが、git の操作にも、乱用を防ぐ制限がある。
  - 直接の push を、5 分ほど遅れて読む側に出してよいなら、それで足りる。

## worker を 1 つだけ動かす

- worker は、1 つだけ動かす。コンテナのレプリカを 1 にする。
  - なぜ：repository ごとに順に処理することと、`latest` を書く規則が、書き手が 1 つであることを前提にするから。
- 誤って 2 つ動いても、git の CAS と `latest` の規則で、木は壊れない（[latest](snapshot.md)）。

## worker が止まっているとき

- 読むことはできる。止まる前の木が返る。
- git に書く要求（版の作成と更新、close、反映、回答、repository の作成）は、できない。バックエンドは `unavailable` を返す。
  - プロバイダだけに書く要求（レビュー、人への依頼の起票）は、できる。ただし `approve` で反映するときは、git に書くので止まる。
- 木は壊れない。worker が戻れば、止まっていた間の直接の push に追いつき、書き込みも再開する。

## 鍵

| 鍵 | 使い方 |
|---|---|
| git を読み書きする資格情報 | GitHub を使う構成では GitHub App の秘密鍵、独自フォージを使う構成では `writer` のトークン |
| 署名の鍵 | 署名を付け、確かめる（[記録の形式](../files/revisions.md)） |
| 置き場に書く鍵 | スナップショットと `latest` を書く |
| 内部 API の鍵 | バックエンドからの要求を確かめる（[worker の内部 API](worker-api.md)） |

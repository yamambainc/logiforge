# worker

反映によらずに `main` が変わったときに、スナップショットを作り、突き合わせをする worker を確かめるときに読む。

## 形

- worker は、バックエンドと同じ Go のコードの CLI である（例：`logiforge snapshot build`）。
  - なぜ：スナップショットの作り方と署名の確かめ方を、バックエンドと 1 つのコードで持つため。
- worker は、ルールを判定しない。木を解析し、記録するだけである。

## すること

1. 今の `main` までの、スナップショットのないコミットについて、[スナップショット](snapshot.md) を作る。
2. [latest](snapshot.md) の規則で、`latest` を今の `main` にする。force push なら、その記録を `latest` に残す。
3. 突き合わせをする。
   - 署名が正しく、`Logiforge-Apply-Request:` を持つコミットがあり、やりとりで open のままの apply request があれば、反映されたことを記録し直す。
   - 署名のないコミットは、スナップショットの `unsigned` に入る。API は、これを警告として返す。

- 何度動かしても、結果は同じになる。

## 動かす場所

| 構成 | 動かす場所 |
|---|---|
| GitHub を使う構成 | `main` への push で走る GitHub Actions |
| 独自フォージを使う構成 | 動かさない |

- GitHub を使う構成では、owner と admin が `main` に直接 push できるので、worker が要る（[main への書き込みを守る](../adapters/github.md)）。
  - バックエンドの App の push でも走る。その場合は、スナップショットがすでにあるので、すぐ終わる。
  - なぜ App の push でも走らせるか：push のあと、バックエンドがスナップショットを置く前や、反映されたことを記録する前に止まったときに、worker がそれを直すから。
- 独自フォージを使う構成では、`main` に push できるのはバックエンドだけなので、反映によらない変更が起きない（[主体](../forge/README.md)）。
  - バックエンドが止まって、スナップショットや反映の記録が欠けたときは、次の書き込みでバックエンドが直す（下の「バックエンドが直すもの」）。

## バックエンドが直すもの

worker を動かさない構成でも欠けたままにしないため、バックエンドは書き込みのたびに次のことを行う。

- 今の `main` のスナップショットがなければ、先に作り、`latest` を進める。
- 反映するときに、その apply request の `Logiforge-Apply-Request:` を持つコミットが、base から今の `main` までにあれば、反映されたことを記録して終わる（[反映の手順](merge.md)）。

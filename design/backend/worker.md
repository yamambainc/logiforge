# worker

スナップショットを作り続ける worker を、動かすときと作るときに読む。
中身は、[スナップショット](snapshot.md) に書く。

## 形

- worker は、1 つのコンテナで動く、常駐のプロセスである。
  - 中身は、バックエンドと同じ Go のコードである（例：`logiforge worker`）。
  - なぜ：スナップショットの作り方と署名の確かめ方を、バックエンドと 1 つのコードで持つため。
- worker は、永続するストレージを 1 つ持ち、その中に repository ごとの clone を持ち続ける。
  - なぜ：変わったコミットだけを fetch すれば足り、毎回 clone し直さずに済むから。
  - clone は正本ではない。失っても、clone し直せば元に戻る。
- 動かす場所は問わない。特定の CI やクラウドの製品に頼らない。
- worker は、ルールを判定しない。木を解析し、記録するだけである。
- 置き場に書くのは、worker だけである。バックエンドは、置き場を読むだけである。
  - なぜ：書き手を 1 つにすると、`latest` を書く規則が単純になるから。

## 起きるきっかけ

- 設定した間隔ごとに、repository ごとに 1 回、巡回する（下の「すること」）。
  - `git ls-remote` で `main` と `refs/logiforge/` の下の ref を読み、変わっていれば `git fetch` する。git のプロトコルなので、GitHub の API のレート制限に当たらない。
- バックエンドは、git に書いたあとに、worker を起こす通知を送る（内部の HTTP）。
  - 通知には、repository の名前だけを入れる。worker は、通知の中身を信じず、`git ls-remote` で確かめる。
  - 通知が届かなくても、次の間隔で追いつく。
- 間隔と、通知を受ける HTTP のエンドポイントは、設定にする（[設定と秘密情報](../adapters/README.md)）。

## すること

1. `main` と `refs/logiforge/` の下の、スナップショットのないコミットについて、[スナップショット](snapshot.md) を作る。
   - 署名のないコミットは、`history` でわかる。API は、これを警告として返す。
2. [ref の一覧](snapshot.md) を書き直す。
3. [latest](snapshot.md) の規則で、`latest` を今の `main` にする。force push なら、その記録を `latest` に残す。
4. `repositories` を書き直す。

- 何度動かしても、結果は同じになる。
- worker が誤って 2 つ動いても、`latest` は、[スナップショットの置き場](ports/snapshot-store.md) の条件付きの書き込みと [latest](snapshot.md) の規則で、古い SHA に戻らない。

## 構成

| 構成 | 置き場 | 動かし方 |
|---|---|---|
| GitHub を使う構成 | 静的ファイルストレージ | バックエンドとは別のコンテナ |
| 独自フォージを使う構成 | 手元のディレクトリ | バックエンドと同じプロセスで動かしてもよい |

- どちらの構成でも、同じ worker を使う。そのため、バックエンドにスナップショットを書くコードはない。

## worker が止まっているとき

- 読むと、止まる前の木と版が返る。レビューと人への依頼は、プロバイダから読むので、新しいものが返る。
- 書く側は、待つ時間の上限まで待たされる（[書いた直後の読み](../api/writes.md)）。
  - 版の作成、レビュー、回答は、上限を過ぎても書ける。まだ読めない印が付く。
  - 反映は、今の `main` のスナップショットがないと検査できないので、`snapshot_pending` で失敗する（[反映の手順](merge.md)）。
- どちらでも、木は壊れない。
- worker が戻れば、止まっていた間のコミットのスナップショットを作り、追いつく。
- worker の clone は正本ではないので、消えても clone し直せる。

## 鍵

worker が持つのは、次のものだけである。

- git を読む資格情報（GitHub を使う構成では、GitHub App の秘密鍵。独自フォージを使う構成では、`writer` のトークン）
- 置き場に書く鍵
- 署名の鍵（署名を確かめるため。[記録の形式](../files/revisions.md)）

- バックエンドと worker を運用する人は同じなので、署名の鍵を両方に置く。

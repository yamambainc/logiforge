# worker

反映によらずに `main` が変わったときに、スナップショットを作り、突き合わせをする worker を確かめるときに読む。

## 形

- worker は、バックエンドとは別の、独立したプロセスである。
  - 中身は、バックエンドと同じ Go のコードの CLI である（例：`logiforge snapshot watch`）。
  - なぜ：スナップショットの作り方と署名の確かめ方を、バックエンドと 1 つのコードで持つため。
- どこで動かすかは問わない。常駐のプロセスでも、定期実行のジョブでもよい。
  - なぜ：特定の CI やクラウドの製品に頼らずに動かせるようにするため。
- worker は、ルールを判定しない。木を解析し、記録するだけである。

## 起きるきっかけ

- worker は、設定した間隔ごとに、repository ごとに `git ls-remote` で今の `main` を読む。
  - なぜ：git のプロトコルなので、GitHub の API のレート制限に当たらないから。clone も要らない。
  - 間隔は、設定にする（[設定と秘密情報](../adapters/README.md)）。
- 今の `main` が `latest` と同じなら、何もしない。違うときだけ、下の「すること」を行う。
  - そのため、バックエンドの push で `latest` がすでに進んでいれば、worker は何もしない。
- 外からの通知（webhook など）で、間隔を待たずに起こしてもよい。これは任意である。
  - 起こされたら、すぐに 1 回確かめる。通知の中身は信じず、`git ls-remote` で確かめる。

## すること

1. 今の `main` までの、スナップショットのないコミットについて、[スナップショット](snapshot.md) を作る。
2. [latest](snapshot.md) の規則で、`latest` を今の `main` にする。force push なら、その記録を `latest` に残す。
3. 署名のないコミットは、スナップショットの `unsigned` に入る。API は、これを警告として返す。

- 何度動かしても、結果は同じになる。2 つの worker が同時に動いても、`latest` の条件付きの書き込みで、結果は同じになる。

## 動かす構成

| 構成 | worker |
|---|---|
| GitHub を使う構成 | 動かす |
| 独自フォージを使う構成 | 動かさない |

- worker が要るのは、反映によらずに `main` が変わるときだけである。
  - GitHub を使う構成では、owner と admin が `main` に直接 push できるので、worker が要る（[前提](../adapters/github.md)）。
  - 独自フォージを使う構成では、`main` に push できるのはバックエンドだけなので、反映によらない変更が起きない（[主体](../forge/README.md)）。
- バックエンドの push のあとに止まったときの回復は、どちらの構成でも、下の「バックエンドが直すもの」で行う。
  - なぜ：回復のしかたを 1 つにし、worker の役目を、反映によらない変更だけに絞るため。

## バックエンドが直すもの

バックエンドは、書き込みのたびに次のことを行う。どちらの構成でも同じである。

- 今の `main` のスナップショットがなければ、先に作り、`latest` を進める。
  - バックエンドが push したあと、スナップショットを置く前に止まったときを直す。
- 反映するときに、その apply request の `Logiforge-Apply-Request:` を持つコミットが、base から今の `main` までにあれば、反映されたことを記録して終わる（[反映の手順](merge.md)）。
  - バックエンドが push したあと、反映されたことを記録する前に止まったときを直す。
- open の apply request を読むときにも、同じことを確かめる。見つかれば、反映されたことを記録し直す。
  - なぜ：だれも反映し直さないと、反映済みの apply request が、レビュー待ちの作業に残り続けるから。
  - 確かめるのは、コミットの記録の親をたどることだけなので、読む経路で git を使わない（[スナップショット](snapshot.md)）。

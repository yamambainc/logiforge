# worker

git を読んで、スナップショットを作り続ける worker を、動かすときと作るときに読む。
スナップショットの中身は [スナップショット](snapshot.md) に書く。

## 形

- worker は、バックエンドとは別のコンテナで動く、常駐のプロセスである。バックエンドのコンテナと、同じタスクに並べる（[動かし方](../deploy.md)）。
  - 中身は、バックエンドと同じ Go のコードである（例：`logiforge worker`）。
  - なぜ：ファイルの形とスナップショットの作り方を、バックエンドと 1 つのコードで持つため。
- worker は、どのポートでも待ち受けない。API を持たない。
  - バックエンドは、worker を呼ばない。置き場を読むだけである。
  - なぜ：worker の仕事は、git の今の姿を、見回りで置き場に写すことだけだから。すべての `main` のコミットにスナップショットツリーを作るので、バックエンドが worker に作らせるものがない（[すべてのコミットに作る](snapshot.md#すべてのコミットに作る)）。見回りの間隔が短いので、起こす要求も要らない。
- worker は、git を読むだけである。git にも GitForge にも書かない。書く鍵も持たない。
- スナップショットを作って置き場に書くのは、worker だけである。
  - バックエンドも、apply request の作成のときだけ、作業用の git の複製から git を読んで検査する（[作業用の git の複製](apply-request.md#作業用の-git-の複製)）。スナップショットは作らない。
  - worker、バックエンド、CLI の `check` は、同じ解析のコードを使う（[ひな形と check](../cli/local.md)）。
- worker は、永続するストレージを 1 つ持ち、その中に repository ごとの clone を持ち続ける。
  - clone は正本ではない。失っても、clone し直せば元に戻る。
- worker は、ルールを判定しない。木を解析し、記録し、不変条件が破れていれば警告するだけである。
- 動かす場所は問わない。特定の CI やクラウドの製品に頼らない。

## 依存するもの

| もの | 使い方 |
|---|---|
| repository ごとの clone | 永続するストレージに置く。fetch して読む |
| ファイルの解析のコード | git のファイルからスナップショットを作る。CLI の `check` と同じコード |
| 置き場への書き込み | スナップショット、artifact、`main` の並びの索引、`latest`、ブランチの履歴、`repositories` を書く。バックエンドのポート（読むだけ）とは別のインターフェース |
| リモートの git リポジトリ | GitForge。読むだけの資格情報を使う |

## 見回り

- worker は、見回りの間隔（既定 1 秒、設定）ごとに、すべての repository の見回りを始める。
  - なぜ 1 秒か：利用者が push した先頭のコミットと、バックエンドが GitForge に書いたもの（反映、repository の用意）が、読む側に出るまでの遅れを短くするため。バックエンドは worker を起こさず、`latest` が進むのを待つ（[書いた直後の読み](../api/writes.md)）。
  - 見回りの `git ls-remote` は、repository ごとに 1 秒に 1 回である。GitForge の API の上限には数えないことが多い。ただし、git の操作にも、乱用を防ぐ制限がある（[費用と規模の見積もり](../estimates.md)）。
- repository の一覧は、見回りごとには読まない。別に、一覧を読み直す間隔（既定 10 秒、設定）ごとに GitForge の API で読み直し、見回りは、最後に読めた一覧を使う。
  - なぜ：一覧を読むのは GitForge の API で、見回りの間隔ごとに読むと、API の上限に数えられるから。
  - なぜ 10 秒か：repository の作成の API が、書いたものが読む側に出るまで待つ上限（既定 10 秒）のうちに、多くは応答できるようにするため。GitForge が止まっても、見回りとハートビートが止まらないようにするためでもある。
  - 一覧を読むときは、時間の上限（30 秒）を付ける。読めなければ、前に読めた一覧を使い続ける。
  - そのため、新しい repository が見回りに入るのは、作ってから最大で一覧を読み直す間隔のあとである。repository の作成の API は、それより短い待つ上限を過ぎると、`Logiforge-Pending-Commit` で応答する（[書いた直後の読み](../api/writes.md)）。
- 前の回の処理が終わっていない repository は、その回は飛ばす。
  - なぜ：1 つの repository の長い取り込みが、ほかの repository の見回りを遅らせないようにするため。
- 1 つの repository の処理は、下の「すること」である。repository が違えば、並行して動かす。

## すること

repository ごとに、次の順に処理する。

1. `git ls-remote` で、`main` とブランチの先頭を読み、前に読んだものと変わっていれば `git fetch` する。
2. 消えたブランチの履歴に、消えたことを記録する。
   - 消えたブランチは、置き場のブランチの名前の一覧のうち、履歴の最後が「消えた」でなく、`ls-remote` の結果にないものである。
   - なぜ置き場と比べるか：手元の ref と比べると、fetch で ref が消えたあと、記録する前に止まったときに、記録が失われるから。
   - `main` より先に行う。なぜ：`main` の処理で誤りが出ても、巻き込まれないようにするため。
3. `main` の、`latest` より新しいコミットを、古い順に 1 つずつ取り込む（[すべてのコミットに作る](snapshot.md#すべてのコミットに作る)）。1 つのコミットについて、次の順に行う。
   1. 1 つ前のコミットのスナップショットツリーのファイルに、`git diff-tree` で求めた差分を重ねる。加わったか変わったファイルだけを読む。
   2. 重ねたファイルの一覧から、スナップショットツリーを作る。不変条件を確かめ、1 つ前の `broken` と比べて、新しく破れたものを求める。
   3. 下の「確かめること」を確かめ、コミットの記録を作る。
   4. コミットの記録、`main` の並びの索引、スナップショットツリーの順に置く（[latest](snapshot.md#latest)）。
   5. `latest` を、そのコミットに進める。
   - 解析の前に、blob の大きさと種類を確かめる。上限を超える blob と、普通のファイルでないもの（シンボリックリンク、実行の属性、submodule）は、読まずに誤りとして記録する（[差分の検査](checks.md)）。
4. 先頭が変わったブランチについて、base からの差分のスナップショットを作り、[ブランチの履歴](snapshot.md#ブランチの履歴) に足す。
   - 初めて見たブランチは、履歴より先に、ブランチの名前の一覧に足す。
5. `repositories` を書き直す。

- 1 つの repository では、`main` を取り込み終えてから、ブランチを取り込む。
  - そのため、`main` に溜まったコミットを取り込むあいだ（初めての取り込みなど）、その repository の新しい先頭のコミットのスナップショットは出ない。そのあいだ、そのコミットへのレビューは `snapshot_pending` になる（[書いた直後の読み](../api/writes.md)）。これは受け入れる。
  - なぜ：ブランチのスナップショットの検査とレビューの材料は、`main` のスナップショットツリーの上で作るから。`main` が追いつく前に作っても、すぐ古くなる。
- git の操作（`ls-remote`、`fetch`、`diff-tree` など）には、1 回ごとに時間の上限（既定 10 分、設定）を付ける。超えたら、誤りとして、その repository のその回の処理を終える。次の見回りで、やり直す。
  - なぜ：GitForge やネットワークが固まっても、その repository の処理が止まったままにならないようにするため。
  - なぜ 10 分か：大きな repository の初めての clone（数百 MB の fetch）でも、終わるようにするため。
- 処理の誤り（上限を超えたことを含む）は、repository の名前をつけて、worker のログに書く。運用では、このログを監視して、その repository の `latest` が進まないことに気づく。
- 何度動かしても、結果は同じになる。
- 途中で止まっても、次の見回りで、`latest` の次のコミットから続ける。
  - 置き場に、`latest` より新しいコミットの記録やスナップショットツリーが置いてあれば、同じ中身で置き直す。

## 確かめること

`main` の新しいコミットについて、次のことを確かめ、破れていれば警告としてコミットの記録に書く。

- 反映の記録（`Logiforge-Apply-Request:`）がある（[記録の形式](../files/revisions.md)）。
- 木の不変条件が成り立つ（[差分の検査](checks.md) の「head の木で確かめること」）。1 つ前のコミットのスナップショットツリーの `broken` になかったものを、新しく破れたものとする。
- 反映した apply request の対象ノードが、その base のあとに、別の反映で変わっていない（[対象ノードの変化](merge.md#対象ノードの変化)）。
  - base は、反映した先頭のコミット（反映のコミットの `Logiforge-Version:`）と、反映の直前の `main` の分かれた点である。worker は、自分の clone の `git merge-base` で求める。
  - 1 つ前のコミットのスナップショットツリーで、対象ノードの `last_changed` の番号が、base の番号より大きければ、重なりとする（[ノードを変えたコミット](snapshot.md#ノードを変えたコミット)）。
  - 対象ノードは、反映のコミットで変わったファイルから求める。検証結果と背景情報はその仮説、新しいストーリーは親の仮説、inactive 化はそのストーリーである。
  - 反映した先頭のコミットは、ブランチが消えても、`refs/pull/*/head` を fetch して読む。そのコミットか base が見つからなければ、確かめられなかったことを警告する（`overlap_unchecked`）。
- 警告の種類は、`no_apply_request`、新しく破れた不変条件の規則、`overlap`、`overlap_unchecked`、`main_rewritten`（[latest](snapshot.md#latest)）である。
- なぜ：`main` の保護が外れたときと、検査と merge のすき間（[反映の手順](merge.md)）で起きたことに気づくため。

## 取り込みの時間

- 1 コミットあたりの時間は、木の大きさに比例する。1 つ前のスナップショットツリーのファイルに差分を重ねても、スナップショットツリーを組み立て、値を計算し、圧縮して置くのは、木の全体だからである。
  - ノード 1,000 個で約 0.18 秒、4,000 個で約 0.46 秒である（[費用と規模の見積もり](../estimates.md)）。
- 初めての取り込みの時間は、`main` のコミットの数と、1 コミットあたりの時間の積である。
- apply request の作成は、worker の取り込みを待たない。バックエンドが、作業用の git の複製から読んで検査する（[作成](apply-request.md#作成)）。
- 大きな repository を移すときは、`ar create` の前に、見回りで取り込みを終えておく。

## worker を 1 つだけ動かす

- worker は、1 つだけ動かす。worker のコンテナを含むタスクのレプリカを 1 にする（[動かし方](../deploy.md)）。
  - なぜ：`latest`、`main` の並びの索引、ブランチの履歴を書く規則が、書き手が 1 つであることを前提にするから。
- worker は、起動のときに、clone のディレクトリの排他のロック（ファイルのロック）を取る。取れなければ、起動しない。
- 誤って 2 つ動いても、スナップショットツリーもブランチの履歴も壊れない。
  - `latest`、ブランチの履歴、ブランチの名前の一覧は、条件付きで書く（読んだときの値のときだけ書く）（[スナップショットの置き場](ports/snapshot-store.md)）。

## ハートビート

- worker は、見回りを始めるたびに、clone のディレクトリのハートビートのファイル（`heartbeat`）に、その時刻を書く。
- 死活確認は、このファイルを見るコマンド（`logiforge worker-health`）を、コンテナの中で動かして行う（[ヘルスチェック](../deploy.md#ヘルスチェック)）。
  - コマンドは、worker と同じ環境変数（clone のディレクトリと、見回りの間隔）を読む。
  - ファイルの時刻から、見回りの間隔の 10 倍（既定 10 秒）より長くたっていれば、止まっているとみなし、0 以外で終わる。
  - なぜ 10 倍か：GC や、ディスクの一時的な遅れで、1 回の見回りが少し遅れただけでは、再起動しないようにするため。
- 見回りは、repository の処理を待たずに始まる（上の「見回り」）。そのため、1 つの repository の取り込みが長くても、ハートビートは止まらない。
  - そのかわり、1 つの repository の処理が進まないことは、ハートビートでは見つけない。git の操作の時間の上限で処理を終わらせ、ログで見つける（上の「すること」）。
- GitForge や置き場に届くかは、ハートビートでは確かめない。
  - なぜ：外のサービスが止まったときに、コンテナを再起動し続けないようにするため。

## worker が止まっているとき

- 読むと、止まる前のスナップショットツリーと、apply request の先頭のコミットが返る。レビューと人への依頼は、GitForge から読むので、新しいものが返る。
- apply request の作成はできる。ただし、先頭のコミットのスナップショットができないので、レビューは `snapshot_pending` のままになる（[書いた直後の読み](../api/writes.md)）。
- 反映は、今の `main` のスナップショットがないと検査できないので、`snapshot_pending` で止まる（[反映の手順](merge.md)）。
- スナップショットツリーは壊れない。worker が戻れば、止まっていた間のコミットに追いつく。

## 鍵

| 鍵 | 使い方 |
|---|---|
| git を読む資格情報 | 読むだけの権限のもの（[設定と秘密情報](../adapters/README.md#設定と秘密情報)） |
| 置き場に書く鍵 | スナップショットと `latest` を書く |

- git と GitForge に書く鍵は、持たない。

# 認証

バックエンドが、API の要求を送った主体を確かめるときに使うポートを確かめるときに読む。

## 操作

| 操作 | 内容 |
|---|---|
| 主体を確かめる | トークンを受け取り、主体（アカウント名）と、主体の種類（`user` か `client`）と、WebUI のサインインで得たトークンかを返す |
| repository を読めるか確かめる | 主体が、その repository を読めるかを返す |

- WebUI のサインインで得たトークンかは、そのトークンが、設定の DB にある、サインインに使うアプリのものかである（[サインイン](../../webui/auth.md#方式)）。
  - 想定用途：CLI のトークン（`gh auth login` のものなど）を持つ主体と分けて、WebUI のサインインをした人だけに許す操作を決めるため（[管理者を確かめる](../../settings/admins.md#管理者を確かめる)）。
  - GitHub を使う構成では、`user` の判定にも使う（[GitHub アダプタの認証](../../adapters/github.md#認証)）。
  - 確かめ方は、構成ごとのアダプタに書く。
- 管理者かどうかは、このポートで決めない。バックエンドが、返したアカウント名を、設定の DB の `admins` と比べる（[認可](../README.md#認可)）。
  - なぜ：管理者の正本は、GitForge ではなく、設定の DB にあるから（[設定の DB](../../settings/database.md)）。

- バックエンドは、要求ごとにこのポートを呼ぶ。結果を保持しない（[状態を持たない](../README.md#状態を持たない)）。
- どの操作を使えるかの判定（認可）は、このポートではなくバックエンドが行う（[認可](../README.md#認可)）。
- 構成ごとの実装は、[アダプタ](../../adapters/README.md) に書く。

## ポートにした理由

- 主体の正本が、構成によって違うから（[レイヤーの分け方](../../architecture.md#レイヤーの分け方)）。
- ほかのポートと同じく、起動処理が構成に合ったアダプタを差し込むだけで済むから（[起動時の組み立て](../../architecture.md)）。

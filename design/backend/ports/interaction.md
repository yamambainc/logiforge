# やりとり

バックエンドが、提案・レビュー・人への依頼を置く先として、プロバイダに何を求めるかを確かめるときに読む。
このポートを実装するのが、プロバイダ（GitHub アダプタと独自フォージのアダプタ）である（[アダプタ](../../adapters/README.md)）。

プロバイダは、ルールを判定しない。受け取ったものを置き、求められたら返すだけである。

## repository

- repository を列挙する。名前と provider_ref の組を返す。
- 名前から provider_ref を求める。
- repository の、やりとりの側を用意する。すでに済んでいれば、何もしない。
  - バックエンドは、provider_ref を渡す。
- ほかの操作は、どれも repository を指定して行う。

## 提案

- 提案（apply request）を作る。識別子と説明欄を渡す。
  - 版は渡さない。版の正本は git の ref である（[apply request の作成と更新](../apply-request.md)）。
- 説明欄を書き換える。
- 反映の失敗の理由を記録する。
- close を記録する。理由と、close したセッションを渡す。
- 反映されたことを記録する。この操作を呼ぶのは、[反映の手順](../merge.md) だけである。
- バックエンドは、読む操作を要求ごとに呼ぶ。結果を保持しない（[状態を持たない](../README.md)）。
- 提案と、そのレビューと反映の失敗を、作った順に読む。

## レビュー

- レビューを記録する。
  - 種類（`approve`、`request_changes`、`comment`）、本文、レビューした版
  - reviewer のセッションと、使ったプロンプトのリビジョン

## 人への依頼

- 人への依頼を記録する（対象ノード、種類、本文、起票したセッション）。
- 回答を記録する（本文、回答した利用者、回答のリビジョン）。すでに回答があれば、そのことがわかる形で失敗する。
- 人への依頼と回答を、作った順に読む。

## 識別子

- apply request、レビュー、人への依頼の識別子は、バックエンドが決める。
  - 形は、接頭辞（`apr_`、`rev_`、`hrq_`）と、Crockford の base32 の 26 文字である。
  - 26 文字は、ULID か、`Idempotency-Key` から決定的に作ったものである（[同じ要求の繰り返し](../../api/writes.md)）。
  - なぜ：版のリビジョンの名前に、提案を作る前から識別子を使うため。
- プロバイダは、一覧を作った順に返す。識別子の順ではない。
- プロバイダは、受け取った識別子で置き、その識別子で返す。

# プロバイダのインターフェース

バックエンドが、提案・レビュー・人への依頼・イベントを置く先として、プロバイダに何を求めるかを確かめるときに読む。
このインターフェースはバックエンドが持ち、プロバイダはこれを実装する。

- 依存の向きは、プロバイダからバックエンドのインターフェースへの 1 方向である。
  - なぜ：プロバイダを差し替えても、バックエンドを変えずに済むようにするため（[レイヤー構成](../architecture.md)）。
- プロバイダは、ルールを判定しない。受け取ったものを置き、イベントをバックエンドに伝えるだけである。

インターフェースは、次の 5 つだけである。

## repository

- repository を用意する。
  - 用意の仕方は、実装ごとに違う。
  - なぜ：repository をバックエンドの設定として扱うと、API から repository を用意できなくなるから。
- repository を一覧する。
- ほかの 4 つの操作は、どれも repository を指定して行う。

## 提案と版

- 提案（apply request）を、ブランチとして作る。
- ブランチにコミットを足して、新しい版を作る。
- 提案と版を読む。
  - 版ごとの head のコミットを返す。
  - base は持たない。バックエンドが `git merge-base <head のコミット> main` で求める。
- 反映の失敗の理由を記録する。
- 提案を close する。理由と、close したセッションを記録する。
- バックエンドの検査が通った提案を、`main` に反映する。
  - この操作を呼ぶのは、[反映の手順](merge.md) だけである。

## レビュー

- レビューを記録する。
  - 種類（`approve`、`request_changes`、`comment`）、本文、レビューした版
  - reviewer のセッションと、使ったプロンプトのリビジョン
- 提案ごとのレビューを、記録した順に読む。

## 人への依頼

- 人への依頼を記録する（対象ノード、種類、本文、起票したセッション）。
- 回答を 1 回だけ記録する（本文、添付、回答した利用者）。
- 人への依頼を読む。

## イベント

- 提案、レビュー、人への依頼が変わったら、バックエンドに知らせる。
- `main` に、反映の手順によらないコミットができたら、バックエンドに知らせる。

# 識別子の番号の取り方

バックエンドが、識別子の番号をどう取り、送り直しと番号の重なりをどう扱うかを確かめるときに読む。
識別子の形は、[識別子](README.md) に書く。

## 番号の ref

- 番号は、GitForge の git リポジトリに置いた ref で数える。repository と種類の組ごとに、ref を 1 つ置く。
  - git リポジトリ全体の repository：`refs/logiforge/ids/<種類>`
  - ディレクトリの repository：`refs/logiforge/dirs/<ディレクトリのパス>/ids/<種類>`
  - 種類は、`apr`、`rev`、`hrq` である。
- ref は、最後に取った番号のコミットを指す。
  - コミットは、空の木で、親を持たない。
  - メッセージの trailer `Logiforge-Number:` に、番号を書く。
  - なぜ親を持たないか：読むのが先頭のコミットだけで済み、履歴が伸びないから。
- 番号の ref は、設定の DB にもバックエンドのプロセスにも写さない。
  - なぜ：GitForge の git リポジトリを正本にすれば、バックエンドが状態を持たずに済むから（[状態を持たない](../README.md#状態を持たない)）。
- `refs/heads/` と `refs/tags/` の外に置く。
  - なぜ：ふつうの clone と fetch には入らず、利用者の作業に混ざらないから。
- 書き方は、[番号の ref に書く](../../adapters/git.md#番号の-ref-に書く) に書く。

## 番号を取る

1. 番号の ref と、キーの ref（下の「同じ要求の繰り返し」）を、名前を指定して読む。
2. キーの ref があれば、それが指すコミットの番号を返して終わる。
3. 番号の ref が指すコミットの番号を読む。ref がなければ、0 とする。
4. 読んだ番号に 1 を足したコミットを作り、番号の ref を、読んだときの値からそのコミットに進める。
   - ref が読んだあとに変わっていれば、GitForge が拒む（compare-and-swap）。
   - 拒まれたら、手順 1 からやり直す。
   - なぜ：ほかの要求が、あいだに番号を取ったから。
5. キーがあれば、キーの ref を作る（下の「同じ要求の繰り返し」）。

- 番号は、GitForge に記録を書く前に取る。
  - なぜ：pull request のタイトルと記録のコメントに、識別子を書くから（[記録のコメント](../../adapters/records.md#記録のコメント)）。
- 1 回に読むのは、ref を 2 つと、コミットを 1 つだけである。
  - なぜ：これまでに取った番号の数によらず、読む量が変わらないようにするため。
- やり直しは、10 回までにする。超えたら、`unavailable` を返す。
  - やり直すのは、あいだにほかの要求が番号を取ったときだけである。
  - そのため、やり直しの回数は、同時に来た要求の数を超えない。
  - 10 は、1 つの repository に同時に書く利用者とエージェントの数の見込みである。

## 番号の重なり

GitForge に書く権限のある人は、番号の ref を、戻したり消したりできる。

- 新しく取った番号の記録が、GitForge にすでにあれば、その番号を使わない。
  - GitForge の記録から、その種類の整数の識別子の最大を読み、番号の ref をそこまで進めてから、取り直す。
  - apply request と人への依頼では、[作成](../apply-request/create.md#作成) の手順 2 の読みで見つける。
  - レビューでは、レビューを書く前に読む、その apply request のレビューの一覧で見つける。
- 記録の最大を読むのは、重なりを見つけたときだけである。
  - なぜ：記録をすべて読むのは重いから。重なりは、ref が戻されたときにしか起きない。
- 送り直しの番号は、取り直さない。その番号の記録は、前の要求で作ったものだからである。
- ほかの apply request のレビューと番号が重なっても、取り直さない。
  - なぜ：レビューの識別子は、1 つの apply request の中で、鎖をたどるためにだけ使うから（[レビューの書き方](../../adapters/records.md#レビューの書き方)）。
- 番号の ref を先へ進められても、番号が飛ぶだけである。番号の欠けは、受け入れる（[形](README.md#形)）。

## 同じ要求の繰り返し

- `Idempotency-Key` があれば、キーの ref を置く。
  - git リポジトリ全体の repository：`refs/logiforge/keys/<種類>/<ハッシュ>`
  - ディレクトリの repository：`refs/logiforge/dirs/<ディレクトリのパス>/keys/<種類>/<ハッシュ>`
  - ハッシュは、repository の名前・主体・キーを改行でつないだ文字列の SHA-256 の、16 進である。
  - なぜ主体を含めるか：別の主体が同じキーを送っても、別の要求として扱うため。
- キーの ref は、番号を取ったコミットを指す。
- キーの ref は、すでにあれば作れない形で作る。
  - 作れなければ、同じキーのほかの要求が先に作っている。そのキーの ref が指す番号を返す。
  - 自分が取った番号は、使わずに欠けにする。
  - なぜ：同じキーの要求が 2 つ同時に来ても、1 つの番号にまとめるため。
- 番号を取ったあと、キーの ref を作る前に止まったら、送り直しで、もう 1 つ番号を取る。前の番号は、欠けになる。
- キーの ref は、消さない。
  - なぜ：消すと、遅れて届いた送り直しが、別の番号で二重に作るから。
  - 読むときは名前を指定するので、キーの ref が増えても、読む量は変わらない。
- キーの ref を消されると、そのキーの送り直しは、二重に作る。これは受け入れる。
  - なぜ：キーの ref を消せるのは、GitForge に書く権限のある人だけで、その人は記録のコメントも消せるから。
- キーのない要求とレビューは、キーの ref を置かない。

送り直しのほかの決まり（中身は比べない、など）は、[同じ要求の繰り返し](../../api/writes.md#同じ要求の繰り返し) に書く。

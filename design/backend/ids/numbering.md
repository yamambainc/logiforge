# 識別子の番号の取り方

バックエンドが、識別子の番号をどう取り、送り直しと番号の重なりをどう扱うかを確かめるときに読む。
識別子の形は、[識別子](README.md) に書く。

## カウンタ

- カウンタは、設定の DB に、repository と種類の組ごとに置く（[設定の DB](../../settings/database.md#表)）。
- 番号は、GitForge に何かを書く前に取る。
  - なぜ：pull request のタイトルと記録のコメントに、識別子を書くから（[記録のコメント](../../adapters/records.md#記録のコメント)）。
- バックエンドを並べるのは、同じノードの中だけである（[DB の種類](../../settings/database.md#db-の種類)）。

### 番号を取る

バックエンドは、番号を、1 つの書き込みのトランザクションで取る。

- トランザクションは、`BEGIN IMMEDIATE` で始める。
  - なぜ：読んだあとに書くロックを取りにいくと、2 つのプロセスが互いを待って、片方が失敗するから。
- トランザクションの中で、カウンタを読み、1 つ進めて書く。
  - なぜ：SQLite の書き込みのトランザクションは、同じ DB を開いたほかのプロセスと同時には走らないから。
  - そのため、バックエンドを何台並べても、同じ番号を 2 回は取らない。
- トランザクションの中では、GitForge を読まない。
  - なぜ：通信のあいだ、ほかのプロセスの書き込みが止まるから。

### カウンタを合わせる

次のときに、カウンタを GitForge の記録に合わせる。

- カウンタの行がまだないとき
- 新しく取った番号の記録が、GitForge にすでにあったとき（下の「番号の重なり」）

合わせ方は、次のとおり。

1. トランザクションの外で、GitForge の記録を読む。
   - その repository の記録のうち、その種類の、整数の識別子の最大を求める。
   - 記録がなければ、最大は 0 とする。
2. 行がなければ、次の番号を「最大＋1」にして、行を作る。
   - 同時にほかのプロセスが作っていれば、作らない（`INSERT ... ON CONFLICT DO NOTHING`）。
   - なぜ：どちらのプロセスが作っても、GitForge の記録と重ならない値になるから。
3. 行があれば、次の番号を、今の値と「最大＋1」の大きいほうにする。
   - なぜ大きいほうか：あいだにほかのプロセスが進めた番号を、戻さないため。
4. そのあと、上の「番号を取る」で取る。

なぜ合わせるか：設定の DB を作り直したり、古いバックアップから戻したりしても、GitForge にある記録と番号が重ならないようにするため。

## 番号の重なり

設定の DB を古いバックアップから戻すと、カウンタが、GitForge にある記録より後ろに戻ることがある。

- 新しく取った番号の記録が、GitForge にすでにあれば、その番号を使わない。
  - 上の「カウンタを合わせる」で合わせてから、取り直す。
  - apply request と人への依頼では、[作成](../apply-request/create.md#作成) の手順 2 の読みで見つける。
  - レビューでは、レビューを書く前に読む、その apply request のレビューの一覧で見つける。
- 送り直しで返した番号は、取り直さない（下の「同じ要求の繰り返し」）。
  - その番号の記録は、前の要求で作ったものだからである。
- ほかの apply request のレビューと番号が重なっても、取り直さない。
  - なぜ：レビューの識別子は、1 つの apply request の中で、鎖をたどるためにだけ使うから（[レビューの書き方](../../adapters/records.md#レビューの書き方)）。

## 同じ要求の繰り返し

- `Idempotency-Key` があれば、キーと番号の対応を、設定の DB に置く。
  - 対応のキーは、repository の名前・主体・キーを改行でつないだ文字列の SHA-256 である。
  - なぜ主体を含めるか：別の主体が同じキーを送っても、別の要求として扱うため。
- 番号を取るトランザクションの中で、対応を読む。
  - 対応があれば、カウンタを進めずに、その番号を返す。
    - この番号を、送り直しの番号と呼ぶ。
  - 対応がなければ、番号を取り、対応も書く。
    - この番号を、新しい番号と呼ぶ。キーのない要求で取った番号も、新しい番号である。
  - なぜ同じトランザクションか：同じキーの要求が 2 つ同時に来ても、2 つの番号を取らないようにするため。
- 番号の重なりで取り直したときは、対応も、取り直した番号に書き換える。
- 対応は、消さない。
  - なぜ：1 件の大きさは小さく、件数は apply request と人への依頼の数を超えないから。
  - 消すと、遅れて届いた送り直しが、別の番号で二重に作る。
- 設定の DB を古いバックアップから戻すと、戻した時点より後の対応はなくなる。
  - その対応のキーで送り直すと、新しい番号で二重に作る。
  - これは受け入れる。
  - なぜ：送り直しは、通信が切れた直後に送るものなので、バックアップから戻す前の要求を送り直すことは、ふつうはないから。
- キーのない要求とレビューは、対応を置かずに、番号を取る。

送り直しのほかの決まり（中身は比べない、など）は、[同じ要求の繰り返し](../../api/writes.md#同じ要求の繰り返し) に書く。

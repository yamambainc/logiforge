# apply request とレビューと人への依頼の識別子

バックエンドが、apply request、レビュー、人への依頼の識別子をどう決めるかを確かめるときに読む。
ノード（仮説、ストーリー、検証結果）の識別子は、このページの対象ではない（[ディレクトリの名前](../../files/layout.md)）。

## 読む順

1. このページ：形、26 文字の識別子、選ばなかった案
2. [番号の取り方](numbering.md)：番号の ref、番号を取る、番号の重なり、同じ要求の繰り返し

## 形

- 識別子は、接頭辞と、1 から始まる 10 進の整数である（例：`apr_42`）。
  - 接頭辞は、apply request が `apr_`、レビューが `rev_`、人への依頼が `hrq_` である。
  - 整数の先頭に、`0` を付けない。
  - なぜ：人が読み、口で伝え、書き写せる長さにするため。
- 番号は、repository ごと、種類ごとに数える。
  - 例：repository `a` と `b` には、どちらにも `apr_1` がある。
  - 例：`apr_3` と `hrq_3` は、別のものである。
  - なぜ：利用者は repository の中で識別子を使うので、repository の中で詰まった番号にするため。
- 番号には、欠けがありうる。
  - 例：番号を取ったあと、GitForge に書く前に失敗し、送り直さなかったとき。
- 番号の順は、作った順と同じとは限らない。
  - なぜ：番号は GitForge に書く前に取るので、2 つの要求が同時に来ると、先に番号を取ったほうが、あとに書き終えることがあるから。
  - なぜ：番号が重なって取り直すと、取り直した番号は、あいだにほかの要求が取った番号より後ろになるから（[番号の重なり](numbering.md#番号の重なり)）。
  - そのため、一覧は、識別子の順ではなく、作った順に返す（[ページング](../../api/paging.md)）。

## 26 文字の識別子

整数の識別子にする前に作ったものは、接頭辞と Crockford の base32 の 26 文字の識別子である。

- 26 文字の識別子は、書き換えない。そのまま読む。
  - なぜ：識別子は、署名した記録のコメント、反映のコミットの `Logiforge-Apply-Request:`、回答を引用した検証結果の URL に残るから（[記録のコメント](../../adapters/records.md#記録のコメント)、[main のコミットと記録](../../files/revisions.md)、[artifact](../../files/artifacts.md)）。
  - 書き換えると、署名と git の履歴を作り直すことになる。
- 読むときは、整数の識別子と 26 文字の識別子の両方を受け付ける。
  - 2 つは、接頭辞のあとの長さで見分けられる。
  - 整数は、64 ビットの符号付きの整数に収めるので、19 桁を超えない。
- 番号の ref は、26 文字の識別子を数えない。
  - なぜ：形が違うので、整数の識別子と重ならないから。
- 新しく作るものは、すべて整数の識別子にする。
- 26 文字の識別子も、作った順には並ばない。
  - なぜ：`Idempotency-Key` から作ったものは、キーの値で決まるから。

## 選ばなかった案

- GitForge の pull request と issue の番号を、そのまま使う案。
  - 選ばなかった理由：ディレクトリの repository では、1 つの git リポジトリの番号を、ほかの repository と、コードの pull request と分け合うから（[ディレクトリ方式](../../directory/README.md)）。
    - そのため、repository の中で詰まった番号にならない。
  - 選ばなかった理由：pull request と issue は 1 つの番号を分け合うので、apply request と人への依頼の番号が混ざるから。
  - 選ばなかった理由：レビューは記録のコメントで、GitForge に番号がないから。
- 番号ごとに ref を作る案（例：`refs/logiforge/ids/apr/42`。すでにあれば作れない）。
  - 選ばなかった理由：次の番号を決めるのに、それまでの番号の ref をすべて読むことになるから。
- GitForge の記録の最大の番号に 1 を足し、重なったら取り直す案。
  - 選ばなかった理由：同時に来た 2 つの要求が同じ番号で記録を書き、重なりは書いたあとにしか分からないから。
  - 書いたあとに番号を変えると、pull request のタイトルと、署名した記録を書き直すことになる。
- 番号を、設定の DB で数える案。
  - 選ばなかった理由：設定の DB には、設定のほかの状態を置かないから（[置くものと置かないもの](../../settings/database.md#置くものと置かないもの)）。

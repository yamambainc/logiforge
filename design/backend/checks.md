# 差分の検査

apply request の差分を、バックエンドがどう検査するかを確かめるときに読む。
バックエンドは、どの GitForge を使っても、同じ検査を行う。
ファイルの形は、[木のファイル配置](../files/README.md) に書く。

## 検査する時点

- apply request が作られたとき（ブランチの差分に対して）
- 新しい先頭のコミットを見せるとき（ブランチの差分に対して。結果は、レビューの材料と作業の一覧に出す）
- 反映する直前（最新の `main` に、先頭のコミットの差分を当てはめた木に対して）

- 検査するのは、向き先が `main` の apply request だけである（[向き先](apply-request/target.md#向き先)）。

検査は、もとの木（base）と、差分を当てはめたあとの木（head）の差分に対して行う。

- apply request の作成のときは、バックエンドが、作業用の git の複製から、ブランチの差分を読んで検査する（[作成](apply-request/create.md#作成)）。worker を待たない。
- 新しい先頭のコミットを見せるときと、反映する直前は、[スナップショット](snapshot/README.md) の上で行う。ブランチの差分は、worker がスナップショットにしたものを使う。
  - なぜ：先頭のコミットの一覧とレビューの材料は、worker のスナップショットから読むから。反映の前の検査は、今の `main` のスナップショットに重ねて行うから。
- 同じ検査のコードを、CLI の `check` も使う（[ひな形と check](../cli/local.md)）。
- 利用者は、ブランチに、どんなファイルの変化でも入れられる。そのため、下の「許すこと」以外の変化は、すべて拒む。

## 差分として許すこと

次の変化だけを許す。

- 新しい仮説とストーリーのディレクトリを、ファイルごと加える。
- 新しい検証結果のファイルを、`verdicts/` に加える。
- `inactivated.md` を、ストーリーのディレクトリに加える。
- `background.md` の末尾に、文章を加える。
  - head の内容が、base の内容で始まることを確かめる。
- `artifacts/sha256/` に、新しいファイルを加える。

## 差分として拒むこと

- `tree/` と `artifacts/sha256/` の外の、どんなファイルの変化も
  - 例：CI の設定のディレクトリや、リポジトリの直下のファイル
  - ディレクトリの repository では、`tree/` と `artifacts/sha256/` は、そのディレクトリの下のものである。
  - ディレクトリの外の変化は、規則 `outside_directory` で拒む（[ディレクトリ方式](../directory/README.md)）
- 形の読めないファイル（front matter が壊れている、決まっていない項目がある、など）
- 普通のファイル（git のモード 100644）でないもの：シンボリックリンク、実行の属性の付いたファイル、submodule
- 上限の大きさを超えるファイル。worker は、解析の前に大きさを確かめ、中身を読まない（[worker](worker/README.md)）
- すでにあるファイルの変更（`background.md` の末尾への追加を除く）
- ファイルとディレクトリの削除
- ファイルとディレクトリの名前の変更

これにより、次の 2 つが守られる。

- append-only：一度加えたファイルは、変わらず残る（[監査](../../docs/architecture/README.md)）。
- 主文を変えないこと：`hypothesis.md` と `story.md` は、加えたあと変わらない（[操作](../../docs/apply-request/README.md)）。

## head の木で確かめること

- 拒むのは、その差分が新しく破った条件だけである。base で成り立ち、head で破れたものを拒む。
  - 比べる単位は、「条件 × ノード」である。同じ条件でも、別のノードで新しく破れれば拒む。
  - 反映の時点の base は、今の `main`（[反映の手順](merge.md) の手順 3 で、先頭のコミットの差分を当てはめるもとの木）である。apply request を作る時点の base は、ブランチと `main` の分かれた点である。
  - base ですでに破れている条件は、拒まずに警告する。
  - なぜ：検査と merge のすき間や、守る設定が外れたときの直接の push で、木が一度壊れたときに、直すための apply request まで通らなくなるのを防ぐため（[検査と merge のすき間](merge.md)）。

- 新しいノード（`h-`、`s-`）と検証結果（`v-`）の識別子が、base の木と、今の `main` の木に、まだない。
  - 識別子は、クライアントが決める（[ファイルの配置](../files/layout.md)）。ぶつかったら、拒む。
- 交互に並ぶこと：`h-` の子は `s-` だけ、`s-` の子は `h-` だけである。
- 深さ：仮説が 24 段を超えない（[深さの上限](../files/parent-child.md)）。
- 根は 1 つ：`tree/` の直下に、仮説のディレクトリが 1 つだけある。
- ストーリーの子仮説は 1 つ以上：新しい `s-` には、`h-` が 1 つ以上ある。
- 文字数：主文、タイトル、概要の上限（[仮説とストーリーの木](../../docs/tree/README.md)）。
- 有効な検証結果は 1 つまで：[有効な検証結果](../files/layout.md) が、1 つの仮説に 2 つ以上ない。
- 差し替え：`supersedes` の一覧の各項目が指すのは、同じ仮説の、その時点で有効な検証結果である。
  - 一覧で、有効な検証結果を、まとめて差し替えられる。有効な検証結果が 2 つになった仮説は、この差し替えで 1 つに戻す。
- 検証結果と active な子ストーリーを同時に持たない。
- 検証結果を持つ仮説の下に、新しいストーリーを作らない。
- inactive な部分木の下に、新しいストーリーを作らない。
- inactive な部分木の中の検証結果は、inactive になる前に葉だった仮説にだけ出す。
  - inactive になる前の状態は、`inactivated.md` が加わった `main` のコミットの 1 つ前のスナップショットツリーで確かめる。
  - そのコミットの番号は、ストーリーの `inactivated_at` である。
  - 1 つ前の SHA は、`main` の並びの索引で引く（[コミットの記録から引くもの](snapshot/main.md#コミットの記録から引くもの)）。
- 部分木の引用：先頭のコミットの木に、指定した識別子の仮説かストーリーがある。
  - 同じ apply request で加えるノードも引用できる。
  - inactive な部分木のノードも引用できる（[inactive](../../docs/tree/inactive.md)）。
- artifact の引用：sha256 が、base の木の `artifacts` か、同じ apply request で加えるファイルにある。
- artifact のファイル名が、中身のハッシュと一致する。
- artifact のファイルが、上限の大きさを超えない（[artifact](../../docs/tree/verdict.md)）。
- 加えた artifact は、加えた検証結果から参照されている。
- 保存しない値（真偽値など）が、ファイルに書かれていない。

これらの不変条件の正本は、[仮説とストーリーの木](../../docs/tree/README.md) と [inactive 化](../../docs/tree/inactive.md) である。

## 値の計算

- バックエンドは、head の木から値を計算する（[真偽値の伝播](../../docs/tree/propagation.md)）。
- 計算した値は、ファイルに書かない。
- 論理レビューの材料や、着手できる作業の判定にも、同じ計算を使う。

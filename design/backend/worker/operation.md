# worker の運用

worker を 1 つだけ動かす仕組み、死活確認、worker が止まっているときの振る舞いを確かめるときに読む。
worker の形は [worker](README.md) に書く。

## worker を 1 つだけ動かす

- worker は、1 つだけ動かす。worker のコンテナを含むタスクのレプリカを 1 にする（[動かし方](../../deploy/README.md)）。
  - なぜ：`latest`、`main` の並びの索引、ブランチの履歴を書く規則が、書き手が 1 つであることを前提にするから。
- worker は、起動のときに、clone のディレクトリの排他のロック（ファイルのロック）を取る。取れなければ、起動しない。
- 誤って 2 つ動いても、スナップショットツリーもブランチの履歴も壊れない。
  - `latest`、ブランチの履歴、ブランチの名前の一覧は、条件付きで書く（読んだときの値のときだけ書く）（[スナップショットの置き場](../ports/snapshot-store.md)）。

## ハートビート

- worker は、見回りを始めるたびに、clone のディレクトリのハートビートのファイル（`heartbeat`）に、その時刻を書く。
- 死活確認は、このファイルを見るコマンド（`logiforge worker-health`）を、コンテナの中で動かして行う（[ヘルスチェック](../../deploy/README.md#ヘルスチェック)）。
  - コマンドは、worker と同じ環境変数（clone のディレクトリと、設定の DB の場所）を読み、見回りの間隔を設定の DB から読む（[環境変数](../../deploy/env.md)）。
  - ファイルの時刻から、見回りの間隔の 10 倍（既定 10 秒）より長くたっていれば、止まっているとみなし、0 以外で終わる。
  - なぜ 10 倍か：GC や、ディスクの一時的な遅れで、1 回の見回りが少し遅れただけでは、再起動しないようにするため。
- セットアップが終わるまで、worker は見回りをせずに待つ（[設定を読むとき](../../settings/README.md#設定を読むとき)）。待つあいだも、見回りの間隔の既定（1 秒）ごとにハートビートを書く。
  - なぜ：セットアップのあいだに、死活確認で再起動され続けないようにするため。
- 見回りは、repository の処理を待たずに始まる（[見回りの間隔](patrol.md#見回りの間隔)）。そのため、1 つの repository の取り込みが長くても、ハートビートは止まらない。
  - そのかわり、1 つの repository の処理が進まないことは、ハートビートでは見つけない。git の操作の時間の上限で処理を終わらせ、ログで見つける（[すること](patrol.md#すること)）。
- GitForge や置き場に届くかは、ハートビートでは確かめない。
  - なぜ：外のサービスが止まったときに、コンテナを再起動し続けないようにするため。

## worker が止まっているとき

- 読むと、止まる前のスナップショットツリーと、apply request の先頭のコミットが返る。
- レビューと人への依頼は、GitForge から読むので、新しいものが返る。
- apply request の作成はできる。ただし、先頭のコミットのスナップショットができないので、レビューは `snapshot_pending` のままになる（[書いた直後の読み](../../api/writes.md)）。
- 反映は、今の `main` のスナップショットがないと検査できないので、`snapshot_pending` で止まる（[反映の手順](../merge.md)）。
- スナップショットツリーは壊れない。worker が戻れば、止まっていた間のコミットに追いつく。

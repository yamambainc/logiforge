# 見回り

worker が、どの間隔で repository を見回り、repository ごとに何をどの順に処理するかを確かめるときに読む。
worker の形は [worker](README.md) に書く。

## 見回りの間隔

- worker は、見回りの間隔（既定 1 秒、[設定](../../settings/README.md#設定の-db-に置くもの)）ごとに、すべての repository の見回りを始める。
  - なぜ 1 秒か：利用者が push した先頭のコミットと、バックエンドが GitForge に書いたもの（反映、repository の用意）が、読む側に出るまでの遅れを短くするため。バックエンドは worker を起こさず、`latest` が進むのを待つ（[書いた直後の読み](../../api/writes.md)）。
  - 見回りの `git ls-remote` は、repository ごとに 1 秒に 1 回である。GitForge の API の上限には数えないことが多い。ただし、git の操作にも、乱用を防ぐ制限がある（[費用と規模の見積もり](../../estimates/README.md#worker)）。
- repository の一覧は、見回りごとには読まない。別に、一覧を読み直す間隔（既定 10 秒、設定）ごとに、設定の DB と GitForge の API で読み直し、見回りは、最後に読めた一覧を使う。
  - なぜ：一覧を読むのは GitForge の API で、見回りの間隔ごとに読むと、API の上限に数えられるから。
  - なぜ 10 秒か：repository の作成の API が、書いたものが読む側に出るまで待つ上限（既定 10 秒）のうちに、多くは応答できるようにするため。GitForge が止まっても、見回りとハートビートが止まらないようにするためでもある。
  - 一覧を読むときは、時間の上限（30 秒）を付ける。読めなければ、前に読めた一覧を使い続ける。
  - そのため、新しい repository が見回りに入るのは、作ってから最大で一覧を読み直す間隔のあとである。repository の作成の API は、それより短い待つ上限を過ぎると、`Logiforge-Pending-Commit` で応答する（[書いた直後の読み](../../api/writes.md)）。
- 前の回の処理が終わっていない repository は、その回は飛ばす。
  - なぜ：1 つの repository の長い取り込みが、ほかの repository の見回りを遅らせないようにするため。
- 1 つの repository の処理は、下の「すること」である。repository が違えば、並行して動かす。

## すること

repository ごとに、次の順に処理する。

1. `git ls-remote` で、`main` とブランチの先頭を読み、前に読んだものと変わっていれば `git fetch` する。
2. 消えたブランチの履歴に、消えたことを記録する。
   - 消えたブランチは、置き場のブランチの名前の一覧のうち、履歴の最後が「消えた」でなく、`ls-remote` の結果にないものである。
   - なぜ置き場と比べるか：手元の ref と比べると、fetch で ref が消えたあと、記録する前に止まったときに、記録が失われるから。
   - `main` より先に行う。なぜ：`main` の処理で誤りが出ても、巻き込まれないようにするため。
3. `main` の、`latest` より新しいコミットを、古い順に 1 つずつ取り込む（[すべてのコミットに作る](../snapshot/main.md#すべてのコミットに作る)）。1 つのコミットについて、次の順に行う。
   1. 1 つ前のコミットのスナップショットツリーのファイルに、`git diff-tree` で求めた差分を重ねる。加わったか変わったファイルだけを読む。
   2. 重ねたファイルの一覧から、スナップショットツリーを作る。不変条件を確かめ、valid かと、`valid_commit`、`invalid_since` を求める（[valid](../invalid-main.md#valid)）。1 つ前の `violations` と比べて、新しく破れたものを求める。
   3. 反映した pull request の一覧で、このコミットを反映した apply request を探す（下の「どの apply request の反映か」）。
   4. 下の「コミットの警告」を確かめ、コミットの情報を作る。
   5. コミットの情報、`main` の並びの索引、スナップショットツリーの順に置く（[latest](../snapshot/main.md#latest)）。
   6. `latest` を、そのコミットに進める。
   - 解析の前に、blob の大きさと種類を確かめる。上限を超える blob と、普通のファイルでないもの（シンボリックリンク、実行の属性、submodule）は、読まずに、読めないファイルとして valid でない理由に入れる（[差分の検査](../checks.md)、[valid](../invalid-main.md#valid)）。取り込みは止めない。
4. 先頭が変わったブランチについて、base からの差分のスナップショットを作り、[ブランチの履歴](../snapshot/branch.md#ブランチの履歴) に足す。
   - 初めて見たブランチは、履歴より先に、ブランチの名前の一覧に足す。
5. `repositories` を書き直す。

- 1 つの repository では、`main` を取り込み終えてから、ブランチを取り込む。
  - なぜ：ブランチのスナップショットの検査とレビューの材料は、`main` のスナップショットツリーの上で作るから。`main` が追いつく前に作っても、すぐ古くなる。
  - そのため、`main` に溜まったコミットを取り込むあいだ（初めての取り込みなど）、その repository の新しい先頭のコミットのスナップショットは出ない。そのあいだ、そのコミットへのレビューは `snapshot_pending` になる（[書いた直後の読み](../../api/writes.md)）。
- git の操作（`ls-remote`、`fetch`、`diff-tree` など）には、1 回ごとに時間の上限（既定 10 分、設定）を付ける。超えたら、誤りとして、その repository のその回の処理を終える。次の見回りで、やり直す。
  - なぜ：GitForge やネットワークが固まっても、その repository の処理が止まったままにならないようにするため。
  - なぜ 10 分か：大きな repository の初めての clone（数百 MB の fetch）でも、終わるようにするため。
- 処理の誤り（上限を超えたことを含む）は、repository の名前をつけて、worker のログに書く。運用では、このログを監視して、その repository の `latest` が進まないことに気づく。
- 何度動かしても、結果は同じになる。
- 途中で止まっても、次の見回りで、`latest` の次のコミットから続ける。
  - 置き場に、`latest` より新しいコミットの情報やスナップショットツリーが置いてあれば、同じ中身で置き直す。

## どの apply request の反映か

- worker は、`main` のコミットごとに、そのコミットを反映した apply request を、反映した pull request の一覧で `merge_commit_sha` から探す（[どの apply request の反映か](../invalid-main.md#どの-apply-request-の反映か)、[一覧の読み](../list-reads.md#反映した-pull-request-の一覧worker)）。
  - 見つかれば、pull request の番号と、その先頭のコミットを、コミットの情報の `apply_request` と `merged_head` に置く。
  - 見つからなければ、worker がそのコミットを初めて見てから 60 秒までは、そのコミットを取り込まずに、次の見回りでやり直す。過ぎたら、`apply_request` と `merged_head` なしで置く。
    - コミットの時刻は使わない。push する人が、未来の時刻にできるから。初めて見た時刻は、worker のプロセスの中だけに持つ。
  - GitForge の API が答えないときも、そのコミットを取り込まずに、次の見回りでやり直す。`latest` は進めない。
- 見つけた結果は、表示と下の重なりの警告にだけ使う。valid かには使わない。

## コミットの警告

`main` の新しいコミットについて、次のことを確かめ、破れていれば警告としてコミットの情報に書く。

- 木の不変条件が成り立つ（[差分の検査](../checks.md) の「head の木で確かめること」）。1 つ前のコミットのスナップショットツリーの `violations` になかったものを、新しく破れたものとする。
- 反映した apply request の対象ノードが、その base のあとに、別の反映で変わっていない（[対象ノードの変化](../merge.md#対象ノードの変化)）。
  - 確かめるのは、上の「どの apply request の反映か」で、反映した apply request が見つかったコミットだけである。
  - base は、`merged_head`（反映した先頭のコミット）と、反映の直前の `main` の分かれた点である。worker は、自分の clone の `git merge-base` で求める。
  - 1 つ前のコミットのスナップショットツリーで、対象ノードの `last_changed` の番号が、base の番号より大きければ、重なりとする（[ノードを変えたコミット](../snapshot/main.md#ノードを変えたコミット)）。
  - 対象ノードは、反映のコミットで変わったファイルから求める。検証結果と背景情報はその仮説、新しいストーリーは親の仮説、inactive 化はそのストーリーである。
  - 反映のコミットで加わった検証結果が引用した部分木も確かめる。1 つ前のコミットのスナップショットツリーで、部分木のどれかのノードの `last_changed` の番号が base の番号より大きければ、重なりとする。
    - 1 つ前のスナップショットツリーにないノードは、同じ反映で加えたノードなので、確かめない。
    - なぜ：引用した時点は反映のコミットなので（[引用した時点](../../files/revisions.md#引用した時点)）、base から反映までの変化は、引用元の変化として現れないから。
  - 反映した先頭のコミットは、ブランチが消えても、`refs/pull/*/head` を fetch して読む。そのコミットか base が見つからなければ、確かめられなかったことを警告する（`overlap_unchecked`）。
- 警告の種類は、次のものである。
  - 新しく破れた不変条件の規則
  - `overlap`
  - `overlap_unchecked`
- なぜ：`main` への直接の push と、検査と merge のすき間（[反映の手順](../merge.md)）で起きたことに気づくため。

## 取り込みの時間

- 1 コミットあたりの時間は、スナップショットツリーの大きさに比例する。
  - なぜ：1 つ前のスナップショットツリーのファイルに差分を重ねても、スナップショットツリーを組み立て、値を計算し、圧縮して置くのは、スナップショットツリーの全体だからである。
  - 時間の見積もりは、[スナップショットの時間と大きさ](../../estimates/snapshot.md) に書く。
- 初めての取り込みの時間は、`main` のコミットの数と、1 コミットあたりの時間の積である。
- apply request の作成は、worker の取り込みを待たない。バックエンドが、作業用の git の複製から読んで検査する（[作成](../apply-request/create.md#作成)）。
- 大きな repository を移すときは、`ar create` の前に、見回りで取り込みを終えておく。

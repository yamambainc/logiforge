# バックエンド

バックエンド（core）が、どのルールを持ち、何を計算するかを確かめるときに読む。
ルールを持つのはこのレイヤーだけ、という決まりは [レイヤー構成](../architecture.md) が正本である。

## 持つルール

| ルール | 要件 | 実現 |
|---|---|---|
| 不変条件 | [仮説とストーリーの木](../../docs/tree/README.md)、[inactive 化](../../docs/tree/inactive.md) | [差分の検査](checks.md) |
| 反映の条件 | [論理レビュー](../../docs/apply-request/review.md) | [反映の手順](merge.md) |
| 対象ノードの変化 | [反映](../../docs/apply-request/README.md) | [反映の手順](merge.md) |
| 値の計算 | [真偽値の伝播](../../docs/tree/propagation.md) | 下の「計算」 |
| 着手できる作業 | [着手できる作業](../../docs/work/README.md) | 下の「計算」 |
| 作業の終わりの判定 | [作業の終わりの判定](../../docs/work/README.md) | 下の「計算」 |
| 認可 | [役割](../../docs/roles/README.md) | 下の「認可」 |

バックエンドが使うポートは、[ポート](ports/README.md) に、メモリに置く状態は [サーバの状態](server-state.md) に書く。

## 認可

- 主体には、次の 2 種類がある。
  - `user`：WebUI を使う利用者
  - `client`：CLI を使う主体（エージェントか人）
- `user` が使える書き込みは、利用者の 2 つの操作だけである。
  - repository の作成（根の主文を含む）
  - 人への依頼への回答
- それ以外の書き込みは、`client` だけが使える。
- 主体と主体の種類は、[認証](ports/authentication.md) のポートで確かめる。
- repository を使えるのは、その repository を読める主体だけである。

## repository の用意

利用者が repository の名前と根の主文を送ったら、バックエンドは次の順に処理する。

1. やりとりの「名前から provider_ref を求める」を呼ぶ（[repository の登録](../adapters/README.md)）。
2. やりとりの「repository の、やりとりの側を用意する」を呼ぶ。
   - なぜ木の読み書きより先か：プロバイダによっては、やりとりの側の用意が git リポジトリの用意を兼ねるから。git リポジトリに書き込めるかは、そのあとでないと確かめられない。
3. 木の読み書きの「用意する」を呼ぶ。
4. 木の読み書きの「最初のリビジョンで main を作る」を呼ぶ。
   - 最初のリビジョンには、根の仮説を入れる。
5. [サーバの状態](server-state.md) の repository の登録に足す。

途中で失敗したら、同じ要求をもう一度送れば、続きから終わらせられる。

- 手順 1〜3 と 5 は、すでに済んでいれば何もしない。
- 手順 4 が「`main` がすでにある」で失敗したら、バックエンドは次のように判定する。
  - `main` が最初のリビジョンだけを指し、それが署名付きで、根の主文も同じなら、済んでいるものとして手順 5 に進む。
  - それ以外なら、`repository_exists` で失敗する。
- なぜ：2 つの用意が同時に走っても、負けた側が、この判定で成功して終われるようにするため。

## 操作と差分

- API が受け取る 4 種類の操作（[操作](../../docs/apply-request/README.md)）を、バックエンドがファイルの変化に変える。
  - `story.create`：仮説とストーリーのディレクトリを加える。
  - `story.inactivate`：`inactivated.md` を加える。
  - `verdict.submit`：`verdicts/` に検証結果のファイルを、`artifacts/` に artifact のファイルを加える。
  - `node.edit`：`background.md` の末尾に文章を加える。
- 操作とファイルの変化は 1 対 1 なので、バックエンドは差分から操作を復元できる。
  - なぜ：操作を別に保存しなくても、差分だけで API の応答を作れるようにするため。
  - 差分の起点は、[反映の手順](merge.md) の base である。
- 版は、バックエンドが [木の読み書き](ports/tree-read-write.md) の「リビジョンを作る」で作る。
  - 版には、差分を書いたセッションと署名を記録する（[記録の形式](../files/revisions.md)）。
  - 今の版は、やりとりに記録された版のうち、番号が最大のものである。
    - 番号には、抜けが出ることがある（下の作り直しのとき）。そのため、版の数では数えない。
  - 新しい版の番号は、今の版の番号に 1 を足したものである。
  - 「同じ名前のリビジョンがすでにある」で失敗したら、番号を進めて作り直す（[失敗の種類](ports/tree-read-write.md)）。
    - なぜ：同じ apply request の更新が同時に走っても、版を取り違えないようにするため。

## 計算

バックエンドは、次のものを保存せず、木の読み書きとやりとりのデータから計算する。

- 値と、葉・要再検討・inactive
  - 「木を読む」で読んだ `tree/` のファイルだけから計算する。
- 引用元の変化
  - 有効な検証結果の部分木の引用ごとに、「変更を列挙する」で、引用したリビジョンから今の `main` までの、部分木のパスの変化を探す。
- 着手できる作業
  - 木の作業は、`tree/` から計算する。
  - apply request と人への依頼の作業は、[やりとり](ports/interaction.md) の提案、版、レビュー、人への依頼から計算する。
- 作業の終わりの判定
  - 根拠部分木を `tree/` から求め、上の着手できる作業のうち、根拠部分木にあるものを数える。

## 突き合わせ

- バックエンドは、定期的に突き合わせを行う。正本は `main` である。
  - `main` の first-parent の並びにあるコミットの `Logiforge-Apply-Request:` を読む。
  - やりとりに記録されていない反映があれば、後から記録する。
    - 何度行っても、結果は同じになる。
  - `Logiforge-Signature:` のないコミットは、反映の手順によらない変更として、API の応答で警告する（[記録の形式](../files/revisions.md)）。
  - 前回の突き合わせのときの `main` と今の `main` の、共通の祖先が前回の `main` でなければ、force push として警告する。
    - 前回の `main` は、[サーバの状態](server-state.md) の突き合わせの状態に置く。

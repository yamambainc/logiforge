# 反映かの判定

worker が、`main` の新しいコミットごとに、そのコミットが反映（論理レビューを通った apply request の merge）によるものかを、どう確かめるかを確かめるときに読む。
反映によらないコミットを見つけたあとの扱いは、[壊れた repository](broken.md) に書く。

## 考え方

- 反映によるものかは、だれが merge したかでは決めない。中身が反映の条件を満たしているかで決める。
  - なぜ：merge する主体を 1 つ（書き込み主体）に絞らずに済むから。承認された apply request を、reviewer のトークンで merge しても、人が GitForge の画面で merge しても、正しい反映として扱える。
- コミットのメッセージの trailer は、判定に使わない。なぜ：`main` に push できる人なら、だれでも書けるから。
- 確かめるのは、[反映の手順](merge.md) の手順 1 と手順 3 と同じことである。バックエンドと同じコードを使う。
  - なぜ同じことか：バックエンドが反映の前に確かめることを、反映のあとに worker がもう一度確かめれば、反映の手順を通らずに `main` に入ったものだけが残るから。

## 確かめること

`main` のコミット C（1 つ前の `main` のコミットを P とする）について、次のどちらかなら、反映によるものとする。

### repository の用意のコミット

- C が根のコミットで、trailer `Logiforge-Init:` がある。
  - なぜ位置で決めてよいか：repository はバックエンドが作るので、根を先に置ける人がいないから。
- C が根の次のコミットで、trailer `Logiforge-Init-Mac:` の MAC が合う。
  - MAC は、repository の識別子、P の SHA、C で加わったファイルのパスと sha256 に対して求める。鍵は、記録のコメントと同じものである（[GitForge アダプタの共通の書き方](../adapters/pull-requests.md#記録のコメント)）。
  - C の差分が、MAC に書いたファイルを加えることだけであることも確かめる。
  - なぜ：GitHub の空のリポジトリには、ファイルを 1 つずつしか置けないので、背景情報を 2 つ目のコミットで置くから（[GitHub アダプタ](../adapters/github.md)）。MAC を求められるのは、鍵を持つバックエンドだけである。

### apply request の反映のコミット

次のすべてを満たす。

1. C を merge した pull request が、GitForge にある。向き先が `main` で、merge のコミットが C である（下の「GitForge の API」）。
2. C の形が、次のどちらかである。
   - squash merge：親が P だけである。
   - merge のコミット：最初の親が P で、2 つ目の親が、pull request の先頭のコミット H である。
   - rebase による merge（複数のコミットが並ぶもの）は、受け付けない。なぜ：途中のコミットの木が、どの先頭のコミットの木とも合わないから。
3. pull request に、MAC の合う `apply_request` の記録がある（[記録のコメント](../adapters/pull-requests.md#記録のコメント)）。
4. 反映の手順の手順 1 の条件を、H について満たす：レビューの鎖が切れていない。H に対する最後の決めるレビューが `approve` である。H に書いたセッションの trailer がある。reviewer のセッションが、どの先頭のコミットを書いたセッションとも違う。
5. P の木に、H の差分（ブランチのスナップショット）を重ねられ、重ねた木の全体が、C の木と同じである。
   - H のスナップショットがなければ、`refs/pull/<number>/head` を fetch して作る。
6. 重ねた木が、反映の手順の手順 3 の検査（対象ノードの変化、差分の検査）を、P を今の `main` として満たす。
   - 直すための apply request（`repair.revert`、`repair.accept`）は、手順 3 のかわりに、直す条件を確かめる（[壊れた repository](broken.md) の「直すための apply request」）。

- どれかを満たさなければ、反映によらないコミットとする。コミットの記録の警告に、満たさなかった条件を書く。
- 壊れているあいだは、直すための apply request の反映のコミットだけを、反映によるものとする。

## GitForge の API

| GitForge | C を merge した pull request の読み方 |
|---|---|
| GitHub | `GET /repos/{owner}/{repo}/commits/{sha}/pulls` のうち、merge されていて、`merge_commit_sha` が C で、向き先が `main` のもの |
| Forgejo | `GET /repos/{owner}/{repo}/commits/{sha}/pull` が返すもので、merge されていて、向き先が `main` のもの |

- 記録とレビューは、その pull request のコメントとレビューの一覧から読む（[GitForge アダプタの共通の書き方](../adapters/pull-requests.md)）。
- API が答えないときは、C を取り込まずに、次の見回りでやり直す。`latest` は進めない。
  - なぜ：判定できないコミットを、正しいとも壊れているとも記録しないため。
- C を merge した pull request が見つからないときは、worker が C を初めて見てから 60 秒までは、決めずにやり直す。
  - なぜ：GitForge は、merge のすぐあと、merge のコミットから pull request を引けないことがあるから（Forgejo 17 で確かめた）。
  - コミットの時刻は使わない。push する人が、未来の時刻にできるから。初めて見た時刻は、worker のプロセスの中だけに持つ。

## worker が持つもの

- 記録の MAC の鍵（確かめるため）。鍵は、バックエンドと同じものである（[設定と秘密情報](../adapters/README.md#設定と秘密情報)）。
  - worker は、鍵で記録を作れるので、バックエンドと同じく信頼の境界の中に置く。worker は、鍵を、確かめることにだけ使う。
- GitForge の読むだけの資格情報（git と API）。

## 重さ

`main` のコミット 1 つの判定に、次のものがかかる。

| もの | 量 | 目安 |
|---|---|---|
| GitForge の API | pull request の読み 1 回、コメントとレビューの一覧の読み 2 回（ページが続けば、その分） | 3 回、1 回あたり 100〜300 ms |
| 差分を重ねる計算 | 先頭のコミットの差分のファイルの数に比例する | 1 回の apply request の差分は数ファイルなので、数 ms |
| 重ねた木の検査 | スナップショットツリーの組み立てと検査と同じく、木のノードの数に比例する | ノード 100 で約 20 ms、1,000 で約 110 ms、4,000 で約 320 ms（[費用と規模の見積もり](../estimates.md) の「組み立てと検査」） |

- 合わせて、ノード 4,000 の木でも、コミット 1 つに 1.3 秒ほどである。多くは GitForge の API の待ちである。今の 1 コミットの取り込み（ノード 4,000 で約 460 ms）に足すと、約 3 倍になる。
- 重ねた木は、そのコミットのスナップショットツリーと同じものになるので、検査の結果を、スナップショットツリーを作るのに使い回せる。そのときは、足す計算の時間は API の待ちだけになる。
- `main` に入るコミットの数は、apply request の反映の数と同じなので、多くても 1 時間に数十である。GitHub の REST の上限（1 時間に 5,000）に対して、十分に小さい。
- 判定は、新しいコミットにだけ行う。取り込み済みのコミットは、判定し直さない。

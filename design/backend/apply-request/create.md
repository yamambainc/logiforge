# apply request の作成

バックエンドが、apply request を作るときに何をどの順に行い、作業用の git の複製をどう持つかを確かめるときに読む。
pull request との対応は [apply request](README.md) に書く。

## 作成

1. GitForge で、そのブランチの open の pull request を読む（[同じ要求の繰り返し](../../api/writes.md)）。
   - あり、作者が要求した主体なら、送り直しとみなして、それを返して終わる。中身は比べない。
   - あり、作者が違えば、`validation_failed` で受け付けない。
2. 作業用の git の複製に、`main` とブランチを fetch する（下の「作業用の git の複製」）。
3. ブランチの先頭と `main` の分かれた点（base）を求め、base から変わったファイルだけを読む。
   - 要求に `commit` があり、ブランチの先頭と違えば、`validation_failed` で受け付けない。
   - base の木は、置き場にスナップショットツリーがあれば、それを使う。なければ（worker が追いついていない）、作業用の複製から読む。
4. 差分に、[差分の検査](../checks.md) を行う。4 種類の操作として読めない変化があれば、`validation_failed` で受け付けない。
   - 解析のコードは、worker と CLI の `check` と同じものである。
5. 要求した主体のトークンで、GitForge に pull request を作る。apply request の識別子は、その pull request の番号である。
   - 手順 1 のあとに、同じブランチの open の pull request ができていれば、GitForge が拒む。そのときは、手順 1 からやり直す。
6. 応答する。
   - 先頭のコミットの一覧とレビューの材料は、worker のスナップショットから読む。worker がブランチを取り込むまで、レビューは `snapshot_pending` になる（[レビュー](../../api/writes.md)）。
   - 応答の操作の一覧は、worker がまだブランチを取り込んでいなければ、手順 4 の検査の結果から返す。

- 作成は、worker を待たない。
  - なぜ：検査をバックエンドで行えば、バックエンドを増やすだけで、作成の数に合わせて広げられるから。
- 作成の時点の検査は、今の `latest` のスナップショットツリーを、検査の文脈（引用元など）に使う。worker が `main` に追いついていなければ、文脈は少し古い。反映の前の検査（[反映の手順](../merge.md)）で、今の `main` に対して確かめ直す。
- 作成の時点の base と、worker があとでブランチを取り込むときの base（そのときの `main` との分かれた点）は、あいだに `main` が進むと違いうる。
  - 先頭のコミットの一覧とレビューの材料は、worker が求めた base で作る。
  - 反映の前に、今の `main` に対して確かめ直す（[反映の手順](../merge.md)）ので、正しさには関わらない。

## 作業用の git の複製

- バックエンドは、repository ごとに、作業用の git の複製（bare）を持つ。
  - 置き場所は、一時的なディスク（コンテナの `/tmp` や `emptyDir`）である。
  - 初めて要るときに、1 度だけ clone する。そのあとの要求では、`main` とそのブランチを fetch するだけにする。要求ごとに clone しない。
  - blob を省いた clone（`--filter=blob:none`）にはしない。
    - なぜ：置き場に base のスナップショットツリーがないとき、base のすべてのファイルを読むから。blob を省くと、そのとき blob ごとに GitForge へ取りに行き、遅くなる。
- 複製は、正本ではない。使い捨てのキャッシュである。消えても、次の要求で作り直す。
  - プロセスごとに持ち、プロセスの間で共有しない。プロセスが止まるときに消す。
- 同じプロセスの中で、同じ repository への要求が重なったら、repository ごとのロックで、1 つずつ通す。
  - なぜ：fetch と読むことが、互いに混ざらないようにするため。違う repository への要求は、並行してよい。
- git は、worker と同じ、読むだけのユーザーの資格情報で読む（[git アダプタ](../../adapters/git.md)）。書く鍵は使わない。

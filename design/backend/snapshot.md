# スナップショット

バックエンドが読むスナップショットツリーと、コミットの記録の形を確かめるときに読む。
作るのは [worker](worker.md) だけで、バックエンドは読むだけである。

## 考え方

- スナップショットは、あるコミットの木を解析したものである。読むためだけにある。
  - 正本は、今までどおり git の `main` である（[木のファイル配置](../files/README.md)）。
  - スナップショットは、git からいつでも作り直せる。
- スナップショットを作って置き場に書くのは、worker だけである。
  - バックエンドは、木を読むのも、反映の検査も、スナップショットの上で行う。git を読むのは、apply request の作成の検査のときだけである（[作成](apply-request.md#作成)）。
  - なぜ：永続する clone を持つものを worker の 1 つにし、バックエンドがデータを保持しないようにするため（[worker](worker.md)）。
- コミットの SHA ごとに 1 つ作る。中身は変えない。上書きも削除もしない。
  - なぜ：SHA で引けば、いつ読んでも同じ中身なので、キャッシュを置くときに、そのままキャッシュできるから。
  - 例外は、`latest`、`main` の並びの索引、ブランチの履歴とその一覧である（[スナップショットの置き場](ports/snapshot-store.md)）。

## 中身

- 形の正本は、`internal/snapshot` の Go の型である。このページには、項目の表だけを置く。
- 形にはフォーマットバージョン（`format_version`）を持たせる。項目を足すときも、フォーマットバージョンを上げる。読むときにフォーマットバージョンを確かめる。
- 今のフォーマットバージョンは 6 である。5 から、スナップショットツリーの `history` とノードの変更の一覧をなくし、`last_changed`、`inactivated_at`、`warned`、コミットの記録の `previous`、`main` の並びの索引を足した。
  - まだデプロイしていないので、入れ替えの手順は、必要になったときに書く。

`main` のコミットのスナップショットは、コミットの記録と、スナップショットツリーの 2 つに分けて置く。

- どちらも、`main` のすべてのコミットに置く（下の「すべてのコミットに作る」）。
- ブランチの先頭のコミットには、コミットの記録と差分を置く（下の「ブランチのスナップショット」）。

コミットの記録（数 KB）：

| 項目 | 内容 |
|---|---|
| `revision` | コミットの SHA。API の `commit` に当たる |
| `parent` | first-parent のコミットの SHA。最初のコミットでは null。`branch` では、base（`main` と分かれた点） |
| `number` | `main` のコミットだけ。最初のコミットを 1 とする、first-parent の番号 |
| `kind` | `main`（`main` のコミット）、`branch`（利用者が push したブランチの先頭） |
| `committed_at` | コミットの時刻 |
| `trailers` | コミットの trailer（[記録の形式](../files/revisions.md)） |
| `last_good` | `main` のコミットだけ。repository が壊れていれば、最後に正しかった時点のコミットの SHA。壊れていなければ null（[壊れた repository](broken.md)） |
| `warnings` | `main` のコミットだけ。反映によらないこと（[壊れた repository](broken.md) の「反映かの判定」）、このコミットで新しく破れた不変条件、worker が見つけた警告（重なり、`main` の書き換え）（[すること](worker.md#すること)） |
| `changes` | `main` のコミットだけ。このコミットで変わったノードごとの、ノードの識別子、変わったファイルの種類（`hypothesis`、`background`、`verdict`、`story`、`inactivated`）とパス、そのノードを前に変えたコミット（`previous`。番号と SHA。初めてなら null）（下の「ノードを変えたコミット」） |
| `paths` | `branch` のコミットだけ。base から変わったファイルのパスと、変わり方（`added`、`modified`、`deleted`） |

スナップショットツリー：

| 項目 | 内容 |
|---|---|
| `nodes` | ノードごとの、ファイルの中身（git のファイルのバイトそのもの）と、計算した値・葉・要再検討・inactive と、そのノードを最後に変えたコミット（`last_changed`。番号と SHA）（下の「ノードを変えたコミット」）。ストーリーは、`inactivated.md` が加わったコミットの番号（`inactivated_at`。inactive でなければなし）も持つ。検証結果のファイルは、そのファイルが加わったコミット（`added`。番号、SHA、反映の apply request）も持つ |
| `artifacts` | `artifacts/sha256/` にあるファイルの一覧。各項目は、sha256、blob の SHA、大きさを持つ。中身は持たない |
| `other` | どのノードにも artifact にも当たらないファイル（木の外のファイルなど）。元のファイルの一覧を、そのまま戻すために持つ |
| `warned` | 最初のコミットからこのコミットまでのうち、警告のある `main` のコミットの一覧。各項目は、番号、SHA、警告の種類を持つ |
| `broken` | このスナップショットツリーで破れている不変条件のすべて（前のコミットから破れているものを含む） |

- ノードのファイルは、git のファイルのバイトと、blob の SHA を持つ。
  - なぜ：バックエンドが、スナップショットから元のファイルの一覧に戻し、[差分の検査](checks.md) に渡すため。
- スナップショットツリーは、`main` のコミットの一覧（history）を持たない。ノードごとの、変えたコミットの一覧も持たない。
  - なぜ：どちらも、コミットの数とともに伸びるから。すべてのコミットにスナップショットツリーを作るので、持つと、置き場の容量がコミットの数の 2 乗で増える（[費用と規模の見積もり](../estimates.md)）。
  - かわりに、コミットの記録と、`main` の並びの索引から引く（下の「コミットの記録から引くもの」）。
  - `warned` は、警告のあるコミットだけを持つ。警告の数でしか伸びない。
  - `warned` の数に上限は置かない。なぜ：警告のあるコミットが増え続けるのは、`main` の保護が外れて、反映によらない push が続くときである。それは異常で、警告そのもので気づくから。
- スナップショットツリーは、すべてのノードを持つ。数百 KB から数 MB で、圧縮して置く。
  - 重くなったら、根の子の部分木ごとに分けて置く。今は分けない。
- 値は、作るときに計算して入れる（[真偽値の伝播](../../docs/tree/propagation.md)）。
  - なぜ：読むたびに計算しないため。スナップショットは正本ではないので、値を持ってもファイルと食い違わない。
- artifact の中身は、スナップショットとは別に、sha256 の名前で置き場に置く。
- 形を変えるときは、置き場の接頭辞ごと新しくして作り直す。古いものは消さない。ただし、ブランチのスナップショットは、作り直せないので、古い形のまま読むか、移す。

## すべてのコミットに作る

- worker は、`main` のすべてのコミットに、コミットの記録とスナップショットツリーを作る。
- 作るのは、古い順に 1 つずつである。1 つ作るたびに `latest` を進める（[latest](#latest)）。
  - そのため、`latest` までのすべてのコミットに、スナップショットツリーがある。
  - 溜まったコミットを取り込むあいだも、`latest` は、取り込み終えたいちばん新しいコミットを指す。
- 1 つのコミットのスナップショットツリーは、1 つ前のコミットのスナップショットツリーのファイルに、そのコミットの差分を重ねて作る。
  - 1 つ前のスナップショットツリーがなければ（最初のコミット、clone し直したあと）、そのコミットのすべてのファイルを読んで作る。
- 新しく破れた不変条件は、すべてのコミットについて、1 つ前のスナップショットツリーの `broken` と比べて求める。
- なぜ、すべてのコミットに作るか：
  - バックエンドが、過去のどの `main` のコミットも、置き場から読むだけで扱えるから。worker に作らせる要求が要らない。
  - 新しく破れた不変条件が、どのコミットで破れたかまで、いつもわかるから。
  - 時間と容量は、測って確かめた（[費用と規模の見積もり](../estimates.md)）。
- 歯止め（溜まったコミットが多いときに、先に先頭を作ること）は、置かない。
  - なぜ：古い順に作っても、`latest` は 1 コミットごとに進むので、読む側が止まらないから。ノード 1,000 個の木で、100 コミットが溜まっても、追いつくまで約 18 秒である（[費用と規模の見積もり](../estimates.md)）。

## コミットの記録から引くもの

| 求めるもの | 求め方 |
|---|---|
| コミットが `main` の並びにあるか | そのコミットの記録の `number` を n として、n が `latest` の `number` 以下で、かつ `main` の並びの索引の n 番が、その SHA である |
| コミットの番号 | そのコミットの記録の `number`。`main` の並びにあることも、上の方法で確かめる |
| 番号から SHA | `main` の並びの索引の、その番号 |
| 反映によらない変更と、不変条件の警告 | 今の `main` のスナップショットツリーの `warned` |
| apply request が反映されたコミット | GitForge の pull request の merge のコミット（[GitForge のポート](ports/gitforge.md)）。そのコミットの記録があれば、読む側に出ている |
| repository に、最初のコミットしかないか | `latest` のコミットの記録の `number` が 1 である |

- `main` の並びの索引は、repository ごとに、番号から SHA を引くキーの集まりである（[スナップショットの置き場](ports/snapshot-store.md)）。
  - worker は、コミットの記録を置いたあと、スナップショットツリーを置く前に、その番号のキーを書く。
  - `main` が書き換えられたら、書き換えのあとの番号のキーを、新しい並びの SHA で上書きする（[latest](#latest)）。
  - なぜ索引を置くか：コミットの記録は SHA ごとに残るので、書き換えで `main` から外れたコミットの記録も残る。記録だけでは、今の並びにあるかがわからないから。
  - なぜ `latest` の番号と比べるか：`main` が短く書き換えられると、新しい並びより後ろの番号のキーに、古い SHA が残るから。
  - 書き換えの取り込みの途中（索引は書き直したが、`latest` はまだ書き換えの前のコミット）では、書き換えの前のコミットが、一時的に並びにないと判定されることがある。`latest` が書き換えのあとのコミットに進めば、食い違いはなくなる。

## ノードを変えたコミット

- worker は、`main` のコミットの記録を作るとき、そのコミットで変わったノードごとに、そのノードを前に変えたコミットを `previous` に書く。
  - 「変わった」の範囲は、[対象ノードの変化](merge.md#対象ノードの変化) のパスの決まりに従う。inactive 化の子孫は、1 つ前のスナップショットツリーのノードのうち、そのストーリーのディレクトリの下にあるものである。
  - 前に変えたコミットは、1 つ前のコミットのスナップショットツリーの、そのノードの `last_changed` である。
- スナップショットツリーは、各ノードの `last_changed` を持つ。
- これにより、次のものを求める。

| 求めるもの | 求め方 | 読む数 |
|---|---|---|
| 対象ノードの変化 | 対象ノードの `last_changed` の番号が、base の番号より大きいか（[反映の手順](merge.md)） | スナップショットツリー 1 つ |
| 引用元の変化 | 部分木のノードの `last_changed` の番号のいちばん大きいものが、引用したコミットの番号より大きいか | スナップショットツリー 1 つ |
| ノードの履歴 | そのノードの `last_changed` のコミットの記録から、`previous` を順にたどる（[ノードの履歴を読む](../api/endpoints/node/history.md)） | 1 件ごとにコミットの記録 1 つ |
| `inactivated.md` が加わったコミット | ストーリーの `inactivated_at` | スナップショットツリー 1 つ |
| 検証結果が加わったコミット | 検証結果のファイルの `added` | スナップショットツリー 1 つ |

- ノードの履歴は、前の形でも、1 件ごとにコミットの記録を読んで trailer を返していた。たどる形にしても、読む数は同じである。ただし、次に読むコミットは、前のコミットの記録を読むまでわからないので、順にしか読めない（[費用と規模の見積もり](../estimates.md)）。
- worker は、`inactivated_at` と検証結果の `added` を、そのファイルが加わったコミットで書き、そのあとのスナップショットツリーに引き継ぐ。
  - ファイルを書き直しても、加わったコミットのまま動かさない。
  - ファイルが消えたら、値も消す。もう一度加わったら、そのコミットを書く。

## latest

`latest` は、repository ごとに 1 つあり、取り込み終えたいちばん新しい `main` のコミットの SHA を持つ。

- worker は、`main` のコミットの記録、`main` の並びの索引、スナップショットツリーを置き終えてから、`latest` を書く。
  - そのため、`latest` が指す `main` のコミットと、その祖先には、いつもスナップショットツリーがある。
- 新しい `main` のコミットの親が、今の `latest` であるときだけ、`latest` を書く。
  - なぜ：worker が誤って 2 つ動いても、`main` が古い SHA に戻らないようにするため。
  - 置き場が条件付きの書き込みを持つなら、それでも守る（[スナップショットの置き場](ports/snapshot-store.md)）。
- 今の `latest` が、git の今の `main` の並びになければ、`main` が書き換えられている。
  - worker は、新しい並びのうち、スナップショットツリーのあるいちばん新しいコミットから続ける。
  - 書き換えのあとの最初のコミットで、`latest` を上書きし、そのコミットの警告（`main_rewritten`）として記録する。
  - 取り込み済みのコミットまで短くされたときは、記録するコミットがないので、`latest` をそのコミットに戻し、書き換えはログにだけ書く。
- 読んだあとに `latest` が書き換えられていたら（worker が 2 つ動いている）、書かない。
- worker は、`latest` がある repository の名前の一覧を、置き場の `repositories` に書く。

## ブランチのスナップショット

ブランチの差分：

| 項目 | 内容 |
|---|---|
| `base` | base（`main` と分かれた点）の SHA |
| `entries` | 変わったパスごとの、変わり方、base での blob の SHA（`base_sha`）、先頭でのファイル（消えたときはなし） |

- ブランチのスナップショットは、base からの差分だけを持つ。
  - なぜ：ブランチの先頭のコミットは、`main` のコミットよりずっと多く作られるから（[費用と規模の見積もり](../estimates.md)）。
- ブランチのスナップショットは、コミットの SHA ごとに作る。apply request の先頭のコミットの一覧に入るかどうかに関わらない。
- ブランチのスナップショットは、フォーマットバージョンの接頭辞の外に置き、中に自分のフォーマットバージョンを持つ（[スナップショットの置き場](ports/snapshot-store.md)）。消えたブランチの先頭のコミットは、git から作り直せないからである。

## ブランチのコミットのスナップショットツリー

- バックエンドは、ブランチのコミットのスナップショットツリーを、読むたびに作る。置き場には置かない。
  1. そのコミットのブランチのスナップショットを読む。
  2. その `base` の `main` のスナップショットツリーに、ブランチの差分を重ねる。
  3. 重ねたファイルの一覧から、木を組み立て、値を計算する。
- ブランチの差分は、`base` からのものなので、重ねるときに衝突は起きない。
- 次のときは、`snapshot_pending`（503）を返す。worker が追いつけば、作れるようになるからである。
  - そのコミットのブランチのスナップショットがまだない。
  - `base` の `main` のコミットが、まだ取り込まれていない。
  - 向き先のブランチの履歴がまだない（worker が一度も取り込んでいない）。
- 使うところは、次の 2 つである。
  - 向き先が `main` でない apply request の、向き先の今の先頭（下の「向き先に重ねる」）
  - 木を読むエンドポイントの `commit` に、ブランチのコミットを指定したとき（[API のコミット](../api/README.md#コミット)）
- なぜ置き場に置かないか：ブランチのコミットは `main` のコミットよりずっと多く、すべてに木を作ると、置き場と worker の仕事が増えるから。読まれるのは、向き先が `main` でない apply request を見るときだけである。
- かかる時間は、ノード 4,000 個の木で約 0.44 秒である（[費用と規模の見積もり](../estimates.md) の「全体を読んで作る」）。

## 向き先に重ねる

- バックエンドは、apply request の向き先の今の先頭のスナップショットツリーに、apply request の先頭のコミットの差分を重ねる。
  - 向き先が `main` なら、今の先頭は `latest` である。
  - 向き先が `main` でなければ、今の先頭は、向き先のブランチの[ブランチの履歴](#ブランチの履歴) の最後のコミットである。そのスナップショットツリーは、上の「ブランチのコミットのスナップショットツリー」で作る。
    - 検査はしない（[向き先](apply-request.md#向き先)）。値は計算するが、決まりに沿っているかは確かめない。
    - 向き先のブランチが消えたことが履歴に記録されていれば、`not_found`（404）を返す。
    - かかる時間は、ノード 4,000 個の木で、作るのと重ねるのを合わせて約 1 秒である。
    - 衝突は判定しない。差分が変えたパスは apply request の先頭のファイルを、ほかのパスは向き先の今の先頭のファイルを使う。
      - なぜ：積み上げたブランチの差分は、`main` との分かれた点からなので、下の apply request の変更を含んでいるから。バックエンドは git を読まないので、向き先との本当の分かれた点を知らず、`base_sha` で比べると、git では衝突しないものまで衝突にしてしまう。検査はしないので、本当の衝突は GitForge の画面で分かる。
  - 向き先が `main` のときは、差分が変えたパスが、`base_sha` のあとに向き先でも変わっていれば、重ねられない。git の merge でも衝突するものとして、衝突にする。
  - 重ねたファイルの一覧から、木を組み立て、値を計算する。
- 使うところは、次の 2 つである。
  - 反映の直前の検査（[反映の手順](merge.md)）。衝突は `conflict` にする。
  - 反映したあとの姿を読むこと（[木の概要を読む](../api/endpoints/tree/get.md) などの `apply_request`）。向き先が `main` のときの衝突は、`overlay_conflict`（409）を返し、`detail` に衝突したパスを書く。
- 重ねた結果は、置き場に置かない。読むたびに重ねる。
  - なぜ：置き場に置くと、向き先が進むたびに作り直すものが増えるから。バックエンドはデータを保持しない（[状態を持たない](README.md#状態を持たない)）。
  - かかる時間は、ノード 4,000 個の木で、1 回 0.5 秒ほどである（[費用と規模の見積もり](../estimates.md)）。

## ブランチの履歴

- worker は、ブランチごとに、先頭のコミットが変わった順の一覧を、置き場の `keep/<repository>/branches/<ブランチの名前>` に書く（[スナップショットの置き場](ports/snapshot-store.md)）。
  - 各項目は、先頭のコミット、base、見つけた時刻を持つ。ブランチが消えたときは、消えたことを足す。
  - 一覧に足すのは、スナップショットを作り終えたコミットだけである。そのため、一覧に出ているコミットには、いつもスナップショットがある。
- apply request の先頭のコミットの一覧は、この一覧から求める（[先頭のコミット](apply-request.md#先頭のコミット)）。
- 反映は squash merge なので、ブランチの先頭のコミットは `main` から辿れない。ブランチを消すと、git からも辿れなくなる。
  - 先頭のコミットのスナップショットとブランチの履歴は、worker が置き場に残し、消さない。そのため、反映や close のあとも、先頭のコミットの差分とレビューしたコミットを読める。
  - GitForge も、pull request の最後の先頭のコミットを ref に残す（[アダプタ](../adapters/README.md)）。途中の先頭のコミットは、置き場にしか残らない。
- ブランチの履歴と、消えたブランチの先頭のコミットのスナップショットは、git から作り直せない。置き場のうち、ここだけはバックアップを取る（[組み合わせ](../adapters/README.md)）。

## 読む

- バックエンドは、木を読むとき、`latest` を読み、次にその `main` の SHA のスナップショットツリーを読む。
  - API で `commit` を指定されたら、その SHA のスナップショットツリーを読む。
  - その SHA のスナップショットツリーがなければ、`snapshot_pending` を返す（[書いた直後の読み](../api/writes.md)）。まだ取り込まれていないのか、git にもない SHA なのかは、区別しない。バックエンドは git を読まないからである。
- apply request の先頭のコミットの一覧は、ブランチの履歴から読む。
- バックエンドは、読んだものを保持しない。読むたびに置き場から取る（[状態を持たない](README.md#状態を持たない)）。
  - 置き場は、バックエンドから転送の費用なしで読める場所に置く（[スナップショットの置き場のアダプタ](../adapters/snapshot-store.md)）。

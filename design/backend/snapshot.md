# スナップショット

バックエンドが、木を git から読まずに、どう読むかを確かめるときに読む。
置き場のポートは [スナップショットの置き場](ports/snapshot-store.md)、作り方の 2 つの経路は下の「作る」に書く。

## 考え方

- スナップショットは、あるコミットの木を解析したものである。読むためだけにある。
  - 正本は、今までどおり git の `main` である（[木のファイル配置](../files/README.md)）。
  - スナップショットは、git からいつでも作り直せる。
- バックエンドの読む経路では、git を使わない。
  - なぜ：プロセスごと・repository ごとに clone を持たずに済み、何台並べても読む量が増えないから。
  - なぜ：GitHub の構成で、GitHub の API のレート制限に当たらないから。
- コミットの SHA ごとに 1 つ作る。中身は変えない。上書きも削除もしない。
  - なぜ：SHA で引けば、いつ読んでも同じ中身なので、プロセスのメモリにそのままキャッシュできるから。

## 中身

スナップショットは、コミットの記録と、木の 2 つに分けて置く。

コミットの記録（数 KB）：

| 項目 | 内容 |
|---|---|
| `revision` | コミットの SHA |
| `parent` | first-parent のコミットの SHA。最初のリビジョンでは null |
| `kind` | `main`（`main` のコミット）、`version`（版）、`answer`（回答） |
| `committed_at` | コミットの時刻 |
| `trailers` | コミットの trailer（[記録の形式](../files/revisions.md)） |
| `signed` | 署名が正しいか |
| `changes` | `parent` から変わったもの。ノードの識別子と、変わったファイルの種類（`hypothesis`、`background`、`verdict`、`story`、`inactivated`）の組 |

木（数百 KB から数 MB）：

| 項目 | 内容 |
|---|---|
| `nodes` | `tree/` のすべてのノード。ファイルの中身と、計算した値・葉・要再検討・inactive |
| `artifacts` | `artifacts/sha256/` にあるファイルの sha256 の一覧 |
| `unsigned` | 最初のリビジョンからこのコミットまでの、署名のない `main` のコミットの SHA の一覧 |

- 2 つに分けるのは、親をたどるときに、木を読まずに済ませるためである（下の「読む」）。
- 値は、作るときに計算して入れる（[真偽値の伝播](../../docs/tree/propagation.md)）。
  - なぜ：読むたびに計算しないため。スナップショットは正本ではないので、値を持ってもファイルと食い違わない。
- `unsigned` は、親の一覧を引き継いで足す。
  - なぜ：反映によらない変更の警告を、親をたどらずに出せるようにするため。
- artifact の中身は、スナップショットとは別に、sha256 の名前で置き場に置く。
- 形を変えるときは、置き場の接頭辞ごと新しくして作り直す。古いものは消さない。

## 読む

- 木を読むときは、いつも `latest`（今の `main` の SHA）を読み、次に、その SHA のスナップショットを読む。
  - API で `revision` を指定されたら、その SHA のスナップショットを読む。
- 版と回答の中身も、その SHA のスナップショットを読む。
  - 版の差分（操作の復元）は、版のスナップショットの `changes` から作る（[操作と差分](README.md)）。
- コミットの記録の親をたどると、git なしで、次のものを求められる。
  - ノードの履歴：`changes` にそのノードがあるコミット（[ノードの履歴を読む](../api/endpoints/node/history.md)）
  - 対象ノードの変化：base から今の `main` までの `changes`（[反映の手順](merge.md)）
  - 引用元の変化：引用したリビジョンから今の `main` までの `changes`
  - リビジョンの並びにあるか：今の `main` から親をたどって、そのリビジョンに着くか

## 作る

| 経路 | 作るもの | いつ |
|---|---|---|
| バックエンド | 自分が作ったコミット（最初のリビジョン、版、回答、反映）のスナップショット | コミットを push した直後（[反映の手順](merge.md)） |
| worker | 反映によらずに `main` に入ったコミットのスナップショット | `main` が push されたとき（[worker](worker.md)） |

- 親のスナップショットに、そのコミットで変わったファイルだけを当てはめて作る。
  - なぜ：変わったファイルだけを git から読めば足り、clone の量が増えないから。
- 親のスナップショットがなければ、先に親のものを作る。最初のリビジョンまでさかのぼってもなければ、`tree/` を全部読んで作る。
- バックエンドは、push の直後に、自分でスナップショットと `latest` を置く。
  - なぜ：書いた直後に読んでも、古い木が返らないようにするため。

## latest

- `latest` は、今の `main` の SHA と、これまでの force push の記録を持つ。
- `latest` は、[スナップショットの置き場](ports/snapshot-store.md) の「`latest` を条件付きで書く」で書く。
  - 書く前に、新しい SHA のスナップショットを置き終えておく。
  - なぜ：`latest` が指すスナップショットが、いつも読めるようにするため。
- 今の `latest` が新しい SHA の親をたどった先にあれば、新しい SHA で上書きする。
- 新しい SHA の親をたどった先に今の `latest` がなければ、どちらかである。
  - 今の `latest` のほうが新しい（新しい SHA の子孫である）：書かない。
  - どちらの子孫でもない：force push である。git の今の `main` と同じなら上書きし、force push として記録する。

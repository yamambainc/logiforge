# スナップショット

バックエンドが読む木と、そのコミットの記録の形を確かめるときに読む。
作るのは [worker](worker.md) だけで、バックエンドは読むだけである。

## 考え方

- スナップショットは、あるコミットの木を解析したものである。読むためだけにある。
  - 正本は、今までどおり git の `main` である（[木のファイル配置](../files/README.md)）。
  - スナップショットは、git からいつでも作り直せる。
- git のファイルを解析して木にするのは、worker だけである。
  - バックエンドは、git のファイルを読まない。木を読むのも、反映の検査も、スナップショットの上で行う。
  - なぜ：git に触れるものを worker の 1 つにし、バックエンドがデータを保持しないようにするため（[worker](worker.md)）。
- コミットの SHA ごとに 1 つ作る。中身は変えない。上書きも削除もしない。
  - なぜ：SHA で引けば、いつ読んでも同じ中身なので、キャッシュを置くときに、そのままキャッシュできるから。

## 中身

スナップショットは、コミットの記録と、木の 2 つに分けて置く。

コミットの記録（数 KB）：

| 項目 | 内容 |
|---|---|
| `revision` | コミットの SHA |
| `parent` | first-parent のコミットの SHA。最初のリビジョンでは null |
| `number` | `main` のコミットだけ。最初のリビジョンを 1 とする、first-parent の番号 |
| `kind` | `main`（`main` のコミット）、`version`（版）、`answer`（回答） |
| `committed_at` | コミットの時刻 |
| `trailers` | コミットの trailer（[記録の形式](../files/revisions.md)） |
| `signed` | 署名が正しいか |
| `changes` | `parent` から変わったもの。ノードの識別子と、変わったファイルの種類（`hypothesis`、`background`、`verdict`、`story`、`inactivated`）の組 |

木：

| 項目 | 内容 |
|---|---|
| `nodes` | ノードごとの、ファイルの中身（git のファイルのバイトそのもの）と、計算した値・葉・要再検討・inactive。各ノードは、そのノードを変えた `main` のコミットの番号と SHA の一覧（下の「ノードの変更の一覧」）を持つ |
| `artifacts` | `artifacts/sha256/` にあるファイルの、sha256 と git の blob の SHA の組の一覧 |
| `history` | 最初のリビジョンからこのコミットまでの、`main` のコミットの一覧（番号の順）。各項目は、SHA、署名が正しいか、`Logiforge-Apply-Request:` の値を持つ |

- `main` のコミットの木は、すべてのノードを持つ。数百 KB から数 MB で、圧縮して置く。
  - 重くなったら、根の子の部分木ごとに分けて置く。今は分けない。
- 版と回答の木は、親からの差分だけを持つ。
  - なぜ：版と回答は、`main` よりずっと多く作られるから（[費用と規模の見積もり](../estimates.md)）。
- 値は、作るときに計算して入れる（[真偽値の伝播](../../docs/tree/propagation.md)）。
  - なぜ：読むたびに計算しないため。スナップショットは正本ではないので、値を持ってもファイルと食い違わない。
- artifact の中身は、スナップショットとは別に、sha256 の名前で置き場に置く。
- 形を変えるときは、置き場の接頭辞ごと新しくして作り直す。古いものは消さない。

## ノードの変更の一覧

- worker は、`main` のコミットのスナップショットを作るとき、変わったノードの一覧に、そのコミットの番号と SHA を足す。親のスナップショットの一覧は、そのまま引き継ぐ。
  - 「変わった」の範囲は、[対象ノードの変化](merge.md) のパスの決まりに従う。
- これにより、次のものを、1 つのスナップショットを読むだけで求められる。

| 求めるもの | 求め方 |
|---|---|
| ノードの履歴 | そのノードの一覧（[ノードの履歴を読む](../api/endpoints/node/history.md)） |
| 対象ノードの変化 | 対象ノードの一覧に、base の番号より大きい番号があるか（[反映の手順](merge.md)） |
| 引用元の変化 | 部分木のノードの一覧に、引用したリビジョンの番号より大きい番号があるか |
| リビジョンが `main` の並びにあるか | 今の `main` の木の `history` に、その SHA があるか |
| 反映によらない変更の警告 | 今の `main` の木の `history` の、署名が正しくない項目 |
| apply request が反映済みか | 今の `main` の木の `history` に、その識別子の項目があるか |

## latest

`latest` は、repository ごとに 1 つあり、次のものを 1 つにまとめて持つ。

| 項目 | 内容 |
|---|---|
| `main` | 今の `main` の SHA |
| `refs` | `refs/logiforge/` の下の ref と、それが指す SHA の一覧（ref の一覧） |
| `force_pushes` | これまでの force push の記録 |

- ref の一覧から、版の一覧と今の版（`head`）、回答のリビジョンがわかる（[apply request の作成と更新](apply-request.md)）。
- `main` と ref の一覧を 1 つにまとめるのは、読む側が、いつも同じ時点の組を見るようにするためである。
  - なぜ：別々に書くと、反映の直後に、`head` が消えたのに `main` がまだ古い間ができ、反映済みの提案が closed に見えるから。
- worker は、`latest` が指す SHA と ref のスナップショットを、すべて置き終えてから、`latest` を書く。
  - そのため、`latest` に出ている `main`、版、回答には、いつもスナップショットがある。
- 新しい `main` のコミットの記録の親をたどった先に、今の `latest` の `main` があるときだけ、`latest` を書く。`main` が同じときも書ける。
  - なぜ：worker が誤って 2 つ動いても、`main` が古い SHA に戻らないようにするため。
  - 置き場が条件付きの書き込みを持つなら、それでも守る。ref の一覧が古いものに戻ることも防げる（[スナップショットの置き場](ports/snapshot-store.md)）。
  - worker は 1 つだけ動かす（[worker](worker.md)）。2 つ動くと、条件付きの書き込みのない置き場では、ref の一覧が短い間だけ古くなることがある。
- 親をたどった先に今の `latest` の `main` がなく、新しい SHA が git の今の `main` なら、force push である。上書きし、force push として記録する。
- worker は、`latest` がある repository の名前の一覧を、置き場の `repositories` に書く。
- なぜ置き場に書くか：バックエンドが、git を読まずに、版と repository の一覧を知れるようにするため。どれも git から求めたものである。

## 読む

- バックエンドは、木を読むとき、`latest` を読み、次にその `main` の SHA のスナップショットを読む。
  - API で `revision` を指定されたら、その SHA のスナップショットを読む。
  - その SHA のスナップショットがなければ、`not_found` を返す。API が返すリビジョンには、いつもスナップショットがある。worker が、書いてから応答するまでに作るからである。
- 版と今の版、回答のリビジョンは、`latest` の ref の一覧から読む。
- バックエンドは、読んだものを保持しない。読むたびに置き場から取る（[状態を持たない](README.md)）。
  - 置き場は、バックエンドから転送の費用なしで読める場所に置く（[スナップショットの置き場のアダプタ](../adapters/snapshot-store.md)）。

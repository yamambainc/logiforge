# スナップショット

バックエンドが読む木と、そのコミットの記録の形を確かめるときに読む。
作るのは [worker](worker.md) だけで、バックエンドは読むだけである。

## 考え方

- スナップショットは、あるコミットの木を解析したものである。読むためだけにある。
  - 正本は、今までどおり git の `main` である（[木のファイル配置](../files/README.md)）。
  - スナップショットは、git からいつでも作り直せる。
- サーバの側で git のファイルを解析して木にするのは、worker だけである。
  - バックエンドは、git のファイルを読まない。木を読むのも、反映の検査も、スナップショットの上で行う。
  - なぜ：clone を持つものを worker の 1 つにし、バックエンドがデータを保持しないようにするため（[worker](worker.md)）。
- コミットの SHA ごとに 1 つ作る。中身は変えない。上書きも削除もしない。
  - なぜ：SHA で引けば、いつ読んでも同じ中身なので、キャッシュを置くときに、そのままキャッシュできるから。

## 中身

- 形の正本は、`internal/snapshot` の Go の型である。このページには、項目の表だけを置く。
- 形には版（`format_version`）を持たせる。項目を足すときも、版を上げる。読むときに版を確かめる。

スナップショットは、コミットの記録と、木の 2 つに分けて置く。

- コミットの記録は、`main` のすべてのコミットと、ブランチの先頭のコミットに置く。
- `main` の木は、決まったコミットにだけ置く（下の「木を作るコミット」）。

コミットの記録（数 KB）：

| 項目 | 内容 |
|---|---|
| `revision` | コミットの SHA |
| `parent` | first-parent のコミットの SHA。最初のリビジョンでは null。`branch` では、base（`main` と分かれた点） |
| `number` | `main` のコミットだけ。最初のリビジョンを 1 とする、first-parent の番号 |
| `kind` | `main`（`main` のコミット）、`branch`（利用者が push したブランチの先頭） |
| `committed_at` | コミットの時刻 |
| `trailers` | コミットの trailer（[記録の形式](../files/revisions.md)） |
| `warnings` | `main` のコミットだけ。反映の記録がない（`Logiforge-Init:` のある最初の用意のコミットを除く）こと、このコミットで新しく破れた不変条件（ふだんの取り込みのときだけ。下の「取り込みの 2 つの形」）、worker が見つけた警告（重なり、`main` の書き換え）（[すること](worker.md)） |
| `changes` | `main` のコミットだけ。`parent` から変わったもの。ノードの識別子、変わったファイルの種類（`hypothesis`、`background`、`verdict`、`story`、`inactivated`）、ファイルのパスの組。git の diff-tree で変わったパスから、パスの形だけで求める（[ファイルの配置](../files/layout.md)）。木は組み立てない。パスは、検証結果が加わったコミットを探すのに使う |
| `paths` | `branch` のコミットだけ。base から変わったファイルのパスと、変わり方（`added`、`modified`、`deleted`） |

木：

| 項目 | 内容 |
|---|---|
| `nodes` | ノードごとの、ファイルの中身（git のファイルのバイトそのもの）と、計算した値・葉・要再検討・inactive。各ノードは、そのノードを変えた `main` のコミットの番号と SHA の一覧（下の「ノードの変更の一覧」）を持つ |
| `artifacts` | `artifacts/sha256/` にあるファイルの一覧。各項目は、sha256、blob の SHA、大きさを持つ。中身は持たない |
| `other` | どのノードにも artifact にも当たらないファイル（木の外のファイルなど）。元のファイルの一覧を、そのまま戻すために持つ |
| `history` | 最初のリビジョンからこのコミットまでの、`main` のコミットの一覧（番号の順）。各項目は、SHA、`Logiforge-Apply-Request:` の値、反映の記録がないか、新しく破れた不変条件があるか、worker が見つけた警告（重なり、`main` の書き換え）があるかを持つ |
| `broken` | この木で破れている不変条件のすべて（前のコミットから破れているものを含む） |

- ノードのファイルは、git のファイルのバイトと、blob の SHA を持つ。
  - なぜ：バックエンドが、スナップショットから元のファイルの一覧に戻し、[差分の検査](checks.md) に渡すため。

ブランチの木（差分）：

| 項目 | 内容 |
|---|---|
| `base` | base（`main` と分かれた点）の SHA |
| `entries` | 変わったパスごとの、変わり方、base での blob の SHA（`base_sha`）、先頭でのファイル（消えたときはなし） |

- バックエンドは、今の `main` のスナップショットに、ブランチの差分を重ねて、反映の直前の検査をする。
  - 差分が変えたパスが、`base_sha` のあとに `main` でも変わっていれば、重ねられない。git の merge でも衝突するものとして、`conflict` にする（[衝突](merge.md)）。

- `main` の木は、すべてのノードを持つ。数百 KB から数 MB で、圧縮して置く。
  - 重くなったら、根の子の部分木ごとに分けて置く。今は分けない。
- ブランチの木は、base からの差分だけを持つ。
  - なぜ：版は、`main` よりずっと多く作られるから（[費用と規模の見積もり](../estimates.md)）。
- ブランチのスナップショットは、コミットの SHA ごとに作る。版になるかどうかに関わらない。
- 値は、作るときに計算して入れる（[真偽値の伝播](../../docs/tree/propagation.md)）。
  - なぜ：読むたびに計算しないため。スナップショットは正本ではないので、値を持ってもファイルと食い違わない。
- artifact の中身は、スナップショットとは別に、sha256 の名前で置き場に置く。
- 形を変えるときは、置き場の接頭辞ごと新しくして作り直す。古いものは消さない。

## 木を作るコミット

worker が `main` の木を作るのは、次のコミットだけである。

| コミット | 作るとき |
|---|---|
| 今の `main`（`latest`） | `main` が進んだとき。`latest` を書く前に作る |
| ブランチの base（`main` と分かれた点） | ブランチの先頭のスナップショットを作るとき。バックエンドは、base の木にブランチの差分を重ねて検査する |
| API で指定された、過去のリビジョン | バックエンドに頼まれたとき（[worker の内部 API](worker-api.md) の「木を作る」） |

- 一度作った木は、SHA で引いて使い回す。古い `latest` の木も消さない。
- なぜ、すべてのコミットに木を作らないか：木を作るには、そのコミットのすべてのファイルを読み、組み立てる必要がある。すべてのコミットに作ると、コミットの数と木の大きさの積の時間と容量がかかる（[費用と規模の見積もり](../estimates.md)）。
- 木の `history` とノードの変更の一覧は、そのコミットまでのものである。最初のリビジョンからそのコミットまでのコミットの記録を、順に重ねて求める。

## 取り込みの 2 つの形

worker は、`main` の新しいコミットを、次のどちらかで取り込む。

| 形 | いつ | すること |
|---|---|---|
| ふだんの取り込み | 前の `latest` の木があり、新しいコミットが少ない（20 以下） | 前の `latest` の木のファイルに、コミットごとの差分を重ね、新しく破れた不変条件を確かめて、コミットの記録の警告にする。最後のコミットの木を、重ねたファイルから作る |
| 初めての取り込み | 前の木がない。または、新しいコミットが多い（まとめて push されたときなど） | コミットの記録を、順に作るだけにする。最後に、今の `main` の木を 1 回だけ作る |

- 初めての取り込みでは、途中のコミットの「新しく破れた不変条件」を判定しない。今の `main` の木の `broken` だけを持つ。
  - なぜ：判定には、コミットごとに木を組み立てる必要があるから。
  - 反映の記録がないこと、重なり、`main` の書き換えは、どちらの形でも警告にする。木を組み立てずに求められるからである。
- どちらの形でも、コミットの記録と、今の `main` の木（`history` とノードの変更の一覧）は、同じものになる。違うのは、途中のコミットの「新しく破れた不変条件」だけである。

## ノードの変更の一覧

- worker は、`main` のコミットの記録を作るとき、変わったノードの一覧に、そのコミットの番号と SHA を足す。
  - 「変わった」の範囲は、[対象ノードの変化](merge.md) のパスの決まりに従う。inactive 化の子孫は、それまでに見たノードのディレクトリのうち、そのストーリーのディレクトリの下にあるものである。
  - 一覧は、コミットの記録の `changes` を、最初のリビジョンから順に重ねて求める。ふだんは、前の `latest` の木の一覧に、新しいコミットの分だけを足す。
- 木は、そのコミットまでの一覧を持つ。これにより、次のものを、1 つの木を読むだけで求められる。

| 求めるもの | 求め方 |
|---|---|
| ノードの履歴 | そのノードの一覧（[ノードの履歴を読む](../api/endpoints/node/history.md)） |
| 対象ノードの変化 | 対象ノードの一覧に、base の番号より大きい番号があるか（[反映の手順](merge.md)） |
| 引用元の変化 | 部分木のノードの一覧に、引用したリビジョンの番号より大きい番号があるか |
| リビジョンが `main` の並びにあるか | 今の `main` の木の `history` に、その SHA があるか |
| 反映によらない変更と、不変条件の警告 | 今の `main` の木の `history` の、警告がある項目 |
| apply request が反映済みか | 今の `main` の木の `history` に、その識別子の項目があるか |

## latest

`latest` は、repository ごとに 1 つあり、今の `main` の SHA を持つ。

- worker は、`main` のコミットの記録と木を置き終えてから、`latest` を書く。
  - そのため、`latest` が指す `main` には、いつも木がある。
- 新しい `main` のコミットの記録の親をたどった先に、今の `latest` があるときだけ、`latest` を書く。
  - なぜ：worker が誤って 2 つ動いても、`main` が古い SHA に戻らないようにするため。
  - 置き場が条件付きの書き込みを持つなら、それでも守る（[スナップショットの置き場](ports/snapshot-store.md)）。
- 親をたどった先に今の `latest` がなく、新しい SHA が git の今の `main` なら、`main` が書き換えられている。上書きし、新しい `main` のコミットの警告（`main_rewritten`）として記録する。
- 読んだあとに `latest` が書き換えられていたら（worker が 2 つ動いている）、書かない。
- worker は、`latest` がある repository の名前の一覧を、置き場の `repositories` に書く。

## ブランチの履歴

- worker は、ブランチごとに、先頭のコミットが変わった順の一覧を、置き場の `keep/<repository>/branches/<ブランチの名前>` に書く（[スナップショットの置き場](ports/snapshot-store.md)）。
  - 各項目は、先頭のコミット、base、見つけた時刻を持つ。ブランチが消えたときは、消えたことを足す。
  - 一覧に足すのは、スナップショットを作り終えたコミットだけである。そのため、一覧に出ている版には、いつもスナップショットがある。
- apply request の版は、この一覧から求める（[版](apply-request.md)）。
- 反映は squash merge なので、版のコミットは `main` から辿れない。ブランチを消すと、git からも辿れなくなる。
  - 版のスナップショットとブランチの履歴は、worker が置き場に残し、消さない。そのため、反映や close のあとも、版の差分とレビューした版を読める。
  - GitForge も、pull request の最後の版のコミットを ref に残す（[アダプタ](../adapters/README.md)）。途中の版は、置き場にしか残らない。
- ブランチの履歴と、消えたブランチの版のスナップショットは、git から作り直せない。置き場のうち、ここだけはバックアップを取る（[組み合わせ](../adapters/README.md)）。

## 読む

- バックエンドは、木を読むとき、`latest` を読み、次にその `main` の SHA のスナップショットを読む。
  - API で `revision` を指定されたら、その SHA の木を読む。
  - その SHA の木がなければ、worker に作らせる（[worker の内部 API](worker-api.md) の「木を作る」）。上限まで待ち、過ぎたら `snapshot_pending` を返す。
  - その SHA のコミットの記録もなければ、`snapshot_pending` を返す（[書いた直後の読み](../api/writes.md)）。まだ取り込まれていないのか、git にもない SHA なのかは、区別しない。バックエンドは git を読まないからである。
- 版は、ブランチの履歴から読む。
- バックエンドは、読んだものを保持しない。読むたびに置き場から取る（[状態を持たない](README.md)）。
  - 置き場は、バックエンドから転送の費用なしで読める場所に置く（[スナップショットの置き場のアダプタ](../adapters/snapshot-store.md)）。

# 計算

バックエンドが、スナップショットと GitForge から読んだやりとりから、何をどう計算するかを確かめるときに読む。
要件は [真偽値の伝播](../../docs/tree/propagation.md) と [着手できる作業](../../docs/work/README.md) が正本である。

## 計算

バックエンドは、次のものを [スナップショット](snapshot/README.md) と、GitForge から読んだやりとりから計算する。

- 値と、葉・要再検討・inactive
  - worker がスナップショットを作るときに計算して入れたものを、そのまま使う。
- 引用元の変化
  - 有効な検証結果の部分木の引用ごとに、部分木のノードの `last_changed` の番号に、[引用した時点](../files/revisions.md#引用した時点)の番号より大きいものがあるかを見る（[ノードを変えたコミット](snapshot/main.md#ノードを変えたコミット)）。
  - 引用した時点は、検証結果のファイルの `added` の番号である。`added` がなければ、変化したものとみなす。
- 反映したあとの姿
  - open の apply request の先頭のコミットの差分を、向き先の今の先頭のスナップショットツリーに重ねて、木と値を求める。重ね方、衝突の扱い、保持しないことは、[向き先に重ねる](snapshot/branch.md#向き先に重ねる) に書く。
- 着手できる作業（下の「着手できる作業」）
- 作業の終わりの判定（下の「作業の終わりの判定」）

## 着手できる作業

- 木の作業は、スナップショットツリーから計算する。
- 向き先が `main` でない apply request は、作業に数えない（[向き先](apply-request/target.md)）。
- apply request と人への依頼の作業は、[ブランチの履歴](snapshot/branch.md#ブランチの履歴) と、GitForge から読んだ apply request、レビュー、人への依頼から計算する。

### apply request の対象ノード

- open の apply request の対象ノードは、先頭のコミットの差分のファイルのパスを含む、今のスナップショットツリーのいちばん近いノードである。
  - 新しいストーリーは、親の仮説
  - `inactivated.md` は、そのストーリー
  - 検証結果と背景情報は、その仮説
- 先頭のコミットのスナップショットがなければ、対象ノードはないものとする。

### レビュー待ちと修正待ち

- レビュー待ちと修正待ちは、向き先が `main` の open の pull request のラベルで決める（[レビュー待ちと修正待ちのラベル](../adapters/pull-requests.md#レビュー待ちと修正待ちのラベル)）。review は読まない。
- 修正待ち：`request changes` の review か、opener が直すべき理由（`stale_target`、`invariant_violation`、`conflict`）での反映の失敗のあと、opener が直し終えたと申告するまで。
- レビュー待ち：修正待ちでないもの。`approve` のあと、そのほかの理由（`snapshot_pending` など）で反映に失敗し、`approve` し直しを待つものも含む。
  - 向き先が `main` でないあいだに `approve` され、あとで向き先を `main` に戻したときも、これに当たる（[向き先](apply-request/target.md)）。
- [着手できる作業](../../docs/work/README.md) の「反映に失敗して `open` に戻った」は、opener が直すべき失敗のことである。

### 回答済みの人への依頼

回答済みの人への依頼は、次のどちらかで作業から外す。

- その回答を引用した検証結果が、次のどちらかにある。
  - 今の `main` のスナップショットツリー
  - open の apply request（向き先が `main` でないものも含む）の先頭のコミットの差分の検証結果のファイル
    - 向き先が `main` でないものも含めるのは、積み上げた変更は、いずれ `main` 向きの apply request に含まれるからである。
- 対象ノードを最後に変えた反映のコミットが、回答より後である。
  - 反映のコミットは、対象ノードの `last_changed` から `previous` をたどり、worker の反映かの判定で反映によるものと決まった最初のコミットである（[ノードを変えたコミット](snapshot/main.md#ノードを変えたコミット)）。

- 引用とは、検証結果の artifact が、次のどちらかの URL の `link` であることである（[人への依頼の回答](../files/artifacts.md)）。
  - 回答の添付を読む API の URL（`getAnswerAttachment`。人への依頼の識別子と sha256 を含む）
  - 人への依頼を読む API の URL
  - なぜ URL だけか：URL が人への依頼の識別子を持つので、issue ごとにコメントを読まずに、引用かを決められるから。添付の sha256 だけで引用を決めると、作業の一覧で、回答のある issue ごとに添付を読むことになる。
- 背景情報など、検証結果でないファイルは見ない。

## 作業の終わりの判定

- 根拠部分木をスナップショットツリーから求め、上の着手できる作業のうち、根拠部分木にあるものを数える。
- 対象ノードのわからない（worker が追いついていない）、向き先が `main` のレビュー待ち・修正待ちの apply request があれば、終わりとしない。

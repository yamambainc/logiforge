# apply request の作成と更新

バックエンドが、apply request の作成・更新・close と、人への依頼の起票・回答で、何をどの順に書くかを確かめるときに読む。
API の決まり（`Idempotency-Key` と識別子の作り方）は、[同じ要求の繰り返し](../api/writes.md) が正本である。反映は [反映の手順](merge.md) に書く。

## 版と ref

- 利用者は、木の git リポジトリを clone し、ファイルを変えてコミットし、ブランチを push する（[CLI](../cli/README.md)）。
- 版は、そのブランチのコミットを取り込んだものである。
  - 版の差分は、そのコミットと `main` の分かれた点（base）からの差分である。ブランチの途中のコミットは見ない。
- 版の正本は、git の ref である。プロバイダには、版を記録しない。
  - `refs/logiforge/apply-requests/<識別子>/<版の番号>`：各版の記録（下の「版の記録」）
  - `refs/logiforge/apply-requests/<識別子>/head`：今の版の記録。open の間だけある
- 今の版は、`head` が指す版である。
- なぜ git の ref を正本にするか：ref の CAS だけで、更新・close・反映の取り合いを決められるから。ロックも、プロバイダへの記録の順も要らない。
- バックエンドは、版と今の版を、置き場の `latest` の ref の一覧から読む（[latest](snapshot.md)）。git は読まない。

## 版の記録

- 版の ref は、利用者のコミットを指す、注釈付きのタグ（git の tag オブジェクト）を指す。
  - タグには、版を取り込んだ API の呼び出しのセッション、apply request の識別子、版の番号、base を書き、worker が署名する（[記録の形式](../files/revisions.md)）。
- 利用者のコミットは、書き換えない。
  - なぜ：書き換えると SHA が変わり、利用者の手元のブランチと合わなくなるから。
- 利用者のコミットの trailer は、信じない。版を書いたセッションは、タグから読む。
  - なぜ：利用者は、コミットの trailer を自由に書けるから。

## 状態

提案の状態は、git から決め、次の順に判定する。

1. 今の `main` のスナップショットの `history` に、その提案の項目があれば、`merged`
2. `latest` の ref の一覧に `head` がなければ、`closed`
3. それ以外は、`open`

- close の理由と、close したセッションは、プロバイダの記録から読む。
- なぜ git から決めるか：書き込みの正本が git の ref の CAS なので、プロバイダへの記録が途中で止まっても、状態が食い違わないから。

## ブランチを取り込む

作成と更新は、どちらも次の手順でブランチを取り込む。

1. [worker の内部 API](worker-api.md) の「ブランチを読む」で、ブランチの先頭のコミットと base を求め、そのスナップショットを作ってもらう。
   - 要求に `revision` があり、ブランチの先頭と違えば、`validation_failed` で受け付けない。
2. スナップショットの差分に、[差分の検査](checks.md) を行う。4 種類の操作として読めない変化があれば、`validation_failed` で受け付けない。
3. worker の内部 API の「版を書く」で、版の記録を書く（下の「作成」「更新」の ref と期待する値）。

- バックエンドは、git のファイルを読まない。解析は worker が行い、バックエンドはスナップショットの上で検査する。
- 操作は、差分から復元して、応答に入れる（[操作と差分](README.md)）。

## 作成

1. 識別子を求める（[同じ要求の繰り返し](../api/writes.md)）。
2. プロバイダで、その識別子の提案を読む。あれば、それを返して終わる。中身は比べない。
3. 上の「ブランチを取り込む」を行う。手順 3 では、`<識別子>/1` と `head` を、どちらもないことを期待して書く。
   - 「すでにある」で失敗したら、前の要求の作りかけである。手順 4 に進む。
4. プロバイダに、提案（識別子、説明欄、ブランチの名前）を記録する。
5. 応答する。

- 人への依頼の起票は、手順 2 のあと、プロバイダに記録して応答する。git には書かないので、待たない。

## 更新

1. 要求の、もとにした版の番号が、`latest` の今の版と同じかを確かめる。違えば `version_conflict` で受け付けない。
2. 上の「ブランチを取り込む」を行う。ブランチを指定しなければ、提案のブランチを使う。手順 3 では、次の 2 つを書く。
   - `<識別子>/<次の番号>`：ないことを期待する
   - `head`：もとにした版の記録を期待して、新しい版の記録に動かす
3. 手順 2 の書き込みが失敗したら、`version_conflict` で受け付けない。
   - 先に別の更新か、close か、反映が通っている。番号を進めて書き直すことはしない。なぜ：先に入ったものを知らないまま上書きすると、その書き込みが黙って失われるから。
   - クライアントは、今の版を読み直し、自分の書いたものかを確かめる（[apply request を更新する](../api/endpoints/apply-request/update.md)）。
4. 説明欄があれば、プロバイダに記録する。応答する。

## ブランチの掃除

- 反映や close のあとも、バックエンドと worker は、利用者のブランチを消さない。
  - なぜ：ブランチは利用者のものだから。版のコミットは、版の ref から辿れるので、ブランチを消しても失われない。
- 利用者は、要らなくなったブランチを、git で消す（`git push --delete`）。CLI は、反映を確かめたあとに消すコマンドを持つ（[CLI](../cli/README.md)）。

## close

1. `head` を、今の版のコミットを期待して消す。
   - 失敗したら、先に更新か反映が通っている。`version_conflict` で受け付けない。
   - `head` がすでになければ、close の送り直しか、反映済みである。今の状態を返す。
2. プロバイダに、close の理由とセッションを記録する。
3. 応答する。

## 回答

1. 回答のコミットを作り、`refs/logiforge/human-requests/<識別子>` を、ないことを期待して書く（[人への依頼の回答](../files/artifacts.md)）。
   - 「すでにある」で失敗したら、その回答のスナップショットを読む。本文と回答した利用者が同じなら送り直しとみなして手順 2 に進む。違えば `not_open` で受け付けない。
2. プロバイダに、回答（本文、回答した利用者、回答のリビジョン）を記録する。
3. 応答する。

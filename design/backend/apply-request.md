# apply request の作成と更新

バックエンドが、apply request の作成・更新・close と、人への依頼の起票・回答で、何をどの順に書くかを確かめるときに読む。
API の決まり（`Idempotency-Key` と識別子の作り方）は、[同じ要求の繰り返し](../api/writes.md) が正本である。反映は [反映の手順](merge.md) に書く。

## 版と ref

- 版の正本は、git の ref である。プロバイダには、版を記録しない。
  - `refs/logiforge/apply-requests/<識別子>/<版の番号>`：各版のコミット
  - `refs/logiforge/apply-requests/<識別子>/head`：今の版のコミット。open の間だけある
- 今の版は、`head` が指す版である。
- 版のコミットの親は、作るときの `latest` である。そのため、版のコミットの親が、反映の base になる。
- 版には、差分を書いたセッションと署名を記録する（[記録の形式](../files/revisions.md)）。
- なぜ git の ref を正本にするか：ref の CAS だけで、更新・close・反映の取り合いを決められるから。ロックも、プロバイダへの記録の順も要らない。
- バックエンドは、版と今の版を、置き場の [ref の一覧](snapshot.md) から読む。git は読まない。

## 状態

提案の状態は、git から決め、次の順に判定する。

1. 今の `main` のスナップショットの `history` に、その提案の項目があれば、`merged`
2. ref の一覧に `head` がなければ、`closed`
3. それ以外は、`open`

- close の理由と、close したセッションは、プロバイダの記録から読む。
- なぜ git から決めるか：書き込みの正本が git の ref の CAS なので、プロバイダへの記録が途中で止まっても、状態が食い違わないから。

## 版の中身を作る

- バックエンドは、`latest` の [スナップショット](snapshot.md) の上で、操作を当てはめる。
- 当てはめた結果に、[差分の検査](checks.md) を行う。
- 通れば、変わったファイルだけを、[木のファイル配置](../files/layout.md) の形に書き出し（serialize）、コミットにする。
  - バックエンドは、git のファイルを読んで解析しない。書き出す方向だけを持つ。
- コミットは、要求の中だけの、使い捨ての clone で作る。要求が終われば消す（[git アダプタ](../adapters/git.md)）。

## 作成

1. 識別子を求める（[同じ要求の繰り返し](../api/writes.md)）。
2. プロバイダで、その識別子の提案を読む。あれば、それを返して終わる。中身は比べない。
3. 版 1 のコミットを作り、`<識別子>/1` と `head` を、どちらもないことを期待して、1 回の atomic な push で書く。
   - 「すでにある」で失敗したら、前の要求の作りかけである。手順 4 に進む。
4. プロバイダに、提案（識別子と説明欄）を記録する。
5. worker を起こし、版が ref の一覧に出るまで待ってから応答する（[書いた直後の読み](../api/writes.md)）。

- 人への依頼の起票は、手順 2 のあと、プロバイダに記録して応答する。git には書かないので、待たない。

## 更新

1. 要求の、もとにした版の番号が、ref の一覧の今の版と同じかを確かめる。違えば `version_conflict` で受け付けない。
2. 次の番号の版のコミットを作る。
3. 次の 2 つを、1 回の atomic な push で書く。
   - `<識別子>/<次の番号>`：ないことを期待する
   - `head`：もとにした版のコミットを期待して、新しい版のコミットに動かす
4. 失敗したら、`version_conflict` で受け付けない。
   - 先に別の更新か、close か、反映が通っている。番号を進めて書き直すことはしない。なぜ：先に入ったものを知らないまま上書きすると、その書き込みが黙って失われるから。
   - クライアントは、今の版を読み直し、自分の書いたものかを確かめる（[apply request を更新する](../api/endpoints/apply-request/update.md)）。
5. 説明欄があれば、プロバイダに記録する。worker を起こし、新しい版が ref の一覧に出るまで待ってから応答する。

## close

1. `head` を、今の版のコミットを期待して消す。
   - 失敗したら、先に更新か反映が通っている。`version_conflict` で受け付けない。
   - `head` がすでになければ、close の送り直しか、反映済みである。今の状態を返す。
2. プロバイダに、close の理由とセッションを記録する。
3. worker を起こし、ref の一覧に出るまで待ってから応答する。

## 回答

1. 回答のコミットを作り、`refs/logiforge/human-requests/<識別子>` を、ないことを期待して書く（[人への依頼の回答](../files/artifacts.md)）。
   - 「すでにある」で失敗したら、その回答のスナップショットを読む。本文と回答した利用者が同じなら送り直しとみなして手順 2 に進む。違えば `not_open` で受け付けない。
2. プロバイダに、回答（本文、回答した利用者、回答のリビジョン）を記録する。
3. worker を起こし、ref の一覧に出るまで待ってから応答する。

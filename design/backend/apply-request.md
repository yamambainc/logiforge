# apply request の作成と更新

バックエンドが、apply request の作成・更新と人への依頼の起票で、版とやりとりをどの順に書くかを確かめるときに読む。
API の決まり（`Idempotency-Key` と識別子の作り方）は、[同じ要求の繰り返し](../api/README.md) が正本である。

## 版

- 版は、[木の読み書き](ports/tree-read-write.md) の「リビジョンを作る」で作る。
  - 親は、作るときの `main` である。そのため、版のコミットの親が、[反映の手順](merge.md) の base になる。
  - 版には、差分を書いたセッションと署名を記録する（[記録の形式](../files/revisions.md)）。
- 今の版は、やりとりに記録された版のうち、番号が最大のものである。
- 新しい版の番号は、今の版の番号に 1 を足したものである。
- 書く順は、どの書き込みでも、ref、スナップショット、やりとりの順にする。
  - なぜ：やりとりに記録された版と回答には、いつもスナップショットがあるようにするため。読む経路で git を使わずに済む。

## ロックを取らない

- apply request と人への依頼への書き込みは、ロックを取らない。同じ repository の書き込みが、同時に走ってよい。
- 正しさは、名前の ref の「同じ名前のリビジョンがすでにある」で守る（[失敗の種類](ports/tree-read-write.md)）。
  - 同じ番号の版の ref は、1 つしか作れない。そのため、同じ番号の版を 2 つのセッションが同時に作っても、片方だけが通る。
  - 人への依頼の回答の ref も、1 つしか作れない。そのため、回答は 1 回だけになる。

## 作成

1. 識別子を求める（[同じ要求の繰り返し](../api/README.md)）。
2. やりとりで、その識別子の提案を読む。あれば、それを返して終わる。中身は比べない。
3. 「今の main を読む」で `main` を得て、それを親に、版 1 のリビジョンを作る。
   - 「同じ名前のリビジョンがすでにある」なら、前の要求の作りかけである。そのリビジョンを使う。
4. 版 1 のスナップショットを置く。
5. やりとりで、提案を作る。
   - プロバイダが「すでにある」と返したら、アダプタの送り直しの規則で、識別子とリビジョンを比べる（[独自フォージのアダプタ](../adapters/forge.md)）。

- 人への依頼の起票も、同じく手順 2 の読み直しを先に行う。版はない。
- アダプタの送り直しの規則は、手順 2 を通ったあとの、通信の送り直しのためだけにある。

## 更新

1. 要求の、もとにした版の番号が、今の版と同じかを確かめる。違えば `version_conflict` で受け付けない。
2. 次の番号で、新しい版のリビジョンを作る。親は、今の `main` である。
3. 新しい版のスナップショットを置く。
4. やりとりに、その番号の版を足す。

手順 2 が「同じ名前のリビジョンがすでにある」で失敗したら、同じ版をもとにした別の更新が、先にその番号を取っている。

- その ref のリビジョンのスナップショットを置き、やりとりに版として足す（まだなければ）。
  - なぜ：先に取った更新が、やりとりに記録する前に止まっていても、その版を失わないため。
- そのうえで、`version_conflict` で受け付けない。
  - 番号を進めて書き直すことはしない。なぜ：先に入った版を知らないまま上書きすると、その更新が黙って失われるから。
  - クライアントは、今の版を読み直し、自分の書いたものかを確かめる（[apply request を更新する](../api/endpoints/apply-request/update.md)）。

## 回答

- 人への依頼の回答の書き方は、[人への依頼の回答](../files/artifacts.md) に書く。
- やりとりの「回答を記録する」が「すでに回答がある」で失敗し、送り直しでもなければ、`not_open` で受け付けない。

# apply request の作成と更新

バックエンドが、apply request の作成・更新と人への依頼の起票で、版とやりとりをどの順に書くかを確かめるときに読む。
API の決まり（`Idempotency-Key` と識別子の作り方）は、[同じ要求の繰り返し](../api/README.md) が正本である。

## 版

- 版は、[木の読み書き](ports/tree-read-write.md) の「リビジョンを作る」で作る。
  - 版には、差分を書いたセッションと署名を記録する（[記録の形式](../files/revisions.md)）。
- 今の版は、やりとりに記録された版のうち、番号が最大のものである。
  - 番号には、抜けが出ることがある（下の「更新」の手順 2）。そのため、版の数では数えない。
- 新しい版の番号は、今の版の番号に 1 を足したものである。

## 直列に行う

- apply request の作成・更新・レビュー・close と、人への依頼の起票・回答は、[反映](merge.md) と同じく、repository ごとに 1 件ずつ直列に行う。
  - なぜ：同じ apply request への書き込みが同時に走らなければ、版の番号の取り合いを考えずに済むから。
  - なぜ：バックエンドは 1 つのプロセスで動くので、プロセスの中の排他で足りるから（[制約](server-state.md)）。

## 作成

1. 識別子を求める（[同じ要求の繰り返し](../api/README.md)）。
2. やりとりで、その識別子の提案を読む。あれば、それを返して終わる。中身は比べない。
3. 版 1 のリビジョンを作る。
   - 「同じ名前のリビジョンがすでにある」なら、前の要求の作りかけである。番号を進めず、そのリビジョンを使う。
4. やりとりで、提案を作る。
   - プロバイダが「すでにある」と返したら、アダプタの送り直しの規則で、識別子とリビジョンを比べる（[独自フォージのアダプタ](../adapters/forge.md)）。

- 人への依頼の起票も、同じく手順 2 の読み直しを先に行う。版はない。
- アダプタの送り直しの規則は、手順 2 を通ったあとの、通信の送り直しのためだけにある。

## 更新

1. 要求の、もとにした版の番号が、今の版と同じかを確かめる。違えば `version_conflict` で受け付けない。
2. 新しい版のリビジョンを作る。
   - 「同じ名前のリビジョンがすでにある」なら、前に止まった更新の残りである。番号を進めて作り直す（[失敗の種類](ports/tree-read-write.md)）。
3. やりとりに、その番号の版を足す。

## 回答

- 人への依頼の回答の書き方は、[人への依頼の回答](../files/artifacts.md) に書く。
- やりとりの「回答を記録する」が「すでに回答がある」で失敗し、送り直しでもなければ、`not_open` で受け付けない。

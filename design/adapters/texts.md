# review と issue の本文

GitHub アダプタと Forgejo アダプタが、review、pull request のコメント、issue に、何を書き、どこを読むかを確かめるときに読む。
どの GitForge の機能に対応させるかは、[GitForge のポートを pull request と issue で実装する](pull-requests.md) に書く。

- 本文に書くものは、GitForge の画面で人が読める、ふつうの文である。機械が読む行（`<名前>: <値>`）も、署名も書かない。
  - なぜ：状態は GitForge の機能（pull request、review、issue の状態と作者とラベル）で表すから（[信頼の境界](pull-requests.md#信頼の境界)）。
- バックエンドは、本文を読まない。例外は、人への依頼の issue のタイトルの頭（下の「人への依頼の issue」）だけである。

## review の本文

- 本文は、reviewer が書いた文である。
- client の review では、本文の最後に、使ったプロンプトの版を、人が読む文で書く（例：「プロンプトの版：abc1234」）。WebUI の review には書かない。
  - バックエンドは、この文を読まない。API でも、値としては返さない。
- 反映の失敗を書く pull request のコメントには、失敗の理由と詳しい説明を、人が読める文で書く。バックエンドは、このコメントを読まない。失敗の理由は、commit status で読む。

## close のコメント

- バックエンドを通して close するときは、close の直前に、close する主体のトークンで、pull request にコメントを書く。コメントは、close の理由を書いた、人が読む文である（例：「閉じた理由：作り直す」）。
  - バックエンドは、このコメントを読まない。API でも、値としては返さない。
- close した主体は、GitForge が記録する、pull request を閉じた人である。

## 人への依頼の issue

- タイトルは、対象ノードの識別子で始め、そのあとに要約を書く（例：「h-abc12 について：測ってください」）。
  - バックエンドは、タイトルの頭の、「 について：」の前を、対象ノードの識別子として読む。
  - なぜタイトルか：issue の一覧に入っているので、一覧の読みで、依頼ごとに GitForge を呼ばずに対象ノードが分かるから。人にも、どのノードへの依頼かが分かる。
  - タイトルは、Write を持つ主体が書き換えられる。書き換えられたら、その依頼は、違うノードへの依頼に見える（[信頼の境界](pull-requests.md#信頼の境界)）。
- 本文は、依頼の本文である。
- 依頼の種類は、ラベル（`logiforge/pvr`、`logiforge/decision`）で決める。起票した主体は、issue の作者である。
- タイトルが対象ノードの識別子で始まらないか、対象ノードが今の木にない依頼は、作業に出さず、一覧で警告する。

## 回答

- 回答は、回答した利用者のトークンで、issue にコメントを書き、続けて同じトークンで issue を close する。
  - 回答済みかは、issue が closed かで決める。
  - 回答は、issue を閉じた人が、閉じる前に書いた最後のコメントである。回答した利用者は、そのコメントの作者である。
  - なぜ close を使うか：回答済みかを、issue の一覧に入っている状態だけで決められるから。
- 回答の添付は、そのコメントの添付である（Forgejo）。GitHub では、リンクだけを本文に書く（[人への依頼の回答](../files/artifacts.md)）。
  - 添付の名前と sha256 は、本文に書かない。sha256 は、添付を読むときに、その中身から求める。
    - そのため、回答の添付の sha256 を求めるのは、その人への依頼を 1 件読むときと、添付を読むときだけである。一覧では求めない。
- issue が reopen されたら、回答されていないものとして扱う。

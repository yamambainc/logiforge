# 費用と規模の見積もり

複数人で使う構成（GitForge と静的ファイルストレージ）を、どれくらいの費用と規模で動かせるかを確かめるときに読む。
想定は、利用者とエージェントが数人から十数人、repository が数個から数十個である。

## 前提

- repository は 30 個、1 つの木のノードは 1,000 個ほどまでとする。
- 書き込み（apply request の作成と push、レビュー、close、起票、回答、反映）は、全体で 1 時間に 100 件ほどまでとする。
  - そのうち反映（`main` への push）は、1 日に数十件から 100 件ほどとする。
- 木を読む要求は、全体で 1 時間に 1 万件ほどまでとする。内訳は次のとおりである。
  - 外の仕組みが、作業の一覧と作業の終わりの判定を、動いている repository 10 個について、30 秒ごとに読む：1 時間 2,400 件
  - エージェント 10 人が、作業の前後に木やノードを読む：1 人 1 時間 400 件で 4,000 件
  - 利用者 10 人が、WebUI で木とノードを見る：1 人 1 時間 300 件で 3,000 件

## 制約：GitForge のレート制限は、今は考えない

- バックエンドは、やりとりと認証を、要求ごとに GitForge から読む。結果を保持しない（[状態を持たない](backend/README.md)）。
- そのため、多くの人とエージェントが頻繁に読むと、GitForge の API のレート制限に当たることがある。今は、これを考えない。
  - GitForge ごとの回数の見積もりは、下の「アダプタごとの見積もり」に書く。
- 当たるようになったら、次の 2 つで対処する。
  - worker が、やりとり（提案、レビュー、人への依頼）も静的ファイルに写し、バックエンドはそれを読む。GitForge を読むのは、repository ごとに 1 つの worker だけになる。
  - バックエンドが、短い期限の署名付きのトークンを発行し、認証の問い合わせを、期限ごとに 1 回にする。

## worker

- worker は、小さな常駐のコンテナ 1 つで足りる。
  - 仕事は、変わった repository の fetch と、スナップショット、ブランチの履歴、`latest` を書くことである。git には書かない。
- clone は、artifact の中身を含むので、repository ごとに数十 MB から数百 MB である。
  - repository 30 個で、永続するストレージは、数 GB から 10 GB ほどである。
- 見回りの `git ls-remote` は、repository 30 個 × 1 秒ごとで、1 秒に 30 回、1 日に約 260 万回である。1 回数 KB（ブランチの数による）である。
  - GitForge の API の上限には数えないことが多いが、git の操作の、乱用を防ぐ制限には数える。
  - 間隔を 1 秒にするのは、push と書き込みが読む側に出るまでの遅れを短くするためである（[見回り](backend/worker.md#見回り)）。GitForge の制限に当たるなら、間隔を延ばす。延ばした分だけ、書き込みの API の応答が遅くなる。
- バックエンドは clone を作らないので、書き込みのたびの clone はない。

## スナップショットツリーを作る時間（測った値）

`bench/snapshot-tree` ブランチの `internal/bench`（`BENCH_SNAPSHOT_TREE=1`）で測った。

- 手元のマシン（AMD Ryzen Embedded R2514、8 スレッド、メモリ 11 GB）で、置き場は手元のディレクトリ（tmpfs）である。
- `main` のコミットは 1,000 個である。ノードは、コミットごとに 4 つ（ストーリー 1 つと仮説 3 つ、背景情報つき）増やし、目標の数に届いたあとは、背景情報に文章を足す。
- スナップショットツリーは、`history` とノードの変更の一覧を持つ、前の形で測った。

| ノード | 1 コミットの取り込み | うち git の読み | うち組み立てと検査 | うち圧縮 | 全体を読んで作る | 1,000 コミットの取り込み | 置き場の合計 |
|---|---|---|---|---|---|---|---|
| 97 | 51 ms | 14 ms | 20 ms | 16 ms | 41 ms | 46 秒 | 38 MiB |
| 997 | 178 ms | 15 ms | 109 ms | 53 ms | 165 ms | 155 秒 | 101 MiB |
| 3,997 | 464 ms | 14 ms | 322 ms | 127 ms | 440 ms | 280 秒 | 178 MiB |

- 1 コミットの取り込みは、1 つ前のスナップショットツリーのファイルに差分を重ね、スナップショットツリーを作り、圧縮して置くまでである（[すること](backend/worker.md#すること)）。
- 1 コミットあたりの時間は、木の大きさにほぼ比例する。
- 1,000 コミットの取り込みは、ノードが 1 個から目標の数まで増えながらの値である。最初から 4,000 個あれば、およそ 1,000 × 0.46 秒 ≈ 8 分である。
- 溜まったコミットに追いつくまでの時間は、溜まったコミットの数 × 1 コミットの時間である。ノード 1,000 個で 100 コミットなら、約 18 秒である。
- 想定（repository 30 個、1 つの木はノード 1,000 個ほど）なら、反映 1 回の取り込みは 0.2 秒ほどである。

## apply request の作成の時間（測った値）

E2E（`internal/e2e`）で、手元の Forgejo に対して測った。バックエンドが、作業用の git の複製から読んで検査する（[作成](backend/apply-request.md#作成)）。

| 木 | 初めての `ar create`（バックエンドの clone を含む） | 2 回目からの `ar create`（fetch だけ） |
|---|---|---|
| 小さい木（E2E の TestE2E） | 0.8 秒 | 1.0〜1.2 秒 |
| `main` のコミット 1,001、ノード 4,001（TestE2ELargeTree） | 1.3 秒 | 1.2 秒 |

- 大きい木の初めての `ar create` は、worker の初めての取り込みと重なっていた。置き場に base のスナップショットツリーがまだないので、base の木を作業用の複製から読んだ。それでも、worker を待たずに終わった。
- 作業用の複製は、repository ごとに、clone 1 つ分のディスクを使う（下の「worker」の clone と同じ大きさ）。バックエンドの一時的なディスクは、それに合わせる。

## スナップショットの大きさ

- 圧縮したスナップショットツリーの大きさ（上と同じ測り方の、先頭のコミットのもの）：

| ノード | 前の形 | `history` を外す | `history` とノードの変更の一覧を外す |
|---|---|---|---|
| 97 | 68 KiB | 40 KiB | 11 KiB |
| 997 | 154 KiB | 125 KiB | 83 KiB |
| 3,997 | 364 KiB | 335 KiB | 249 KiB |

- 前の形の大きさのほとんどは、コミットの数とともに伸びる `history` とノードの変更の一覧だった。今の形では、どちらも持たない（[スナップショット](backend/snapshot.md#中身)）。
  - かわりに各ノードが持つ `last_changed`（番号と SHA）は、ノードの数でしか伸びない。
  - そのため、スナップショットツリー 1 つの大きさは、木の大きさで決まり、コミットの数によらない。
- スナップショットツリーは、`main` のすべてのコミットに置く（[すべてのコミットに作る](backend/snapshot.md#すべてのコミットに作る)）。
  - 置き場の容量は、コミットの数 × スナップショットツリー 1 つの大きさである。ノード 1,000 個の木で反映 1,000 回なら、100 MB ほどである。
  - artifact の中身は、sha256 ごとに 1 つだけ置くので、コミットの数では増えない。
- ブランチのスナップショットは、base からの差分だけなので、1 つ数 KB から数十 KB である。
- コミットの記録は、1 つ数百 B から数 KB である。
- 古いスナップショットを消さないのは、引用と履歴で過去の SHA を読むからである。

## 読む量と費用

- バックエンドはキャッシュを持たないので、木を読む要求ごとに、`latest`（数 KB）と、`main` のスナップショットツリー（圧縮して数百 KB）を置き場から読む。
  - 木を読む要求が 1 時間 1 万件、1 回 1 MB なら、1 時間 10 GB、1 か月で 7 TB ほどである。
- 置き場は、バックエンドから転送の費用なしで読める場所に置く（[スナップショットの置き場のアダプタ](adapters/snapshot-store.md)）。
  - そうすると、かかるのは、読む回数の費用だけである。1 か月 700 万回で、数ドルほどである。
  - 転送に費用がかかる場所に置くと、7 TB で数百ドルになる。
- CDN は任意である。CDN からバックエンドへの転送は、多くの CDN でインターネットへの転送として費用がかかるので、費用を下げる手段にはならない。読むのが遅いことが問題になったときに置く。
- 重くなったら、スナップショットツリーを、根の子の部分木ごとに分けて置く。今は分けない（[スナップショット](backend/snapshot.md)）。

### 読む時間（測った値）

上の「スナップショットツリーを作る時間」と同じ測り方である。apply request の反映したあとの姿（[向き先に重ねる](backend/snapshot.md#向き先に重ねる)）は、ノード 4 つを足す差分で測った。

| ノード | 読んで展開する | 差分を重ねる | 木を組み立て、値を計算する | 反映したあとの姿の計 | 参考：操作の復元 |
|---|---|---|---|---|---|
| 97 | 14 ms | 0.1 ms | 4.5 ms | 19 ms | 9 ms |
| 997 | 64 ms | 1.0 ms | 45 ms | 110 ms | 91 ms |
| 3,997 | 252 ms | 9.3 ms | 265 ms | 527 ms | 522 ms |

- 読んで展開するのは、置き場から読み、gzip と JSON を解き、ファイルの一覧に戻すまでである。前の形（`history` とノードの変更の一覧を持つ）で測った。今の形では、読む量が減るので、これより短い。
- 木を読む要求は、どれも「読んで展開する」と「木を組み立て、値を計算する」がかかる。ノード 1,000 個で 0.1 秒、4,000 個で 0.5 秒ほどである。
  - 1 時間 1 万件なら、ノード 1,000 個の木で、平均 1 CPU の 3 割ほどである。

## アダプタごとの見積もり

### GitHub アダプタ

App のインストールの上限は、REST が 1 時間 5,000 回である（repository と利用者が増えると、12,500 回まで増える）。
主体のトークンの上限は、主体ごとに 1 時間 5,000 回である。

| 要求 | REST の回数 | 数える上限 |
|---|---|---|
| どの要求も（認証） | 2〜3 回（主体、team の所属、リポジトリの権限） | 主体ごと |
| 作業の一覧 | 3 回以上（open の PR と issue の一覧、repository のコメントの一覧）＋ open の PR ごとに 1 回（レビュー） | App |
| apply request を読む | 3 回（PR、PR のコメント、レビュー） | App |
| 木のノードを読む | 3 回以上（open の PR と issue の一覧、repository のコメントの一覧） | App |
| 書き込み | 1〜3 回（PR の作成・merge・close、レビュー、コメント、ラベル） | App |
| worker | 0 回（git だけを使う） | なし。git の操作の、乱用を防ぐ制限には数える |

- open の apply request が 50 件あると、作業の一覧 1 回で、App の REST を 50 回ほど使う。
  - 外の仕組みが、作業の一覧を repository 10 個について 1 分ごとに読むと、1 時間 3 万回ほどで、上限を超える。
  - 認証は、エージェントが 1 秒ごとに要求すると、主体ごとに 1 時間 7,000〜1 万回で、上限を超える。
- そのため、多くの人とエージェントが頻繁に読むと、GitHub の API のレート制限に当たる（[GitHub アダプタ](adapters/github.md)）。

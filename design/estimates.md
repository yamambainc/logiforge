# 費用と規模の見積もり

GitHub を使う構成を、どれくらいの費用と規模で動かせるかを確かめるときに読む。
想定は、利用者とエージェントが数人から十数人、repository が数個から数十個である。

## 前提

- 1 つの repository の木は、ノードが 1,000 個ほどまでとする。
- 書き込み（版の作成と更新、回答、反映）は、全体で 1 日に数百件までとする。
  - そのうち反映（`main` への push）は、1 日に数十件から 100 件ほどとする。

## GitHub Actions の時間

- worker は、`main` への push のたびに 1 回走る（[worker](backend/worker.md)）。
- 1 回は、スナップショットがあれば数十秒で終わる。GitHub Actions は、1 回ごとに分単位に切り上げて数える。
  - そのため、1 回あたり 1 分と見積もる。
- 反映が 1 日 60 件なら、1 か月で約 1,800 分である。private のリポジトリの無料枠（1 か月 2,000 分）に収まる。
- それを超えるときは、超えた分を支払うか、自前の runner で動かす。

## スナップショットの大きさ

- 1 つのスナップショットの木は、ノード 1,000 個で、背景情報とレポートを含めて 1〜5 MB ほどである。
- コミットの記録は、1 つ数 KB である。
  - 圧縮して置くと、数百 KB から 1 MB ほどになる。
- コミットごとに 1 つ置くので、反映 1,000 回の repository で、およそ 1 GB になる。
  - artifact の中身は、sha256 ごとに 1 つだけ置くので、コミットの数では増えない。
- 静的ファイルストレージの費用は、この量なら小さい。古いスナップショットを消さないのは、引用と履歴で過去の SHA を読むからである。

## 書き込みのたびの clone

- 書き込みのたびに、深さ 1 で、ファイルの中身を取らない clone を作る（[git アダプタ](adapters/git.md)）。
  - 取るのは、ディレクトリの構造（git の tree）と、変えるファイルだけである。
- ノード 1,000 個の木で、1 回に数百 KB ほどである。artifact の中身は取らないので、artifact が増えても変わらない。
- clone は、書き込みが終わったら消す。プロセスの台数と repository の数を掛けた数の clone は、持たない。

## 読む量

- 読むたびに、`latest`（数十バイト）と、SHA のスナップショット（数百 KB から数 MB）を読む。
- スナップショットは SHA ごとに変わらないので、プロセスのメモリにキャッシュする。`main` が進むまでは、`latest` だけを読む。
- ノードの履歴と引用元の変化は、コミットの記録の親をたどる。反映 1,000 回の repository では、最大で 1,000 個（数 MB）を読む。これもキャッシュする。

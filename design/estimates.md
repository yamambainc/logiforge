# 費用と規模の見積もり

複数人で使う構成（GitForge と静的ファイルストレージ）を、どれくらいの費用と規模で動かせるかを確かめるときに読む。
想定は、利用者とエージェントが数人から十数人、repository が数個から数十個である。

## 前提

- repository は 30 個、1 つの木のノードは 1,000 個ほどまでとする。
- 書き込み（版の作成と更新、レビュー、close、起票、回答、反映）は、全体で 1 時間に 100 件ほどまでとする。
  - そのうち反映（`main` への push）は、1 日に数十件から 100 件ほどとする。
- 木を読む要求は、全体で 1 時間に 1 万件ほどまでとする。内訳は次のとおりである。
  - 外の仕組みが、作業の一覧と作業の終わりの判定を、動いている repository 10 個について、30 秒ごとに読む：1 時間 2,400 件
  - エージェント 10 人が、作業の前後に木やノードを読む：1 人 1 時間 400 件で 4,000 件
  - 利用者 10 人が、WebUI で木とノードを見る：1 人 1 時間 300 件で 3,000 件

## 制約：GitForge のレート制限は、今は考えない

- バックエンドは、やりとりと認証を、要求ごとに GitForge から読む。結果を保持しない（[状態を持たない](backend/README.md)）。
- そのため、多くの人とエージェントが頻繁に読むと、GitForge の API のレート制限に当たることがある。今は、これを考えない。
  - GitForge ごとの回数の見積もりは、下の「アダプタごとの見積もり」に書く。
- 当たるようになったら、次の 2 つで対処する。
  - worker が、やりとり（提案、レビュー、人への依頼）も静的ファイルに写し、バックエンドはそれを読む。GitForge を読むのは、repository ごとに 1 つの worker だけになる。
  - バックエンドが、短い期限の署名付きのトークンを発行し、認証の問い合わせを、期限ごとに 1 回にする。

## worker

- worker は、小さな常駐のコンテナ 1 つで足りる。
  - 仕事は、変わった repository の fetch と、スナップショット、ブランチの履歴、`latest` を書くことである。git には書かない。
- clone は、artifact の中身を含むので、repository ごとに数十 MB から数百 MB である。
  - repository 30 個で、永続するストレージは、数 GB から 10 GB ほどである。
- 巡回の `git ls-remote` は、repository 30 個 × 1 分ごとで、1 日に約 43,000 回、1 回数 KB（ブランチの数による）である。GitForge の API の上限には数えないことが多いが、git の操作の、乱用を防ぐ制限には数える。
  - 間隔を 1 分にするのは、利用者の push を版として見つけるのが巡回だからである。遅れてよいなら、間隔を延ばす。
- バックエンドは clone を作らないので、書き込みのたびの clone はない。

## スナップショットの大きさ

- `main` のコミットの木は、ノード 1,000 個で、背景情報とレポートを含めて 1〜5 MB ほどである。
  - 圧縮して置くと、数百 KB から 1 MB ほどになる。
- ブランチの先頭の木は、base からの差分だけなので、1 つ数 KB から数十 KB である。
- コミットの記録は、1 つ数 KB である。
- `main` のコミットごとに 1 つ置くので、反映 1,000 回の repository で、およそ 1 GB になる。
  - artifact の中身は、sha256 ごとに 1 つだけ置くので、コミットの数では増えない。
- 古いスナップショットを消さないのは、引用と履歴で過去の SHA を読むからである。

## 読む量と費用

- バックエンドはキャッシュを持たないので、木を読む要求ごとに、`latest`（数 KB）と、`main` の木（圧縮して数百 KB から 1 MB）を置き場から読む。
  - 木を読む要求が 1 時間 1 万件、1 回 1 MB なら、1 時間 10 GB、1 か月で 7 TB ほどである。
- 置き場は、バックエンドから転送の費用なしで読める場所に置く（[スナップショットの置き場のアダプタ](adapters/snapshot-store.md)）。
  - そうすると、かかるのは、読む回数の費用だけである。1 か月 700 万回で、数ドルほどである。
  - 転送に費用がかかる場所に置くと、7 TB で数百ドルになる。
- CDN は任意である。CDN からバックエンドへの転送は、多くの CDN でインターネットへの転送として費用がかかるので、費用を下げる手段にはならない。読むのが遅いことが問題になったときに置く。
- バックエンドは、要求ごとに、圧縮した木を展開し、数 MB の JSON を読む。
  - 1 回あたり、数十ミリ秒と、1 CPU のその時間ほどである。1 時間 1 万件なら、平均で 1 CPU の 1 割ほどである。
- 重くなったら、木を、根の子の部分木ごとに分けて置く。今は分けない（[スナップショット](backend/snapshot.md)）。

## アダプタごとの見積もり

### GitHub アダプタ

App のインストールの上限は、REST が 1 時間 5,000 回である（repository と利用者が増えると、12,500 回まで増える）。
主体のトークンの上限は、主体ごとに 1 時間 5,000 回である。

| 要求 | REST の回数 | 数える上限 |
|---|---|---|
| どの要求も（認証） | 2〜3 回（主体、team の所属、リポジトリの権限） | 主体ごと |
| 作業の一覧 | 3 回以上（open の PR と issue の一覧、repository のコメントの一覧）＋ open の PR ごとに 1 回（レビュー） | App |
| apply request を読む | 3 回（PR、PR のコメント、レビュー） | App |
| 木のノードを読む | 3 回以上（open の PR と issue の一覧、repository のコメントの一覧） | App |
| 書き込み | 1〜3 回（PR の作成・merge・close、レビュー、コメント、ラベル） | App |
| worker | 0 回（git だけを使う） | なし。git の操作の、乱用を防ぐ制限には数える |

- open の apply request が 50 件あると、作業の一覧 1 回で、App の REST を 50 回ほど使う。
  - 外の仕組みが、作業の一覧を repository 10 個について 1 分ごとに読むと、1 時間 3 万回ほどで、上限を超える。
  - 認証は、エージェントが 1 秒ごとに要求すると、主体ごとに 1 時間 7,000〜1 万回で、上限を超える。
- そのため、多くの人とエージェントが頻繁に読むと、GitHub の API のレート制限に当たる（[GitHub アダプタ](adapters/github.md)）。

# 検証結果と引用

葉の仮説に、値と根拠をどう付けるかを確かめるときに読む。

## 検証結果

- 検証結果は、値（`true` または `false`）とレポートの、1 対 1 の組である。
  - レポートのない値は出せない。
  - なぜ：すべての値を、根拠から辿れるようにするため。
- 検証結果を出せるのは、葉の仮説だけである（[葉と検証結果](README.md)）。
- 検証結果は、[apply request](../apply-request/README.md) の `verdict.submit` で出す。
- 検証結果は差し替えられる。
  - 差し替えた検証結果も、ファイルとして木に残る。
  - いつ出され、いつ差し替えられたかは、`main` の履歴で辿る。
  - 1 つの検証結果で、同じ仮説の有効な検証結果を、まとめて差し替えられる。
    - なぜ：有効な検証結果が 2 つになった仮説（[反映](../apply-request/README.md) の確認と反映の間に起きうる）を、1 つの差分で直せるようにするため。
- inactive な部分木の中では、inactive になる前に葉だった仮説にだけ、検証結果を出せる。
  - なぜ：inactive にされた時点で進行中だった作業を、記録として残すため。
  - その値は、伝播しない（[inactive 化](inactive.md)）。
- 葉を直接検証してよいかの判断は、[論理レビューの審査観点](../apply-request/review-criteria.md) に書く。

## レポート

レポートには、次のものを含められる。

- 本文
- artifact
- 引用

## artifact

artifact は、レポートが参照する根拠物である。次のようなものがある。

- 参考文献からの引用とリンク
- プログラムと、その実行結果
- データ
- 人への依頼の回答（[人への依頼](../human-requests/README.md)）

artifact の置き方は、次の 2 種類だけである。

- ファイル：repository の git リポジトリに入れる、小さなファイル
- リンク：外の URL
  - 中身の sha256（ハッシュ値）を書いておけば、検証のときに照合する。

ファイルの大きさは、1 つあたり 10 MiB までにする。

- なぜ：PVR の回答に添えるスマートフォンの写真（数 MiB）を、そのままファイルにできるようにするため。
- なぜ：それ以上の大きさのファイルが増えると、git リポジトリのクローンが遅くなるため。

artifact の扱いは、次のとおり。

- artifact は、変更しない。
  - なぜ：検証をあとから再現できるようにするため。
- プログラムによる検証では、次のものを artifact として残す。
  - コード
  - 入力
  - 実行環境の情報
  - 出力

## 探索の対象の成果物

探索の対象の成果物とは、Logiforge で問いを探索しているプロジェクトが、最終的に作るもののことである。次のようなものがある。

- ソフトウェア開発では、そのソフトウェアのソースコードとテストコード
- 論文では、tex プロジェクトの中のファイル

探索の対象の成果物は、検証結果の根拠にしない。

- 例：開発中のソフトウェアのテストが通ったことを、根拠にしない。
- 例：書いている論文の本文に書いてあることを、根拠にしない。
- なぜ：Logiforge は、広い空間の探索結果を残して次へ進むためのツールである。探索の対象の成果物は、その探索結果を整理したものにすぎない。
  - 成果物を根拠にすると、探索の結果を、それを整理したもので裏付けることになり、順序が逆になる。

根拠には、探索の対象の成果物から独立したものだけを使う。次のようなものは根拠にできる。

- 検証のために別に書いた試作やプログラムと、その実行結果（[artifact](#artifact)）
  - 例：アルゴリズムの性質を確かめるために、成果物を使わずに別に書いた小さなプログラムとその出力
  - 検証のために作ったプログラムは、artifact に入れ、成果物とは別に残す。
- 文献
- データ
- 人への依頼の回答（[人への依頼](../human-requests/README.md)）
- ほかの仮説の artifact や部分木の引用（[引用](#引用)）

検証のために別に書いたプログラムでも、成果物を使うものは根拠にできない。

- 例：成果物のリポジトリにあるテストを、そのまま実行した結果
- 例：成果物のコードを import したり呼んだりする、別に書いたスクリプトの結果
- 例：成果物のファイルを読むスクリプトの結果（tex の表の数値を集めるなど）

そのため、成果物そのものの振る舞いについての仮説は、葉として直接は検証できない。

- 根や途中の仮説は、成果物についての主張でもよい。その値は、子ストーリーから決まる。
- 葉の仮説は、方法や性質についての主張として立てる。
- 例：「開発中の在庫管理サービスの引き当ては、在庫を超えない」ではなく、「在庫の行を SELECT … FOR UPDATE で読んでから引き当てれば、並行に引き当てても在庫を超えない」とする。

## 引用

レポートからは、次のものを引用できる。

- ほかの仮説の artifact
- 部分木

部分木は、根のノードの識別子だけで指す。

- 引用できるのは、apply request の先頭のコミットの木にあるノードである。
  - 同じ apply request で加えるノードも引用できる。
- 引用した時点は、その検証結果が反映された `main` のコミットである。
  - なぜ：反映のコミットは git の履歴に残り、あとから変わらないから。引用する人が、コミットを選んで書かずにすむ。
- 引用した時点の部分木は、そのコミットの木の部分木である。
  - なぜ：引用したときの根拠を、あとからそのまま辿れるようにするため。

引用できるのは、同じ repository の中のものだけである。

- ほかの repository から移した repository では、移した検証結果の引用した時点は、移したときである。

## 流用

検証済みの仮説 X を、別のストーリーで使いたいときは、次のようにする。

1. 新しいストーリーの下に、新しい仮説 X′ を作る。
2. X′ に、X の部分木を引用するだけのレポートを付けて、true の検証結果を出す。
   - X が葉なら、X の検証結果を引用する。
   - X が葉でなければ、X を true にしている子ストーリーの配下にある検証結果を引用する。

流用は、引用の使い方の 1 つであり、特別な仕組みではない。

## 引用元の変化

引用元の変化とは、引用した時点のあとに、引用している部分木の中で、次のどちらかが起きることをいう。

- 検証結果の差し替え
- ストーリーの inactive 化

引用元が変化しても、引用している仮説の値は、自動では変えない。

- なぜ：引用元の変化が結論に影響するかどうかは、判断が要るから。

見直して値を変える必要がなかったときも、検証結果を出し直すと、引用元の変化は解消する。

## 対応しないこと

- repository をまたぐ引用
  - ほかの repository の根拠を使いたいときは、その中身を artifact に含めて参照する。
- 10 MiB を超えるデータの保管と配布
  - 利用者やエージェントが別の場所で管理し、リンクの artifact で参照する。
  - なぜ：大容量データの保管と配布は Logiforge の責務の外。仕組みを持つと、ポート・アダプタ・秘密情報・掃除が増えるため。

# 仮説検証ハーネス 要件定義書

- 版: v0.2（レビューを反映したドラフト）
- 日付: 2026-11-11
- 対象: 研究など不確実性の高い問いに取り組むための、エージェント常駐型・仮説検証ハーネス
- 本書の扱い: 概要説明用 HTML（`index.html`）の原稿を兼ねる。改訂はこの Markdown を正とする。

### v0.2 の主な変更
- 仮説を inactive にするときの規則（C-11）を追加した。親ストーリーごと inactive にすることを必須とし、「active なストーリーの子仮説はすべて active」が常に成り立つようにした。inactive にした子仮説が AND の計算から外れ、ストーリーが誤って true になるのを防ぐため。作り直しは、新しい兄弟ストーリーで行う。
- 要再検討フラグの条件を絞った。また、まだ子ストーリーを一度も持っていない状態を unexpanded として分けた。
- `conclude_false` は、直接の反証があるときに限った。代わりの道筋が尽きただけの場合は exhausted として owner に上げる。
- inactive な終端仮説にも検証結果を出せるようにした（値は記録として残すが、伝播はしない）。
- 終端解除をするときは、同じ AR の中で Verdict を失効させることにした。流用は、部分木を固定して引用する形にした。停止条件を見直した。

## 1. 背景と目的

### 1.1 背景
研究のように答えが分からない問いに取り組むとき、人もエージェントも「問いを仮説に分ける → 仮説を検証できる大きさまで分ける → 検証する → 外れたら別の道を探す」を繰り返している。ただ、この過程は普通、会話やメモの中に散らばっていて、

- どの仮説がどの論理でどの問いを支えているのか、
- どの結論がどの根拠に基づくのか、
- 偽になった仮説の影響がどこまで及ぶのか、

を後から辿れない。

### 1.2 目的
**構造化データ（仮説とストーリーの木）と非構造化データ（レポート・artifacts）を組み合わせ、再帰的に回し続けられる環境**を作り、そこにエージェントを常駐させる。具体的には次の 4 つ。

1. 究極的な問いを根とする「仮説—ストーリー」の木を、規則付きのデータ構造として管理する。
2. 末端の仮説だけを検証すれば、上位の真偽が自動的に決まるようにする。
3. すべての変更を Apply Request（opener / reviewer）で審査し、履歴として残す。GitHub に近い仕組みだが、管理対象がファイルだけでなく**規則付きの木構造**である点が違う。
4. エージェントは CLI、人間は WebUI で同じ基盤を操作し、計算機の中では検証できない問いは人間に物理検証を依頼できるようにする。

### 1.3 スコープ
| 対象内 | 対象外（本書では扱わない） |
|---|---|
| データモデル、真偽値の伝播、Apply Request、inactive、PVR、エージェントの責務分担、CLI、WebUI、ストア、スケジューラ | エージェントに使う LLM の選定、プロンプトの詳細、プログラム実行サンドボックスの実装、認証基盤の実装方式 |

## 2. 用語

| 用語 | 定義 |
|---|---|
| 仮説 (Hypothesis) | 真偽を問える命題。50 字以下の**主文**と、文字数に上限のない**背景情報**からなる。木の根は常に仮説（＝究極的な問い）。 |
| ストーリー (Story) | 「子仮説がすべて真なら親仮説は真になる」ことを保証する論理的なつながり。50 字以下の**タイトル**と 300 字以下の**概要**からなる。 |
| 親 / 子 / 孫、ストーリー / サブストーリー | **相対的な**関係を指す言葉で、木の中の絶対的な位置を表すものではない。どの階層でも同じ規則（文字数制限など）が適用される。 |
| 終端仮説 (Terminal Hypothesis) | active な子ストーリーを持たず、文献検索やプログラムの実装・実行などで直接真偽を確かめる仮説。終端であるという判定も Apply Request で承認されて初めて確定する。 |
| unexpanded（未展開） | 終端でもなく、子ストーリーをまだ一度も持ったことがない仮説の状態。作ったばかりの子仮説はこの状態から始まる。 |
| 検証結果 (Verdict) | 終端仮説の真偽値（true / false）と、その根拠となる**レポート**の組。両者は常に 1 対 1。 |
| レポート (Report) | 検証結果の根拠を書いた文書。参考文献からの引用とリンク、プログラムとその実行結果などを含む。 |
| artifacts | レポートが参照する根拠物の総称（引用・リンク・プログラム・実行結果・データ・人による記入など）。他の仮説の artifacts も参照・引用できる。 |
| Apply Request (AR) | 木やその検証結果への変更提案。opener が作り、opener とは別の reviewer が承認したときだけ正式なデータに反映される。GitHub の Pull Request にあたる。 |
| 物理検証リクエスト (PVR: Physical Verification Request) | 計算機の中だけでは検証できない物理的な問いについて、「人による検証手順」を書き下して人間に依頼するもの。 |
| inactive | 論理構造に重大な欠陥があるなどの理由で、ノードを計算から外した状態。inactive なノードとその子孫からは新しいノードを作れない。 |
| 要再検討フラグ | 子ストーリーを 1 つ以上持ったことがあり、今はそれがすべて inactive か false になっている非終端仮説に立つフラグ。代替ストーリーの検討を促す。 |
| exhausted バッジ | 代わりの道筋が尽きたと Builder が判断し、owner に判断を委ねた仮説に付く印。 |
| ハーネス | 本システム全体。ストア、API、検証ルール、真偽値の伝播エンジン、スケジューラ、CLI、WebUI を含む。 |

## 3. データモデル

### 3.1 木の形
- 根は**仮説**。
- 仮説ノードの子は必ず**ストーリーノード**、ストーリーノードの子は必ず**仮説ノード**。H → S → H → S … と交互に並ぶ。
- 1 つの仮説の下にストーリーは 0 個以上（複数ありうる）。1 つのストーリーの下に仮説は 1 個以上。
- DAG ではなく厳密な木とする。既存の仮説を別のストーリーで使いたいときは、新しいノードを作って引用する（§6.3）。

### 3.2 エンティティと属性

**Hypothesis**
| 属性 | 型 | 制約・説明 |
|---|---|---|
| id | string | 例 `H-123`。不変 |
| parent_story_id | id / null | 根のときだけ null |
| statement | string | 主文。**50 字以下** |
| background | text | 背景情報。**上限なし**（Markdown） |
| is_terminal | bool | 終端仮説かどうか。AR で承認されて確定する |
| expansion | unexpanded / expanded / terminal | 計算で決まる。unexpanded は「非終端で、子ストーリーを一度も持ったことがない」 |
| value | true / false / null | 終端なら入力（検証結果）、非終端なら計算結果 |
| verdict_id | id / null | 有効な Verdict（1 対 1） |
| needs_reconsideration | bool | 計算で決まる（§4.4） |
| exhausted | bool | owner に判断を委ねたことを示すバッジ（§6.1） |
| state | active / inactive | |
| inactive_reason | enum + text | `logic_flaw`（論理の欠陥。子仮説の欠陥によって親ストーリーごと外す場合を含む）/ `concluded_false`（`conclude_false` で外した）/ `other` |
| derived_from | {node_id, revision} / null | 検証済み仮説を流用したときの引用元（§6.3） |

**Story**
| 属性 | 型 | 制約・説明 |
|---|---|---|
| id | string | 例 `S-45` |
| parent_hypothesis_id | id | 必須 |
| title | string | **50 字以下** |
| summary | string | 概要。**300 字以下** |
| value | true / false / null | 常に計算結果 |
| state, inactive_reason | | 仮説と同じ |
| supersedes | id / null | このストーリーが置き換えた、inactive な旧ストーリー（任意。作り直しの経緯を辿るための記録で、計算には使わない） |

**Verdict（検証結果）** — `{ id, hypothesis_id, value: true|false, report_id, created_by, ar_id, status: valid|revoked, propagates: bool }`。終端仮説 1 つにつき有効なもの（`valid`）は 1 件。差し替えや終端解除で `revoked` になったものも履歴に残る。inactive な終端仮説に出された Verdict は `propagates = false`（記録として残すだけ）。

**Report** — `{ id, verdict_id, body(Markdown), artifact_refs[], citations[] }`。必ず 1 つの Verdict に属する（1 対 1）。`citations` には、他の仮説の artifact か、リビジョンで固定した部分木を指定する（§6.3）。

**Artifact** — `{ id, kind(file|link|citation|program|output|human_entry), sha256, uri, meta }`。中身のハッシュで識別し、変更しない。他の仮説のレポートからも参照できる。

**ApplyRequest** — `{ id, type, opener, reviewer, state, base_revision, payload(差分), comments[], reviews[] }`（§5）。

**PVR** — `{ id, hypothesis_id, procedure(Markdown), state, human_entries[], attachments[], resulting_ar_id }`（§9.4）。

**HumanRequest** — `{ id, author, body(自由記述), target_node_id?, state, replies[] }`。人間からエージェントへの依頼。Builder から owner への上申（exhausted）もこの形で記録する。

**Event（履歴）** — `{ seq, at, actor, kind, subject_id, before, after, ar_id? }`。追記のみで、書き換えも削除もしない。

### 3.3 制約（不変条件）
| ID | 制約 |
|---|---|
| C-01 | 根は仮説で、1 つの木に根は 1 つ。 |
| C-02 | 仮説の子はストーリー、ストーリーの子は仮説（交互）。 |
| C-03 | ストーリーは、子仮説を 1 つ以上含めた AR で作る（子仮説のないストーリーは作れない）。 |
| C-04 | 終端仮説は **active な**子ストーリーを持たない（inactive な子ストーリーは記録として残ってよい。`conclude_false` で終端化した場合など）。 |
| C-05 | value を直接入力できるのは、終端仮説の Verdict だけ。非終端仮説とストーリーの value は常に計算で決まる。 |
| C-06 | Verdict と Report は常に 1 対 1。非終端仮説にはレポートは要らない。 |
| C-07 | 文字数: 仮説の主文は 50 字以下、ストーリーのタイトルは 50 字以下、概要は 300 字以下。数え方は **Unicode NFC に正規化したあとのコードポイント数**（全角・半角を区別しない）。 |
| C-08 | inactive なノードとその子孫の下には、新しいノードを作れない。 |
| C-09 | 正式なデータを変更できるのは、承認された AR の適用だけ。**例外**として、owner（人間）の記録付きの直接操作（根の作成、直接の inactive 化）を認める。 |
| C-10 | AR の opener と reviewer は別の主体でなければならない。owner の直接操作は AR ではないので、この制約の対象外とする。 |
| C-11 | **仮説を inactive にするとき、その親ストーリーが active なら、同じ操作（AR でも owner の直接操作でも）の中で親ストーリーも必ず inactive にする**。親ストーリーの子孫全体（兄弟の子仮説を含む）も、まとめて inactive になる。その結果、**active なストーリーの子仮説はすべて active** という状態が常に成り立つ。validator が提出時と適用時に強制する。根の仮説には親ストーリーがないため、この規則は適用されない。 |

> C-11 により、active なストーリーの下に inactive な子仮説があるという状態は起こらない。そのため、ストーリーの AND の条件が知らないうちに緩むことはない。子仮説を差し替えたいときは、ストーリーごと作り直す（§7）。

## 4. 真偽値の伝播

### 4.1 値
すべてのノードの値は 3 値で、`true` / `false` / `null`（未決）のいずれか。

### 4.2 計算規則
- **終端仮説**: 入力値。有効な Verdict があればその値、なければ `null`。
- **ストーリー** = 子仮説の **AND**
  - 1 つでも false があれば `false`
  - すべて true なら `true`
  - それ以外は `null`
  - C-11 により、active なストーリーの子仮説はすべて active。そのため、AND は常に子仮説全体に対して計算する（inactive な子仮説をどう扱うかという問題は生じない）。
- **非終端仮説** = active な子ストーリーの **OR**（ただし false は伝わらない）
  - 1 つでも true があれば `true`
  - それ以外は `null`。**子ストーリーがすべて false でも自動では false にしない**（leader 決定。原文の「親仮説まで棄却されるかはわからない」に基づく）
  - **inactive な子ストーリーは OR から外す**（親仮説から見て存在しないものとして扱う）
- **inactive なノード**（とその子孫）は伝播に関わらない。inactive なノード自身の値と、inactive な終端仮説に出された Verdict の値は記録として表示するが、親には伝えない。

### 4.3 真理値表

ストーリー（子仮説 2 つの AND。3 つ以上でも同じ考え方）
| A \ B | true | null | false |
|---|---|---|---|
| **true** | true | null | false |
| **null** | null | null | false |
| **false** | false | false | false |

非終端仮説（子ストーリー 2 つの OR）
| S1 \ S2 | true | null | false |
|---|---|---|---|
| **true** | true | true | true |
| **null** | true | null | null |
| **false** | true | null | **null＋要再検討** |

ストーリーの AND は 3 値論理（Kleene）の AND そのものである。仮説の OR は、Kleene の OR から「false の結果を null に置き換える」変更を加えたもの。

### 4.4 要再検討フラグと unexpanded
- **要再検討フラグ**（`needs_reconsideration = true`）: 次の条件をすべて満たす仮説に立つ（計算で決まる）。
  1. 非終端で active である
  2. 子ストーリーを 1 つ以上**持ったことがある**
  3. 今の子ストーリーが**すべて inactive か false** である
- **unexpanded**: 非終端で、子ストーリーを一度も持ったことがない状態。要再検討の対象ではなく、「展開待ち」として別に扱う。作ったばかりの子仮説は、終端と判定されるか子ストーリーを持つまでこの状態にある。
- 要再検討フラグが立つと、スケジューラが Builder に「代替ストーリーの検討」タスクを渡す。ただし、exhausted バッジの付いた仮説は owner の判断待ちなので、タスクを作らない。

### 4.5 具体例
```
H0 究極の問い ........................ true  (S1 OR S2)
├─ S1 ストーリー1 ..................... false (H1 AND H2)
│   ├─ H1 [終端] ...................... true
│   └─ H2 [終端] ...................... false   ← 偽が出た
└─ S2 ストーリー2（代替）............... true  (H3 AND H4)
    ├─ H3 [終端・H1 を流用] ............ true   (H1 を引用するレポート)
    └─ H4 (非終端) .................... true  (S3)
        └─ S3 ......................... true
            └─ H5 [終端] .............. true
```
S2 がまだない段階では H0 は `null＋要再検討` になる（S1 を持ったことがあり、それが false のため）。Builder が S2 を作り、それが承認・検証されて H0 は `true` になる。S2 を作った直後の H4 は unexpanded（要再検討ではない）。

### 4.6 再計算
- Verdict の適用、ノードの inactive 化、ストーリーの追加などがあるたびに、変更されたノードから根までの経路を再計算する。
- 再計算は AR の適用と同じトランザクションの中で行う（途中の状態は外から見えない）。
- 値が変わったノードごとに `value_changed` イベントを記録する。

## 5. Apply Request のライフサイクル

### 5.1 役割
- **opener**: 変更を提案する主体。普段は Builder/Verifier。
- **reviewer**: 審査する主体。普段は Story Reviewer。opener とは別の主体でなければならない（C-10）。
- 人間（owner）はどちらにもなれる。また、C-09 の例外として、記録付きの直接操作もできる。

### 5.2 種別
| 種別 | 内容 | 主な審査観点 |
|---|---|---|
| `story.create` | 仮説の下にストーリーを新しく作る。子仮説（流用分を含む）もまとめて作る | 十分性（子仮説がすべて真なら親仮説が真になるか）、兄弟ストーリーとの整合性 |
| `story.add_hypothesis` | 既存のストーリーに子仮説を追加する | 追加後も論理が成り立つか |
| `node.edit` | 背景情報の追記、軽微な文言の修正 | 意味が変わっていないか（大きく変わるなら inactive にして作り直す） |
| `hypothesis.mark_terminal` | 終端仮説であると判定する | 単一の検証で真偽を決められる大きさか |
| `hypothesis.unmark_terminal` | 終端の判定を外す。**同じ AR の中で有効な Verdict を `revoked` にし（履歴には残す）、値を null に戻す** | 終端を外す理由 |
| `verdict.submit` | 終端仮説に検証結果（値＋レポート＋artifacts）を出す。inactive な終端仮説にも出せるが、その場合は伝播しない | 根拠が値を支えているか、再現できるか、引用は正しいか |
| `verdict.revise` | 検証結果を差し替える。古い Verdict は `revoked` として履歴に残る | 差し替える理由 |
| `node.inactivate` | ノードを inactive にする（理由が必須）。対象が仮説で、その親ストーリーが active なら、親ストーリーとその子孫全体も同じ AR で inactive にする（C-11） | 論理の欠陥が本当に重大か |
| `hypothesis.conclude_false` | 非終端仮説を積極的に偽と結論する。**直接の反証レポートがあるときに限る**（§6.4） | 反証レポートの妥当性 |

1 つの AR に複数の操作をまとめてよい（例: `story.create` の中で、子仮説の作成・終端判定・流用した仮説の Verdict を同時に行う）。適用は全部まとめて行い、一部だけ反映されることはない。

### 5.3 状態遷移
```
                 ┌──────────── 審査中 ─────────────┐
draft ─submit─▶ │ open ⇄ changes_requested        │ ─approve(open から)─▶ approved ─apply(自動)─▶ applied
                 │  request_changes / revise        │                         │
                 └──────────────────────────────────┘                  適用時の検証失敗
                    │ reject            │ withdraw                             ▼
                    ▼                   ▼                                   conflict ─rebase─▶ open
                 rejected            closed
```
- `reject`（reviewer）と `withdraw`（opener）は、`open` と `changes_requested` のどちらからでも出られる。
- `approve` できるのは `open` からだけ。`approved` になると、ハーネスが自動で適用する。適用の直前に、§3.3 の制約と `base_revision` との衝突をもう一度確認する。
- 審査中に対象のノードが inactive になった場合などは `conflict` になり、opener が rebase（作り直し）する。例外として、inactive な終端仮説に向けた `verdict.submit` は conflict にしない（§7）。
- コメントもレビューも、すべてイベントとして残る。

### 5.4 変更履歴
- 正式なデータへの変更は、すべて AR か owner の直接操作のどちらかに対応づく。
- ノードごとの履歴（作成、編集、終端判定、Verdict、inactive 化、値の変化）を時系列で見られる。
- 任意のリビジョン時点の木を再現できる（イベントソーシング）。

## 6. 仮説が偽になったときのフロー

### 6.1 流れ
1. Builder が終端仮説 H に `verdict.submit(false)` を出し、Reviewer が承認して適用される。
2. H の親ストーリー S は AND の規則により**自動的に false**（棄却）になる。
3. S の親仮説 P については、**棄却を確定させない**。
   - 兄弟ストーリーに true のものがあれば P は true のまま。
   - そうでなければ P は `null` のままで、子ストーリーがすべて inactive か false なら**要再検討フラグ**が立つ。
4. スケジューラが Builder に「P の再検討」タスクを渡す。
5. Builder は次のどれかを行う。
   - (a) **兄弟ストーリーを新しく作る**（`story.create`）。兄弟ストーリーがもともとない場合でも作れる。
   - (b) 既存の兄弟ストーリーの検証を先に進める。
   - (c) **P を直接否定する証拠がある**なら、反証レポートを付けて `hypothesis.conclude_false` を出す（§6.4）。
   - (d) 代わりの道筋が尽きたが、直接の反証はない場合: P は **null のまま**にし、要再検討フラグも残したまま、owner に上申して **exhausted バッジ**を付ける。そのあとの方針（新しい切り口の提示、保留、owner による判断など）は owner が決める。
6. Reviewer が審査する。`conclude_false` を除き、偽の結果は親へ連鎖して伝わらない。そのため、再検討の範囲は P とそのすぐ下に限られる。

### 6.2 偽になったストーリーの扱い
偽になったストーリーはそのまま残す（棄却された道筋も記録として価値がある）。inactive にするのは、**論理の欠陥があるとき（§7）か、`conclude_false` のとき**だけ。

### 6.3 検証済みの仮説を流用する
新しい兄弟ストーリーで、すでに真と検証された仮説 X をもう一度使いたい場合:

1. 新しいストーリーの下に**新しい仮説ノード X'** を作る（データ構造としては別のノード。`derived_from = {X, revision}`）。
2. X' を終端仮説とし、**引用するだけのレポート**を付けて `true` の Verdict を出す。引用の対象は「**その時点のリビジョンで固定した X の部分木**」とする。
   - X が終端なら、X の Verdict とレポート、artifacts を引用する。
   - X が非終端なら、**X を true にしている子ストーリーの配下にある Verdict 群**（そのストーリーの下にある、すべての終端仮説の Verdict）を引用する。
3. 1 と 2 は 1 つの `story.create` AR にまとめて、Reviewer が承認する。
4. 固定した部分木の中で Verdict の差し替え、inactive 化、終端解除が起きたら、X' に「引用元変更」の通知とバッジを付け、Builder の再検討タスクを作る。X' の値は自動では変えない（D-06）。

### 6.4 積極的に偽と結論する（`hypothesis.conclude_false`）
- **前提**: P を直接否定する反証レポートがあること。「代わりの道筋が見つからない」だけでは使えない。その場合は §6.1 の (d)（exhausted）にする。
- **中身**（1 つの AR でまとめて適用する）:
  1. P の active な子ストーリーをすべて inactive にする（理由は `concluded_false`）
  2. P を終端にする（C-04 は active な子ストーリーがないので満たされる）
  3. 反証レポートを付けて `false` の Verdict を出す
- **結果**: P は false になり、その結果は P の親ストーリーへ通常どおり伝わる。

## 7. inactive 化

- **いつ使うか**
  - ノードの論理構造に重大な欠陥が見つかったとき（`logic_flaw`）。例: ストーリーの十分性が成り立たない、仮説の主文が曖昧で真偽を決められない。
  - `conclude_false` で子ストーリーを外すとき（`concluded_false`）。
- **手続き**: `node.inactivate` AR に理由を必ず書き、Reviewer が承認する。owner は WebUI から直接 inactive にすることもできる（C-09 の例外で、C-10 の対象外。操作は記録される）。どちらの経路でも C-11 が適用される。
- **仮説を inactive にする場合（C-11）**: その親ストーリーが active なら、**親ストーリーごと inactive にする**。同じ AR に、ストーリーとその子孫全体（兄弟の子仮説を含む）が含まれる。子仮説だけを差し替える操作はない。
- **効果**
  - そのノードと子孫全体を伝播から外す（§4.2）。inactive になったストーリーは、親仮説の OR から外れる。
  - そのノードと子孫の下には**新しいノードを作れない**（C-08）。内容の編集もできない。
  - そのノードと子孫に向けた審査中の AR は `conflict` になる。ただし、終端仮説への `verdict.submit` と `verdict.revise` は除く。
  - データは削除せず、閲覧も引用もできる。
- **inactive な終端仮説への検証結果の提出**: 認める（祖先が inactive の場合も含む）。レポートと値の 1 対 1 の組を、通常どおり AR で審査して記録に残す。ただし伝播はしない（`propagates = false`）。原文の「inactive にもレポートの追加はできても良さそう」（やりかけの作業をコミットしないのは勿体無い）という意図に合わせた。
- **作り直し**: inactive にしたストーリーの親仮説（もとの仮説から見ると親の親）の下に、**新しい兄弟ストーリーを立てる**（`story.create`。OR に選択肢を 1 つ足すことになる）。
  - もとのストーリーで有効だった他の子仮説を使い回したい場合は、§6.3 の流用の手順に従う。つまり、新しいノードを作り、引用だけのレポートで true を入れる。
  - 新しいストーリーの `supersedes` に旧ストーリーを記録してもよい（任意）。
- **inactive からの復帰**: 認めない（D-10）。

```
H 親の親仮説 ─OR─┬─ S  旧ストーリー  [inactive・logic_flaw]  ← C-11 によりストーリーごと
                 │    ├─ Ha 欠陥のあった子仮説   [inactive]
                 │    └─ Hb 有効だった子仮説     [inactive]
                 └─ S′ 新しい兄弟ストーリー（supersedes: S は任意）
                      ├─ Hb′ Hb の流用（Hb を引用するレポートで true）
                      └─ Hc  新しい子仮説
```

## 8. エージェントの責務分担

### 8.1 エージェント
**① Builder / Verifier（木を作り、検証する役）** — AR の opener
- 問いを仮説とストーリーに分解して木を作る（`story.create` など）
- 終端判定を提案する（`mark_terminal`）
- 終端仮説を検証する（文献検索、プログラムの実装・実行）。レポートと artifacts を作り、`verdict.submit` を出す
- 偽が出たときや要再検討フラグが立ったときに、代替ストーリーを検討する（流用を含む）。道筋が尽きたら owner に上申する（exhausted）
- 計算機の中で検証できない終端仮説について PVR を起票する
- PVR に人間が記入した結果を、レポート＋真偽値の AR に変換する
- 人間からのフリーフォーマットのリクエストに応える
- 論理の欠陥に気づいたら inactive 化を提案する（C-11 に従って親ストーリーごと外し、新しい兄弟ストーリーで作り直す）

**② Story Reviewer（審査する役）** — AR の reviewer
- ストーリーの論理的な妥当性: 子仮説がすべて真なら親仮説が真になるか（十分性）、隠れた前提がないか
- 整合性: 兄弟ストーリーや祖先との矛盾、子仮説どうしの重複や循環がないか
- 終端判定の妥当性: 単一の検証で真偽を決められるか、検証手段は明確か
- 検証レポートの妥当性: 根拠が値を支えているか、引用は正確か、プログラムの実行は再現できるか
- PVR の結果を AR に変換したものが、人の記入に忠実か
- inactive 化と作り直したストーリー、`conclude_false`（直接の反証があるか）が妥当か

### 8.2 エージェントではなくハーネス側に置く機能
判断を伴わない機械的な処理はハーネスに置き、エージェントは判断だけに集中させる。

| 機能 | 内容 |
|---|---|
| スケジューラ / オーケストレータ | タスクキューの管理、優先度付け、担当の割り当てとリース（排他）、ループを回し続けること、停止条件と予算の管理 |
| 検証ルール（validator） | 文字数、木の形、終端・inactive・C-11 の制約、opener ≠ reviewer を、AR の提出時と適用時に機械的に確認する |
| 伝播エンジン | 真偽値、要再検討フラグ、unexpanded を計算する |
| AR エンジン | 状態遷移、全部まとめた適用、衝突の検出 |
| 通知 | イベントを購読しているエージェントや人間に知らせる。引用元が変わったことも知らせる |
| 履歴 | イベントログ、スナップショット |

### 8.3 スケジューラのタスク優先度と停止条件（推奨の初期値）
1. 審査待ちの AR の審査（Reviewer）
2. 差し戻された AR と conflict の対応（Builder）
3. 人間のリクエストと、PVR に記入された結果の取り込み（Builder）
4. 引用元が変わったことへの対応（Builder）
5. 要再検討フラグへの対応（Builder。exhausted のものは除く）
6. 値が null の終端仮説の検証（Builder）
7. unexpanded な仮説の展開（終端判定か、ストーリーの作成）（Builder。根に近いものから）

**停止条件**（どれか 1 つを満たしたら止める）:
- 根の値が決まり、**かつ**、引用元の変更への対応と要再検討の未処理タスクが残っていない
- 予算（トークン数・時間・タスク数）を使い切った
- owner が一時停止した

> 根の値が決まったあとも、その根拠になっている部分木のどこかで引用元の変更や要再検討が残っていれば、ループを止めない。D-06 で「値は自動では変えない」としているため、これらのタスクを処理しないと、根の値が古い根拠のまま確定してしまう。

### 8.4 人間（owner）
根の仮説（究極の問い）を作る。エージェントへリクエストを出す。PVR に結果を記入する。exhausted として上申された仮説の扱いを決める。必要に応じて AR を承認・却下したり、直接 inactive 化したりする（すべて記録される）。

## 9. CLI

### 9.1 方針
- gh に似たコマンド体系。コマンド名は仮に `hv`。
- すべてのコマンドに `--json` を付けられる（エージェントが扱いやすくするため）。終了コードは決まった値を返す。
- エージェントは計算機の中の特定のディレクトリ（ワークスペース）に常駐し、`hv task next` でタスクを受け取って処理し、また次を受け取る、を繰り返す。

### 9.2 コマンド例
```
hv auth login --role builder                 # エージェントの認証。役割はトークンに紐づく
hv tree view [<node>] [--depth 3] [--json]   # 木を表示
hv node view H-12                            # ノードの詳細（背景、Verdict、履歴）
hv node history H-12

hv ar create --type story.create --parent H-12 --file story.yaml
hv ar list --state open [--reviewer @me]
hv ar view AR-88 / hv ar diff AR-88
hv ar review AR-88 --approve | --request-changes | --reject --body "..."
hv ar comment AR-88 --body "..."
hv ar rebase AR-88 / hv ar withdraw AR-88

# verdict.submit の AR を作る（すぐに確定するわけではない。Reviewer の承認で適用される）
hv verdict submit H-34 --value false --report report.md --artifact ./out/result.csv \
                       [--cite H-7:A-301] [--cite-subtree H-9@r120]
hv artifact upload ./run.py ./run.log        # sha256 で登録し、ID を返す

hv pvr create H-50 --procedure procedure.md
hv pvr list --state answered
hv pvr convert PVR-3                         # 人の記入を元に verdict.submit の AR を作る

hv request list --state open                 # 人間からのリクエスト
hv request reply RQ-9 --body "..."
hv escalate H-12 --body "..."                # 道筋が尽きたことを owner に上申する（exhausted）

hv task next --role builder --wait           # スケジューラから次のタスクを受け取る（リース）
hv task done T-120 / hv task release T-120
hv watch                                     # イベントを流し続けて表示
```
他の仮説の artifact を引用するときは `hv verdict submit --cite` を使う（引用は必ず検証結果のレポートに含まれる）。

### 9.3 常駐ループの例
```bash
while true; do
  task=$(hv task next --role builder --wait --json)
  # エージェントが task.kind に応じて hv ar create / hv verdict submit などを行う
  hv task done "$(jq -r .id <<<"$task")"
done
```

### 9.4 PVR の状態
`open`（人の対応待ち）→ `in_progress` → `answered`（人が記入済み）→ `converted`（Builder が AR にした）→ `closed`（AR が適用された）。手順の不備で人が実施できなかった場合は `blocked` として差し戻す。

## 10. WebUI（人間向け）

| 画面 | 機能 |
|---|---|
| 木のビューア | 木を折りたたんで表示する。値（true / false / null）を色で、inactive をグレーで示す。要再検討・unexpanded・exhausted・引用元変更・審査中 AR・PVR 待ちをバッジで示す。絞り込みと検索ができる |
| ノード詳細 | 主文と背景、ストーリーの概要、Verdict とレポート（失効した Verdict と、伝播しない記録用の Verdict を含む）、artifacts、引用関係、履歴 |

| PVR 受付箱 | 検証手順を読み、結果をフリーフォーマットで記入する（ファイル・写真も添付可）。記入内容は `human_entry` artifact として保存する |
| AR 一覧と差分 | 審査中の AR とその差分、議論を見る。owner は承認・却下もできる |
| 履歴 / タイムライン | イベントを時系列で見る。任意の時点の木を表示する |
| ダッシュボード | 根の状態、検証が済んだ割合。要再検討・unexpanded・exhausted・引用元変更の未処理の数（別々に表示）。PVR 待ちの数。停止条件をどこまで満たしているか。予算の消化状況 |

PVR 結果の取り込み（決定）: 人間が WebUI に自由に記入する → Builder がそれをレポート＋真偽値の `verdict.submit` AR に変換する（人の記入は artifact として引用する）→ Reviewer が承認する。人の記入内容がそのまま真偽値になるわけではない。

## 11. 全体アーキテクチャ

```
 [Builder agent]  [Reviewer agent]        [人間]
  workspace/       workspace/               │
      │ hv CLI         │ hv CLI            WebUI
      └──────┬─────────┘                    │
             ▼                              ▼
   ┌──────────────── Harness API ─────────────────┐
   │ 検証ルール │ AR エンジン │ 伝播エンジン │ スケジューラ │ 通知 │
   └──────────────────────┬───────────────────────┘
                          ▼
   ┌──────────────── Store（GitHub に近い）───────────┐
   │ 構造化された木（ノード、AR、Verdict、PVR）           │
   │ ファイル / artifacts（中身のハッシュで管理、変更不可） │
   │ 履歴（追記のみのイベントログ＋スナップショット）       │
   └──────────────────────────────────────────────┘
```

- CLI と WebUI は同じ API を使う。役割（builder / reviewer / owner）はトークンで判別する。
- Store の構成（**推奨・初期値。設計時に確定**）: 初期は SQLite（あとで Postgres）＋ローカルの CAS ディレクトリ（あとで S3 互換ストレージ）。git での直接管理は採らず、必要なら git 形式へのエクスポート機能を付ける（D-13）。

## 12. 要件一覧

### 12.1 機能要件
| ID | 要件 |
|---|---|
| FR-01 | 仮説（主文 50 字以下、背景は無制限）とストーリー（タイトル 50 字以下、概要 300 字以下）を作成・保存できる |
| FR-02 | 仮説とストーリーが交互に並び、根が仮説である木構造を強制する |
| FR-03 | 1 つの仮説の下に複数のストーリーを作れる |
| FR-04 | 根の仮説（究極の問い）は owner が作る |
| FR-05 | 終端仮説の判定・判定解除を AR で行う。判定を外すときは、同じ AR で Verdict を失効させ、値を null に戻す |
| FR-06 | 終端仮説に、検証結果（値＋レポート＋artifacts、1 対 1）を AR で提出できる |
| FR-07 | 3 値（true / false / null）を、ストーリーは AND、仮説は OR で自動計算して伝播する |
| FR-08 | 子ストーリーを持ったことがあり、今はそれがすべて inactive か false の非終端仮説は null のままにし、要再検討フラグを立てる。子ストーリーを一度も持っていない仮説は unexpanded として区別する |
| FR-09 | inactive なノードとその子孫を伝播から外す。inactive な子ストーリーは、親仮説の OR から外す（ストーリーの AND は、C-11 によりすべて active な子仮説に対して計算する） |
| FR-10 | AR を作成・審査（承認・差し戻し・却下）・コメント・取り下げ・rebase できる。却下と取り下げは open と changes_requested のどちらからでもできる |
| FR-11 | 承認された AR を自動で適用する。適用は全部まとめて行い、適用時に制約をもう一度確認する |
| FR-12 | opener と reviewer が同じ主体になることを禁止する |
| FR-13 | ノードを inactive にできる（理由は必須）。inactive なノードとその子孫の下には新しいノードを作れない |
| FR-14 | 検証済みの仮説を流用できる（新しいノード＋引用するだけのレポート＋true）。引用の対象は、リビジョンで固定した部分木（非終端なら、それを true にしている子ストーリー配下の Verdict 群）とする |
| FR-15 | artifacts（ファイル・リンク・引用・プログラム・実行結果）を中身のハッシュで登録し、他の仮説から参照・引用できる |
| FR-16 | PVR の起票、人による結果の自由記入、Builder による AR への変換ができる |
| FR-17 | 人間がエージェントへフリーフォーマットのリクエストを出し、返信を受け取れる |
| FR-18 | スケジューラがタスクを生成し、優先度を付け、リースで割り当てる。停止条件（根の値が決まり、かつ、引用元の変更と要再検討の未処理がないこと／予算／owner による停止）と予算を管理する |
| FR-19 | すべての変更をイベントとして記録し、ノードごとの履歴と任意の時点の木を見られる |
| FR-20 | gh に似た CLI を提供する（全コマンドで JSON 出力に対応） |
| FR-21 | WebUI を提供する（木のビューア、ノード詳細、リクエスト、PVR、AR、履歴、ダッシュボード） |
| FR-22 | イベントを購読できる（`hv watch`、WebUI での通知） |
| FR-23 | 固定した引用元の部分木が変わったら、引用している仮説に通知とバッジを付け、再検討タスクを作る |
| FR-24 | 審査中の AR の対象が inactive になったら、その AR を conflict にする（終端仮説への verdict.submit / revise は除く） |
| FR-25 | 仮説を inactive にするとき、親ストーリーが active なら、同じ操作で親ストーリーとその子孫全体も inactive にすることを validator で強制する（C-11）。これにより、active なストーリーの子仮説は常にすべて active になる |
| FR-26 | 直接の反証レポートがある場合に限り、`hypothesis.conclude_false` で非終端仮説を偽と結論できる（子ストーリーの inactive 化、終端化、false の Verdict をまとめて適用する） |
| FR-27 | 代わりの道筋が尽きたことを owner に上申し、exhausted バッジを付けられる。exhausted の仮説には、再検討タスクを自動では作らない |
| FR-28 | inactive な終端仮説にも verdict.submit を出せる。値は記録として残し、伝播はしない |

### 12.2 非機能要件
| ID | 区分 | 要件 |
|---|---|---|
| NFR-01 | 監査可能性 | 正式なデータの変更は、すべて「誰が・いつ・どの AR（または owner の直接操作）で・なぜ」まで追える。イベントログは追記のみ |
| NFR-02 | 再現性 | artifacts は変更不可で、中身のハッシュで管理する。プログラムによる検証では、コード、入力、実行環境の情報、出力を残す。任意の時点の木を再現できる |
| NFR-03 | 並行性 | 複数の Builder と Reviewer が同時に動ける。AR は `base_revision` による楽観ロック、タスクはリースで排他する。適用はトランザクションで行う |
| NFR-04 | 整合性 | §3.3 の制約は、どの経路で変更しても常に成り立つ |
| NFR-05 | 耐障害性 | エージェントやハーネスが途中で止まっても、リースが切れればタスクは別の担当に回り、処理を再開できる。API は同じ要求を何度送っても結果が変わらないようにする（実現方式は推奨・初期値として idempotency key を想定。設計時に確定） |
| NFR-06 | 性能 | 想定規模の木に対して、木の表示と再計算が対話的に使える応答時間で終わる（規模と目標値は設計時に確定） |
| NFR-07 | セキュリティ | 役割ごとに権限を分ける（builder / reviewer / owner）。エージェントのトークンは役割に紐づける |
| NFR-08 | 可観測性 | タスクの処理量、AR の滞留数、要再検討・unexpanded・exhausted の数、予算の消化状況を見られる |
| NFR-09 | コスト管理 | スケジューラに予算の上限と停止条件を設定できる |
| NFR-10 | 移植性 | データを JSON や Markdown でエクスポートできる。読み取り専用のビューは静的ホスティングでも出せる |

## 13. 未決事項と設計判断

| ID | 論点 | 状態 | 推奨案・判断 |
|---|---|---|---|
| D-01 | 子ストーリーがすべて偽の非終端仮説の値 | **決定** | 自動で false にしない。null＋要再検討フラグにして、Builder に代替ストーリーを検討させる |
| D-02 | 仮説を積極的に偽と結論する手段 | 未決（方針は決定） | **決定済みの範囲**: `conclude_false` は、直接の反証レポートがあるときに限る。代わりの道筋が尽きただけなら、null のまま要再検討フラグを残し、owner に上げて exhausted バッジを付ける。**推奨**: 中身は既存の操作の組み合わせとする（子ストーリーを `concluded_false` として inactive にする、終端にする、反証レポート付きで false の Verdict を出す）。「反証ストーリー」（子仮説がすべて真なら親が偽になるストーリー）は AND/OR の意味を複雑にするため初期版では採らず、将来の検討とする |
| D-03 | inactive なノードに検証結果を出せるか | **決定** | inactive な終端仮説（祖先が inactive の場合を含む）にも verdict.submit（レポートと値の 1 対 1）を認める。値は記録として残し、伝播はしない。原文の「inactive にもレポートの追加はできても良さそう」に合わせた。v0.1 の推奨案だった「Verdict なしの artifact 添付」は取り下げた |
| D-04 | PVR の結果の取り込み | **決定** | 人間が WebUI に自由に記入する → Builder がレポート＋真偽値の AR に変換する → Reviewer が承認する。人の記入は `human_entry` artifact として扱う |
| D-05 | 終端判定の手続き | **決定** | AR（Builder が提案し、Reviewer が承認する）を通す。判定を外すときは、同じ AR で Verdict を失効させ、値を null に戻す |
| D-06 | 流用元が変わったときの扱い | **決定** | 引用はリビジョンで固定した部分木を対象とする。固定した部分木が変わったら、流用した仮説に通知とバッジを付け、Builder の再検討タスクを作る。値は自動では変えない。その代わり、未処理の対応は停止条件に含める（§8.3） |
| D-07 | PVR の起票に審査が必要か | 未決 | **推奨**: 不要。ただし対象は、終端と承認された仮説に限る。手順の妥当性は人間が実施時に確かめ（不備があれば `blocked` で差し戻す）、結果は変換された AR の審査で担保する |
| D-08 | 人間（owner）の権限 | 未決 | **推奨**: owner はすべての操作ができる（AR の承認、直接の inactive 化、根の作成）。直接操作は C-09 の例外で、C-10 の対象外。C-11 は owner にも適用する。操作はすべて記録する |
| D-09 | 有効な子仮説がないストーリー | **解消** | C-03 と C-11 により、active なストーリーは常に 1 つ以上の子仮説を持ち、それらはすべて active |
| D-10 | inactive からの復帰 | 未決 | **推奨**: 認めない。必要なら新しいノードとして作り直す（履歴を単純に保つため） |
| D-11 | 検証結果の差し替え | 未決 | **推奨**: `verdict.revise` AR で行う。古い Verdict とレポートは `revoked` として履歴に残る。値が変わったら伝播を再計算する |
| D-12 | 文字数の数え方 | 未決 | **推奨**: Unicode NFC に正規化したあとのコードポイント数で数える（全角・半角を区別しない） |
| D-13 | ストアの実装 | 未決 | **推奨・初期値（設計時に確定）**: DB（イベントソーシング）＋ CAS。木の制約を確実に守らせたいので、git をそのまま使う方式は採らない。git 形式へのエクスポートは任意で付ける |
| D-14 | Reviewer の独立性 | 未決 | **推奨・初期値（設計時に確定）**: Builder とは別のセッション・コンテキストで動かす。可能なら別のモデルやプロンプトにする。承認は 1 件で足りるが、件数は設定で変えられるようにする |
| D-15 | 適用済みノードの文言の編集 | 未決 | **推奨**: 子ノードや Verdict がついたあとは、主文とタイトルの意味を変える編集を禁止する（変える場合は inactive にして、§7 の手順で作り直す）。背景は追記のみ認める |
| D-16 | スケジューラの優先度と停止条件 | 停止条件は決定 | 停止条件は §8.3 のとおり（根の値が決まり、かつ、引用元の変更と要再検討の未処理がない／予算／owner による停止）。優先度は §8.3 を推奨・初期値とし、owner が設定で変えられるようにする |
| D-17 | 複数の木（複数の問い）への対応 | 未決 | **推奨・初期値（設計時に確定）**: 1 つのストアで複数のプロジェクト（＝木）を扱えるようにする。プロジェクトをまたぐ引用は artifact の引用として認める |
| D-18 | 子仮説の inactive 化と AND の整合 | **決定**（customer） | C-11: 仮説を inactive にするときは、親ストーリーごと inactive にする。置き換えの子仮説を足す方式は採らない。作り直しは、親の親にあたる仮説の下に新しい兄弟ストーリーを立てて行い、使い回したい子仮説は流用の手順（新しいノード＋引用レポートで true）を使う。validator で強制する |
| D-19 | 要再検討の範囲 | **決定** | 「子ストーリーを持ったことがあり、今はそれがすべて inactive か false」に限る。未展開の仮説は unexpanded として分ける |
| D-20 | exhausted 後の扱い | 未決 | **推奨**: owner が次のどれかを選ぶ。① 新しい切り口を Builder にリクエストする（バッジを外して再開）、② 保留する（null のまま）、③ owner が反証レポートを付けて `conclude_false` を opener として出す。バッジは、新しい子ストーリーが適用されたら自動で外す |

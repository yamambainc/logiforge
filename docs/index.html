仮説検証ハーネス 要件定義（概要）

問いを「仮説—ストーリー」の木に分解し、エージェントが検証を回し続けるための、GitHub に近い情報管理基盤

版 v0.2（レビューを反映したドラフト） ・ 2026-11-11 ・ 詳細版（正本）: requirements.md

3 分でわかる要点

  1. 究極の問いを根にして、仮説とストーリーが交互に並ぶ木を作る。ストーリーは子仮説の AND、仮説は子ストーリーの OR。
  2. 人やエージェントが値を入れるのは終端仮説だけで、値は必ずレポートと 1 対 1 の組で入れる。上位の値はすべて自動で計算される。
  3. 木への変更はすべて Apply Request（Builder が提案し、Reviewer が承認する）を通して正式なデータになり、履歴が残る。
  4. 偽が出ても、親仮説は自動では棄却しない。要再検討として代替ストーリーを探す。偽と結論するのは、直接の反証があるときだけ。
  5. エージェントは CLI で常駐ループを回し、人間は WebUI で閲覧・依頼・物理検証の結果の記入を行う。ループを回すスケジューラはハーネスの機能。

1背景と目的

研究のように答えが分からない問いに取り組むとき、人もエージェントも「問いを仮説に分ける → 検証できる大きさまで分ける → 検証する → 外れたら別の道を探す」を繰り返しています。ただ、この過程は普通、会話やメモの中に散らばっていて、どの仮説がどの論理で問いを支えているのか、どの結論がどの根拠に基づくのか、偽になった仮説の影響がどこまで及ぶのかを後から辿れません。

本プロジェクトでは、構造化データ（仮説とストーリーの木）と非構造化データ（レポート・artifacts）を組み合わせ、再帰的に回し続けられる環境を作り、そこにエージェントを常駐させます。

目的

  • 究極的な問いを根とする「仮説—ストーリー」の木を、規則付きのデータとして管理する
  • 末端の仮説だけを検証すれば、上位の真偽が自動的に決まるようにする
  • すべての変更を Apply Request（opener / reviewer）で審査し、履歴に残す
  • エージェントは CLI、人間は WebUI で同じ基盤を操作する。計算機の中で検証できない問いは、人間に物理検証を依頼できる

GitHub との違い

変更履歴が残り、ファイル（レポート・artifacts）をコミットでき、変更提案に opener / reviewer がいる、という点は GitHub と同じです。違うのは、管理対象がファイルだけでなく規則付きの木構造であり、その木の上で真偽値が自動的に伝わる点です。

対象外: LLM の選定、プロンプトの詳細、プログラム実行サンドボックスの実装、認証基盤の実装方式

2用語

用語定義
仮説 (Hypothesis)真偽を問える命題。50 字以下の主文と、文字数に上限のない背景情報からなる。木の根は常に仮説（＝究極的な問い）。
ストーリー (Story)「子仮説がすべて真なら親仮説は真になる」ことを保証する論理的なつながり。50 字以下のタイトルと300 字以下の概要からなる。
親 / 子 / 孫、ストーリー / サブストーリー相対的な関係を指す言葉で、木の中の絶対的な位置を表すものではない。子仮説は孫仮説から見れば親仮説になる。どの階層でも同じ規則（文字数制限など）が適用される。
終端仮説active な子ストーリーを持たず、文献検索やプログラムの実装・実行などで直接真偽を確かめる仮説。終端であるという判定も Apply Request で承認されて初めて確定する。
unexpanded（未展開）終端でもなく、子ストーリーをまだ一度も持ったことがない仮説の状態。作ったばかりの子仮説はこの状態から始まる。
レポート検証結果の根拠を書いた文書。終端仮説の真偽値と常に 1 対 1 の組になる（この組を検証結果 / Verdict と呼ぶ）。非終端仮説には不要。
artifactsレポートが参照する根拠物の総称。参考文献からの引用とリンク、プログラムとその実行結果、データ、人による記入など。他の仮説の artifacts も参照・引用できる。
Apply Request (AR)木やその検証結果への変更提案。opener が作り、opener とは別の reviewer が承認したときだけ正式なデータに反映される。GitHub の Pull Request にあたる。
物理検証リクエスト (PVR)Physical Verification Request。計算機の中だけでは検証できない物理的な問いについて、「人による検証手順」を書き下して人間に依頼するもの。
inactive論理構造に重大な欠陥があるなどの理由で、ノードを計算から外した状態。inactive なノードとその子孫からは新しいノードを作れない。
要再検討フラグ子ストーリーを 1 つ以上持ったことがあり、今はそれがすべて inactive か false になっている非終端仮説に立つフラグ。代替ストーリーの検討を促す。
exhausted バッジ代わりの道筋が尽きたと Builder が判断し、owner に判断を委ねた仮説に付く印。

3データモデル

3.1 木の形

  • 根は仮説。仮説の子は必ずストーリー、ストーリーの子は必ず仮説。H → S → H → S … と交互に並ぶ（冒頭の具体例を参照）。
  • 1 つの仮説の下にストーリーは 0 個以上（複数ありうる）。1 つのストーリーの下に仮説は 1 個以上。
  • DAG ではなく厳密な木とする。既存の仮説を別のストーリーで使いたいときは、新しいノードを作って引用する（§6）。

3.2 ノード種別と属性

種別主な属性制約
仮説statement 主文 / background 背景 / is_terminal / expansion（unexpanded / expanded / terminal） / value / verdict_id / needs_reconsideration / exhausted / state / inactive_reason / derived_from（ノードとリビジョン）主文は 50 字以下、背景は上限なし。value は、終端なら入力、非終端なら計算結果
ストーリーtitle / summary / value（常に計算結果） / state / inactive_reason / supersedes（任意。置き換えた inactive な旧ストーリーを指す記録で、計算には使わない）タイトルは 50 字以下、概要は 300 字以下。子仮説を 1 つ以上持つ
inactive_reasonlogic_flaw（論理の欠陥。子仮説の欠陥で親ストーリーごと外す場合を含む） / concluded_false（conclude_false で外した） / other、と理由の本文inactive にするときは必須

3.3 制約（不変条件）

ID制約
C-01根は仮説で、1 つの木に根は 1 つ。
C-02仮説の子はストーリー、ストーリーの子は仮説（交互）。
C-03ストーリーは、子仮説を 1 つ以上含めた AR で作る（子仮説のないストーリーは作れない）。
C-04終端仮説は active な子ストーリーを持たない（inactive な子ストーリーは記録として残ってよい。conclude_false で終端化した場合など）。
C-05value を直接入力できるのは、終端仮説の Verdict だけ。非終端仮説とストーリーの value は常に計算で決まる。
C-06Verdict とレポートは常に 1 対 1。非終端仮説にはレポートは要らない。
C-07文字数: 仮説の主文は 50 字以下、ストーリーのタイトルは 50 字以下、概要は 300 字以下。数え方は Unicode NFC に正規化したあとのコードポイント数（全角・半角を区別しない）。提出時と適用時に機械的に確認する。
C-08inactive なノードとその子孫の下には、新しいノードを作れない。
C-09正式なデータを変更できるのは、承認された AR の適用だけ。例外として、owner（人間）の記録付きの直接操作（根の作成、直接の inactive 化）を認める。
C-10AR の opener と reviewer は別の主体でなければならない。owner の直接操作は AR ではないので、この制約の対象外とする。
C-11仮説を inactive にするとき、その親ストーリーが active なら、同じ操作（AR でも owner の直接操作でも）の中で親ストーリーも必ず inactive にする。親ストーリーの子孫全体（兄弟の子仮説を含む）も、まとめて inactive になる。その結果、active なストーリーの子仮説はすべて active という状態が常に成り立つ。validator が提出時と適用時に強制する（根の仮説には親ストーリーがないので対象外）。

C-11 により、active なストーリーの下に inactive な子仮説があるという状態は起こりません。そのため、ストーリーの AND の条件が知らないうちに緩むことはありません。子仮説を差し替えたいときは、ストーリーごと作り直します（§7）。

4真偽値の伝播

すべてのノードの値は 3 値で、true false null（未決）のいずれかです。終端仮説の値は入力変数、それ以外の値は自動的に計算される結果です。

ストーリー ＝ 子仮説の AND

  • 1 つでも false があれば false
  • すべて true なら true
  • それ以外は null
  • C-11 により、active なストーリーの子仮説はすべて active。AND は常に子仮説全体に対して計算する

兄弟仮説どうしは、親ストーリーに対して AND の関係

非終端仮説 ＝ active な子ストーリーの OR（false は伝わらない）

  • 1 つでも true があれば true
  • それ以外は null（すべて false でも false にはしない）
  • inactive な子ストーリーは OR から外す（親仮説から見て存在しないものとして扱う）

兄弟ストーリーどうしは、親仮説に対して OR の関係

inactive なノード（とその子孫）は伝播に関わりません。inactive なノード自身の値と、inactive な終端仮説に出された Verdict の値は記録として表示しますが、親には伝えません。

決定子ストーリーがすべて偽になった非終端仮説は自動では false にしません。null（未決）のまま要再検討フラグを立て、Builder に代替ストーリーを検討させます。原文の「親仮説まで棄却されるかはわからない（新たに兄弟ストーリーを作れば検証できる可能性が残る）」に基づく判断です。偽と結論するのは、直接の反証があるときだけです（§6.2）。

子が 3 つ以上でも考え方は同じです。ストーリーの AND は 3 値論理（Kleene）の AND そのものです。仮説の OR は、Kleene の OR から「false の結果を null に置き換える」変更を加えたものです。

4.2 要再検討フラグと unexpanded

要再検討フラグ

次の条件をすべて満たす仮説に立ちます（計算で決まります）。

  1. 非終端で active である
  2. 子ストーリーを 1 つ以上持ったことがある
  3. 今の子ストーリーがすべて inactive か false である

フラグが立つと、スケジューラが Builder に代替ストーリーの検討タスクを渡します（exhausted の仮説は除きます）。

unexpanded（未展開）

非終端で、子ストーリーを一度も持ったことがない状態です。作ったばかりの子仮説は、終端と判定されるか子ストーリーを持つまでこの状態にあります。要再検討とは別の「展開待ち」として扱います。

4.3 再計算のタイミング

Verdict の適用、inactive 化、ストーリーの追加などがあるたびに、変更されたノードから根までの経路を再計算します。再計算は AR の適用と同じトランザクションの中で行い（途中の状態は外から見えない）、値が変わったノードごとに value_changed イベントを記録します。

5Apply Request のライフサイクル

木は、Story Reviewer に承認されて初めて正式なものになります。それまでの変更は Apply Request（AR）という一時データとして保持します。opener（普段は Builder/Verifier）が作り、opener とは別の reviewer（普段は Story Reviewer）が審査します。人間（owner）はどちらの役にもなれ、C-09 の例外として記録付きの直接操作もできます。

5.1 種別

種別内容主な審査観点
story.create仮説の下にストーリーを新しく作る。子仮説（流用分を含む）もまとめて作る十分性（子仮説がすべて真なら親仮説が真になるか）、兄弟ストーリーとの整合性
story.add_hypothesis既存のストーリーに子仮説を追加する追加後も論理が成り立つか
node.edit背景情報の追記、軽微な文言の修正意味が変わっていないか
hypothesis.mark_terminal終端仮説であると判定する（決定この判定も AR を通す）単一の検証で真偽を決められる大きさか
hypothesis.unmark_terminal終端の判定を外す。同じ AR の中で有効な Verdict を失効（revoked）させ、値を null に戻す（履歴には残す）終端を外す理由
verdict.submit終端仮説に検証結果（値＋レポート＋artifacts）を出す。inactive な終端仮説にも出せるが、その場合は伝播しない根拠が値を支えているか、再現できるか、引用は正しいか
verdict.revise検証結果を差し替える（古いものは revoked として残る）差し替える理由
node.inactivateノードを inactive にする（理由が必須）。対象が仮説で、その親ストーリーが active なら、親ストーリーとその子孫全体も同じ AR で inactive にする（C-11）論理の欠陥が本当に重大か
hypothesis.conclude_false非終端仮説を積極的に偽と結論する。直接の反証レポートがあるときに限る（§6.2）反証レポートの妥当性

1 つの AR に複数の操作をまとめられます（例: story.create の中で、子仮説の作成・終端判定・流用した仮説の Verdict を同時に行う）。適用は全部まとめて行い、一部だけ反映されることはありません。

5.2 状態遷移

5.3 変更履歴

  • 正式なデータへの変更は、すべて AR か owner の直接操作のどちらかに対応づきます。コメントもレビューもイベントとして残ります。
  • ノードごとの履歴（作成、編集、終端判定、Verdict、inactive 化、値の変化）を時系列で見られます。
  • イベントソーシングにより、任意のリビジョン時点の木を再現できます。

6仮説が偽になったときのフロー

  1. Builder が終端仮説 H に verdict.submit(false) を出し、Reviewer が承認して適用される。
  2. H の親ストーリー S は自動的に false（棄却）になる（AND の規則）。
  3. S の親仮説 P については棄却を確定させない。true の兄弟ストーリーがあれば P は true のまま。なければ P は null のままで、子ストーリーがすべて inactive か false なら要再検討フラグが立つ。
  4. スケジューラ（ハーネスの機能）が Builder に「P の再検討」タスクを渡す。
  5. Builder は次のどれかを行う。
    (a) 兄弟ストーリーを新しく作る（兄弟ストーリーがもともとない場合でも作れる）
    (b) 既存の兄弟ストーリーの検証を先に進める
    (c) P を直接否定する証拠があるなら、反証レポートを付けて conclude_false を出す（§6.2）
    (d) 代わりの道筋が尽きたが、直接の反証はない場合: P は null のままにし、要再検討フラグも残したまま、owner に上申して exhausted バッジを付ける。そのあとの方針は owner が決める
  6. Reviewer が審査する。conclude_false を除き、偽の結果は親へ連鎖して伝わらない。そのため、再検討の範囲は P とそのすぐ下に限られる。

偽になったストーリーは削除も inactive 化もせず、そのまま残します（棄却された道筋も記録として価値があるため）。inactive にするのは、論理の欠陥があるとき（§7）か、conclude_false のときだけです。

6.1 検証済みの仮説を流用する

新しい兄弟ストーリーで、すでに真と検証された仮説 X を使いたい場合でも、データ構造としては新しい仮説ノード X′ を作ります（derived_from = X とそのリビジョン）。X′ を終端仮説とし、引用するだけのレポートを付けて true を入れます。引用の対象は「その時点のリビジョンで固定した X の部分木」です。
  • X が終端なら、X の Verdict とレポート、artifacts を引用します。
  • X が非終端なら、X を true にしている子ストーリーの配下にある Verdict 群を引用します。
この一連の操作は 1 つの story.create AR にまとめ、Reviewer が承認します。固定した部分木の中で変更（Verdict の差し替え、inactive 化、終端解除）が起きたら、X′ に「引用元変更」の通知とバッジを付け、再検討タスクを作ります。X′ の値は自動では変えません（D-06）。

6.2 積極的に偽と結論する（hypothesis.conclude_false）

  • 前提: P を直接否定する反証レポートがあること。「代わりの道筋が見つからない」だけでは使えません。その場合は上の (d)（exhausted）にします。
  • 中身（1 つの AR でまとめて適用する）: ① P の active な子ストーリーをすべて inactive にする（理由は concluded_false）、② P を終端にする（C-04 は active な子ストーリーがないので満たされる）、③ 反証レポートを付けて false の Verdict を出す。
  • 結果: P は false になり、その結果は P の親ストーリーへ通常どおり伝わります。

7inactive 化

  • いつ使うか: 論理構造に重大な欠陥が見つかったとき（logic_flaw。十分性が成り立たない、主文が曖昧で真偽を決められない、など）。conclude_false で子ストーリーを外すとき（concluded_false）。
  • 手続き: node.inactivate AR に理由を必ず書き、Reviewer が承認する。owner は WebUI から直接 inactive にすることもできる（C-09 の例外で、C-10 の対象外。操作は記録される）。どちらの経路でも C-11 が適用される。
  • 仮説を inactive にする場合（C-11）: その親ストーリーが active なら、親ストーリーごと inactive にする。同じ AR に、ストーリーとその子孫全体（兄弟の子仮説を含む）が含まれる。子仮説だけを差し替える操作はない。
  • 効果: そのノードと子孫全体を伝播から外す（inactive なストーリーは親仮説の OR から外れる）。そのノードと子孫からは新しいノードを作れないし、編集もできない。そこに向けた審査中の AR は conflict になる（終端仮説への verdict.submit / revise は除く）。データは消さず、閲覧も引用もできる。
  • inactive な終端仮説への検証結果の提出: 認める（祖先が inactive の場合を含む）。レポートと値の 1 対 1 の組を通常どおり AR で審査し、記録として残す。ただし伝播はしない。
  • 作り直し: inactive にしたストーリーの親仮説（もとの仮説から見ると親の親）の下に、新しい兄弟ストーリーを立てる（OR に選択肢を足す）。もとのストーリーで有効だった他の子仮説を使い回したいときは、流用の手順（§6.1。新しいノードを作り、引用だけのレポートで true を入れる）を使う。新しいストーリーの supersedes に旧ストーリーを記録してもよい（任意）。inactive からの復帰は認めない（D-10）。

8エージェントの責務分担

「仮説とストーリーを考えて検証する役」と「それを審査する役」の opener / reviewer 構造を基本にします。終端仮説の検証は、木を作るエージェントが兼ねても問題が生じないため、両者を 1 つの役割にまとめます。判断を伴わない機械的な処理はエージェントではなくハーネスの機能として切り出します。

① Builder / Verifier（木を作り、検証する役。AR の opener）

  • 問いを仮説とストーリーに分解して木を作る。終端判定を提案する
  • 終端仮説を検証する（文献検索、プログラムの実装・実行）。レポートと artifacts を作り、検証結果の AR を出す
  • 偽が出たときや要再検討フラグが立ったときに、代替ストーリーを検討する（流用を含む）。道筋が尽きたら owner に上申する（exhausted）
  • 計算機の中で検証できない終端仮説について PVR を起票する。人が記入した結果を AR に変換する
  • 人間からのフリーフォーマットのリクエストに応える。論理の欠陥に気づいたら inactive 化を提案する（親ストーリーごと外し、新しい兄弟ストーリーで作り直す）

② Story Reviewer（審査する役。AR の reviewer）

  • 論理的な妥当性: 子仮説がすべて真なら親仮説が真になるか（十分性）、隠れた前提がないか
  • 整合性: 兄弟ストーリーや祖先との矛盾、子仮説どうしの重複や循環がないか
  • 終端判定: 単一の検証で真偽を決められるか、検証手段は明確か
  • 検証レポートの妥当性: 根拠が値を支えているか、引用は正確か、実行は再現できるか
  • PVR の結果を変換した AR が人の記入に忠実か。inactive 化と conclude_false（直接の反証があるか）が妥当か

ハーネスの機能（エージェントではない）

  • スケジューラ / オーケストレータ: タスクキューの管理、優先度付け、担当の割り当てとリース、ループを回し続けること、停止条件と予算の管理
  • 検証ルール: 文字数、木の形、終端・inactive・C-11 の制約、opener ≠ reviewer を機械的に確認する
  • 伝播エンジン（真偽値、要再検討、unexpanded）、AR エンジン、通知（引用元の変更を含む）、履歴

人間（owner）

  • 根の仮説（究極の問い）を作る
  • エージェントへフリーフォーマットのリクエストを出す。PVR に結果をフリーフォーマットで記入する
  • exhausted として上申された仮説の扱いを決める
  • 必要に応じて AR の承認・却下や直接の inactive 化を行う（すべて記録される）

8.1 スケジューラのタスク優先度と停止条件

優先度は推奨の初期値です（owner が設定で変えられます）。

  1. 審査待ちの AR の審査（Reviewer）
  2. 差し戻された AR と conflict の対応（Builder）
  3. 人間のリクエストと、PVR に記入された結果の取り込み（Builder）
  4. 引用元が変わったことへの対応（Builder）
  5. 要再検討フラグへの対応（Builder。exhausted のものは除く）
  6. 値が null の終端仮説の検証（Builder）
  7. unexpanded な仮説の展開（終端判定か、ストーリーの作成）（Builder。根に近いものから）
決定停止条件（どれか 1 つを満たしたら止める）: ① 根の値が決まり、かつ、引用元の変更への対応と要再検討の未処理タスクが残っていない、② 予算（トークン数・時間・タスク数）を使い切った、③ owner が一時停止した。D-06 で引用元が変わっても値を自動では変えないとしているため、①では未処理のタスクがないことも条件に含めています。

Builder も Reviewer も複数のインスタンスを同時に動かせます（タスクはリースで排他します）。

9CLI

gh に似たコマンド体系の CLI を用意します（コマンド名は仮に hv）。すべてのコマンドに --json を付けられます。各エージェントは計算機の中の特定のディレクトリ（ワークスペース）に常駐し、hv task next でタスクを受け取って処理する、を繰り返して検証を回し続けます。hv verdict submit は verdict.submit の AR を作るコマンドで、Reviewer が承認したときに初めて値が確定します。他の仮説の artifact や部分木を引用するときは --cite を使います。

コマンド例を開く 
# 閲覧
hv tree view [<node>] [--depth 3] [--json]
hv node view H-12
hv node history H-12

# Apply Request
hv ar create --type story.create --parent H-12 --file story.yaml
hv ar list --state open [--reviewer @me]
hv ar view AR-88        |  hv ar diff AR-88
hv ar review AR-88 --approve | --request-changes | --reject --body "..."
hv ar comment AR-88 --body "..."
hv ar rebase AR-88      |  hv ar withdraw AR-88

# 検証結果（verdict.submit の AR を作る。Reviewer の承認で適用される）
hv verdict submit H-34 --value false --report report.md --artifact ./out/result.csv \
                       [--cite H-7:A-301] [--cite-subtree H-9@r120]
hv artifact upload ./run.py ./run.log         # sha256 で登録し、ID を返す

# 物理検証リクエスト / 人間とのやりとり
hv pvr create H-50 --procedure procedure.md
hv pvr list --state answered
hv pvr convert PVR-3                          # 人の記入から verdict.submit の AR を作る
hv request list --state open
hv request reply RQ-9 --body "..."
hv escalate H-12 --body "..."                 # 道筋が尽きたことを owner に上申する（exhausted）

# 常駐ループ用
hv task next --role builder --wait            # スケジューラから次のタスクを受け取る（リース）
hv task done T-120  |  hv task release T-120
hv watch                                      # イベントを流し続けて表示
# 常駐ループの例（エージェントのワークスペースで実行）
while true; do
  task=$(hv task next --role builder --wait --json)
  # エージェントが task.kind に応じて hv ar create / hv verdict submit などを行う
  hv task done "$(jq -r .id <<<"$task")"
done

PVR の状態: open → in_progress → answered（人が記入済み）→ converted（Builder が AR にした）→ closed（AR が適用された）。手順に不備があって人が実施できない場合は blocked として差し戻します。

13未決事項と設計判断

決定は leader が決めた方針、未決は推奨案を付けた検討事項、解消は他の決定によって論点でなくなったものです。主な決定: 偽を自動で親に伝えない（D-01）、inactive な終端仮説にも Verdict を出せる（D-03）、C-11（D-18）、要再検討と unexpanded の区別（D-19）、停止条件（D-16）。

一覧（D-01〜20）を開く
ID論点状態推奨案・判断
D-01子ストーリーがすべて偽の非終端仮説の値決定自動で false にしない。null＋要再検討フラグにして、Builder に代替ストーリーを検討させる
D-02仮説を積極的に偽と結論する手段未決
方針は決定		決定済みの範囲: conclude_false は、直接の反証レポートがあるときに限る。代わりの道筋が尽きただけなら、null のまま要再検討フラグを残し、owner に上げて exhausted バッジを付ける。推奨: 中身は既存の操作の組み合わせとする（子ストーリーを concluded_false として inactive にする、終端にする、反証レポート付きで false の Verdict を出す）。「反証ストーリー」（子仮説がすべて真なら親が偽になるストーリー）は AND/OR の意味を複雑にするため初期版では採らず、将来の検討とする

D-11検証結果の差し替え未決推奨: verdict.revise AR で行う。古い Verdict とレポートは revoked として履歴に残る。値が変わったら伝播を再計算する

停止条件		停止条件は §8.1 のとおり（根の値が決まり、かつ、引用元の変更と要再検討の未処理がない／予算／owner による停止）。優先度は §8.1 を推奨・初期値とし、owner が設定で変えられるようにする
D-17複数の木（複数の問い）への対応未決推奨・初期値（設計時に確定）: 1 つのストアで複数のプロジェクト（＝木）を扱えるようにする。プロジェクトをまたぐ引用は artifact の引用として認める
D-18子仮説の inactive 化と AND の整合決定（customer 決定）C-11: 仮説を inactive にするときは、親ストーリーごと inactive にする。置き換えの子仮説を足す方式は採らない。作り直しは、親の親にあたる仮説の下に新しい兄弟ストーリーを立てて行い、使い回したい子仮説は流用の手順（新しいノード＋引用レポートで true）を使う。validator で強制する
D-19要再検討の範囲決定「子ストーリーを持ったことがあり、今はそれがすべて inactive か false」に限る。未展開の仮説は unexpanded として分ける
D-20exhausted 後の扱い未決推奨: owner が次のどれかを選ぶ。① 新しい切り口を Builder にリクエストする（バッジを外して再開）、② 保留する（null のまま）、③ owner が反証レポートを付けて conclude_false を opener として出す。バッジは、新しい子ストーリーが適用されたら自動で外す

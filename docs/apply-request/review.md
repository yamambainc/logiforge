# 論理レビュー

apply request が、どういう条件で反映され、論理レビューがどう行われるかを確かめるときに読む。
論理レビューの仕組みの正本は、このページである。

## 反映の条件

[apply request](README.md) は、次の条件をすべて満たすと反映される。

- 差分を書いたどのセッションとも別のセッションによる `approve` がある。
  - push された先頭のコミットは、どれも、書いたセッションが記録される。
- `approve` が有効なのは、`approve` した時点の差分に対してだけである。
  - apply request が更新されたら、それまでの `approve` は無効になる。
- 最新の差分に対するレビューのうち、最後のものが `approve` である。

この条件は、GitForge の「承認を必須にする」設定（required review）に相当する。

- 論理レビューは、CLI を使う主体か、WebUI の利用者が行う。人も reviewer になれる。
  - WebUI のレビューは、CLI のレビューと同じ意味である。approve で反映の条件を満たしたら、反映まで行う。
  - WebUI でレビューできるのは、その repository に書ける利用者だけである（[役割](../roles/README.md#利用者)）。
  - WebUI のセッションは、ブラウザのタブごとに別である。そのため、差分を書いた CLI のセッションとは、いつも別のセッションになる。

## 起動

- 論理レビューを起動するのは、Logiforge の外の仕組み（CI など）である。
  - Logiforge は、論理レビューを起動しない。
- 外の仕組みは、レビュー待ちの apply request を、[着手できる作業](../work/README.md) の問い合わせで見つける。

## レビューの材料

Logiforge は、apply request ごとに「レビューの材料」を返す問い合わせを提供する。
材料は、次のものである。

- 差分そのもの
- 操作の対象ノードの、現在の値
- 対象ノードの親の仮説から根までの、各仮説の主文
- 兄弟ストーリーの、タイトルと概要と値
- 引用している部分木（固定した `main` のコミットのもの）と artifact

対象ノードと兄弟ストーリーは、操作ごとに次のものである。

| 操作 | 対象ノード | 兄弟ストーリー |
|---|---|---|
| `story.create` | 親仮説 | 親仮説のほかの子ストーリー |
| `story.inactivate` | そのストーリー | 同じ親仮説のほかの子ストーリー |
| `verdict.submit`、`node.edit` | その仮説 | その仮説が属するストーリーと同じ親仮説を持つ、ほかのストーリー |

根の仮説への `verdict.submit` と `node.edit` には、兄弟ストーリーはない。根の仮説は、ストーリーに属さないから。

apply request の説明欄は、材料に含めない。

- なぜ：opener の推論がそのまま入り、コンテキストを分けた意味がなくなるから。

審査で確かめることは、[論理レビューの審査観点](review-criteria.md) に書く。

## 想定する使い方

次の使い方を想定する。ただし、要件ではない。

- 外の仕組みが、レビュー待ちの apply request を見つけるたびに、新しいコンテキストで reviewer を動かす。
- reviewer は、レビューの材料だけを読んで審査する。
- レビューを終えたら、その reviewer は使い捨てる。

これを要件にしない理由は、Logiforge からは確かめられないからである。
この使い方をすると、次の利点がある。

- 前のレビューの文脈に、引きずられない。
- 同じ材料なら、判断を再現しやすい。

## プロンプト

- レビューのプロンプトは、Logiforge 自体の git リポジトリに置く。
- プロンプトは差し替えられる。
- 標準のプロンプトを 1 つ同梱する。
- プロンプトの変更は、Logiforge の範囲外とする。
  - プロンプトの変更は、その git リポジトリの通常のレビューに従う。

## 保証の範囲

Logiforge が確かめること：

- reviewer のセッション ID が、差分を書いたどのセッション ID とも違うこと。
  - 差分を書いたセッション ID は、差分を書いた主体の自己申告である。Logiforge は、それが正しいかを確かめない。
  - 差分を書いたセッションを正しく申告するのは、CLI を使う側の責任である。
  - 差分を書いたセッションを申告していない先頭のコミットは、`approve` できない。
  - 短い間に何度も push されると、Logiforge が見なかった途中のコミットのセッションは、記録されない。
  - WebUI のレビューでは、セッションの分離は、文脈の分離を保証しない。WebUI のタブは、いつも別のセッションだから。
    - 自分が書いた差分や、自分が指示した差分を、自分で `approve` しないのは、人の責任である。
    - WebUI は、自分が作った apply request なら、`approve` の前にそのことを示す（[apply request と履歴](../webui/history.md)）。

Logiforge が記録すること：

- `approve` ごとの、reviewer のセッション ID
- `approve` ごとの、使ったプロンプトのリビジョン

対応しないこと：

- 同じ主体が、別のセッションを名乗るなりすまし
  - 認証基盤は、この仕様の範囲外である（[目的と範囲](../concepts/README.md)）。

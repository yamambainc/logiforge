# 壊れた repository を直す

反映によらない変更が `main` に入ったとき、Logiforge が何を示し、どう直すかを確かめるときに読む。

## 壊れた repository

- `main` の変更は、apply request の反映でだけ行う（[反映](README.md)）。
- GitForge の `main` を守る設定は、勧めるが求めない。
  - なぜ：守る設定は、GitForge とプランによって使えないことがあるから（例：GitHub Free の private のリポジトリ）。後から見つけて直せれば、仕様の性質は保てる。
- 反映によらない変更が `main` に入るか、`main` が書き換えられたら（force push など）、Logiforge が見つけ、その repository を「壊れている」状態にする。
  - なぜ書き換えも含めるか：古い反映まで巻き戻すと、残ったコミットはどれも反映によるものなので、結論が消えたことに気づけないから。
  - 反映によるものかは、コミットのメッセージでなく、GitForge の記録（書き込み主体が merge した pull request か）で決める。
  - なぜ：コミットのメッセージは、だれでも書けるから。
- 壊れる前の時点（反映によらない変更の直前、または書き換えの前）を、「最後に正しかった時点」と呼ぶ。

## 壊れているあいだ

- 木を読む操作は、最後に正しかった時点の木を返し、壊れていることを誤りとして添える。
  - WebUI は、最後に正しかった時点の木を示し、壊れていることと、壊れた変更のコミットを示す。
  - CLI は、最後に正しかった時点の木を出力し、壊れていることを誤りとして返す（終了コードを 0 以外にする）。git で clone した木を扱うコマンドも、壊れていることを誤りとして返す。
  - なぜ最後に正しかった時点か：反映によらない変更は、論理レビューを通っていないので、その木と値を正しいものとして示せないから。
- 反映するのは、直すための apply request だけである。ほかの apply request は、作れるが、反映しない。
  - なぜ：壊れた木の上に重ねた変更は、直し方によって前提が変わるから。

## 直し方

直すための apply request は、次の 2 種類である。どちらも、ふつうの apply request と同じく、論理レビューで `approve` されて反映される（[論理レビュー](review.md)）。

- 戻す（`repair.revert`）：`main` の木の全体を、最後に正しかった時点の木と同じにする。
  - 反映によらない変更を、すべて取り消す。
  - 差分の検査の、append-only の規則は適用しない。結果の木の全体が、最後に正しかった時点の木と同じであることだけを確かめる。
- 認める（`repair.accept`）：反映によらない変更（書き換えのあとの `main`）を、そのまま認める。
  - 認めるのは、直すための apply request を作った時点の `main` までである。そのあとに入った反映によらない変更は、認めない。
  - 木の置き場所（`tree/` と `artifacts/`）の外のファイルを含む変更は、認めない。戻すことでだけ直す。
  - reviewer は、最後に正しかった時点から今の `main` までの差分を、ふつうの apply request の差分と同じ観点で審査する（[論理レビューの審査観点](review-criteria.md)）。
  - 認めたあとの木で、不変条件が破れていれば、警告として残る。直すのは、新しい apply request である。

- 反映されると、repository は壊れていない状態に戻る。
- 反映によらない変更のコミットは、履歴に残る。消さない（[監査](../architecture/README.md)）。

## 着手できる作業

- 壊れた repository を直すことは、着手できる作業である（[着手できる作業](../work/README.md)）。
- 直すための apply request が open のあいだは、ほかの主体に作業として返さない。

# 目的と範囲

Logiforge が何のためにあり、どこまでを扱うかを確かめるときに読む。

## 解く課題

研究のように答えが分からない問いでは、人もエージェントも次を繰り返す。

1. 問いを仮説に分ける。
2. 仮説を、検証できる大きさまで分ける。
3. 検証する。
4. 外れたら、別の道を探す。

この過程は、会話やメモの中に散らばりやすい。
散らばると、次のことを後から辿れない。

- どの仮説が、どの論理で問いを支えているか
- どの結論が、どの根拠に基づくか
- 偽になった仮説の影響が、どこまで及ぶか

## 目的

構造化データと非構造化データを組み合わせ、再帰的に回し続けられる環境を作る。
エージェントが常駐して使う正本にする。

- 構造化データは、[仮説とストーリーの木](../tree/README.md)。
- 非構造化データは、[レポートと artifact](../tree/verdict.md)。

この環境は、次のことを満たす。

- 究極的な問いを根とする木を、規則付きのデータとして管理する。
- 葉の仮説だけを検証すれば、上位の真偽が自動で決まる（[真偽値の伝播](../tree/propagation.md)）。
- すべての変更を [apply request](../apply-request/README.md) で審査し、履歴に残す。
- エージェントは [CLI](../cli/README.md)、人間は [WebUI](../webui/README.md) で、同じ基盤を使う。
- 計算機の中で検証できない問いは、[PVR](../human-requests/README.md) で人間に物理検証を依頼する。

## 位置づけ

- Logiforge は、仮説と根拠を記録する正本（system of record）である。
  - [Forge](glossary.md) がコードの正本であるのと同じ位置づけである。
  - エージェントを包んで動かす仕組みではない。

## Forge との関係

次の点は、Forge と同じ仕組みにする。

- 変更履歴が残る。
- ファイル（レポートと artifact）をコミットできる。
- 変更提案に opener と reviewer がいる。

違いは、管理対象がファイルだけでなく、規則付きの木構造であること。
木の上では、真偽値が自動で伝わる。

## 対応しないこと

- エージェントに使う LLM（大規模言語モデル）の選定
- エージェントのプロンプトの詳細
- プログラムを実行するサンドボックスの実装
- 認証基盤の実装方式
- エージェントへの自由記述の依頼（会話）
  - Forge の issue、チャット、エージェント自身の画面など、既存の仕組みを使う。
